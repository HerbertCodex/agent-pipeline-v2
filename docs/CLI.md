# Outil `apv` (Agent Pipeline V3)

`apv` est l'outil en ligne de commande du plugin APV3. Il reprend de V2 ce qui a fait ses preuves (schéma des specs, registre des décisions, minimum de sécurité OWASP, périmètre des tâches, exécution des contrôles, reçus) sans le contrôleur : aucune commande ne lance d'agent, ne décide à la place du chef de projet ni n'écrit sur un service externe.

Installation locale : `npm run build`, puis `node dist/cli.js <commande>` ou `npx apv <commande>` depuis le dépôt du plugin. Node 22.16 ou plus, Git, Linux, macOS ou WSL2. Aucune dépendance d'exécution.

## Conventions communes

- Toutes les commandes acceptent `--help` (ou `apv help <commande>`).
- `--json` produit une sortie structurée, stable, sur la sortie standard ; sans elle, la sortie est un texte en français.
- `--repo <chemin>` désigne le projet (par défaut : le dossier courant).
- Codes de sortie : `0` succès, `1` échec du contrôle (spec invalide, contrôle rouge, fichier hors périmètre...), `2` appel incorrect ou commande indisponible.
- Fichiers lus dans le projet :
  - configuration : `.apv/config.json`, sinon `pipeline.v2.json` (projet V2, tant que `apv onboard` n'a pas créé `.apv/config.json`) ;
  - registre des décisions : `.apv/DECISIONS.json`, sinon `.agent-pipeline/DECISIONS.json` (projet V2).
- De la configuration, seules les sections `name` (nom du projet, écrit par `apv init`), `gates`, `risk`, `validationRules`, `environment.passEnv`, `skills`, `preview`, `design`, `structure`, `run`, `spec`, `review`, `receipts`, `resources`, `suite`, `stacks`, `batch`, `web`, `reuse`, `map` et `freshness` sont lues par le chargeur commun ; la section `db` est lue et validée par `apv db check`. Les champs d'agent, de budget, de délais, de modèles et de réglage d'un fichier V2 sont ignorés (et listés comme tels par `apv gates run --json` et `apv status --json`).

## `apv init`

```
apv init [--name <nom>] [--repo <chemin>] [--json]
```

Prépare un projet pour APV3 (`/apv:init`). Crée ce qui manque dans `.apv/`, **sans jamais écraser un fichier existant** : la commande peut être relancée, elle ne complète que ce qui manque.

| Élément | Contenu initial |
|---|---|
| `.apv/config.json` | `{ "name": "<nom>", "gates": [...] }` : les contrôles de l'arborescence et de la réutilisation seulement, `structure` (`apv structure check --base {{baseSha}}`, étape `task`, [STRUCTURE.md](STRUCTURE.md)) et `code-map` (`apv map --check`, étape `task` : l'implementer régénère et commite la carte dans son commit, décision D1 de la revue du pipeline du 2026-10-03 validée par l'opérateur (« oui à tout »), document suivie-pilotage/REVUE-PIPELINE-2026-10-03.md du projet pilote) pour tout projet et `reuse` (`apv reuse check --base {{baseSha}}`, étape `task` : `apv gates run` demande alors `--base`) pour un projet web, avec la section `reuse` détectée ([REUSE.md](REUSE.md)) ; pas de section `preview` ni `design` ; ce sont aussi les contrôles qu'exigent les règles avant fusion ([REGLES.md](REGLES.md)) : une configuration existante n'est jamais modifiée, les contrôles requis qui lui manquent sont listés (`reuse.missingRequired` en JSON) |
| `.apv/DECISIONS.json` | registre vide, valide pour `apv ledger validate` |
| `.apv/brief.md` | consigne commune des implementers, tirée du modèle `skills/chef-de-projet/references/brief-type.md` du plugin (le bloc de modèle, nom du projet substitué) ; les passages entre chevrons restent à adapter |
| `.apv/specs/`, `.apv/state/` | dossiers vides |
| `.apv/.gitignore` | fichiers machine (`state/*.log`, `state/task.json`, `state/preview.json`, `receipts/`), créé ou complété comme par `apv quota` |
| `.apv/code-map.md` | la carte du code, comme [`apv map`](#apv-map) |
| `docs/carte-architecture.md` (`structure.architectureMap`) | la carte de l'architecture, comme [`apv structure map`](#apv-structure-map), écrite en dernier quand elle manque, jamais remplacée |

Le nom du projet est `--name`, sinon le nom du dossier du dépôt. La commande travaille à la racine du dépôt Git qui contient le dossier courant (ou `--repo`) et refuse hors d'un dépôt Git. Elle liste ce qui est créé, complété et ce qui existait déjà ; rien n'est commité.

Maquettes validées : si la configuration existante déclare leur dossier (`design.dir`) ou des groupes (`design.groups`, `design.defaultGroup`), ou si ce dossier existe (`docs/design` par défaut), `apv init` ajoute aussi à `.gitattributes` (créé ou complété) la ligne `<dossier>/**/*.html -whitespace`, quand Git ne l'applique pas déjà pour le dossier et ses groupes (`git check-attr whitespace`) ; avec des groupes, l'ancienne ligne `<dossier>/*.html -whitespace` est remplacée à sa place : voir [`apv design`](#apv-design). `apv onboard` fait de même.

Projet web : dépendance d'interface dans `package.json` (Svelte, SvelteKit, React, Next.js, Vue, Nuxt, Astro, Solid, Preact, Lit, Angular, Remix, Qwik, htmx, Alpine) ou fichier d'interface (`.svelte`, `.vue`, `.tsx`, `.jsx`, `.astro`, `.html`...) hors de la documentation. La section `reuse` détectée : `reference` (`origin/HEAD`, sinon `origin/main` ou `origin/master` ; jamais la branche courante, absente sans dépôt distant), `shared` (les plus hauts dossiers `components`, `ui`, `shared`, `common`, `widgets`, `primitives`... qui contiennent des composants, hors des dossiers de routes), `native` (composant partagé générique qui remplace `select`, `dialog`, `datalist`, celui des primitives d'abord ; dossier des primitives `ui` ou `primitives` comme chemin permis, repris par `styles.allowedPaths`), `typography.locale` (le `lang` du document). Une configuration existante n'est jamais modifiée. La carte ne bloque jamais l'installation : au-delà de 50 000 fichiers elle est partielle, et une carte impossible à construire est signalée (`mapNote`) sans empêcher la configuration. Les contrôles appellent `apv` par son nom : la sortie avertit quand il n'est pas sur le PATH (`apvOnPath`).

Branches fusionnées : quand `origin` est l'adresse d'un dépôt GitHub (`https://<hôte>/<propriétaire>/<dépôt>`, `git@<hôte>:<propriétaire>/<dépôt>` ou `ssh://`), `apv init` lit son réglage « supprimer la branche après fusion » par `gh api repos/<propriétaire>/<dépôt> --jq '{default_branch, fork, delete_branch_on_merge}'` (`APV_GH` remplace `gh` ; 20 s au plus par appel). Seul github.com est interrogé d'office ; un autre hôte ne l'est que si `gh auth status --hostname <hôte>` réussit (un hôte GitHub Enterprise où `gh` est connecté), sinon « non interrogé » : l'adresse d'un autre serveur n'est jamais envoyée ailleurs. Toute partie identifiant de l'adresse (`utilisateur:jeton@`) est masquée (`***@`) dans la sortie et le JSON. Faux, la sortie le signale (« ATTENTION : … les branches s'accumulent ») avec la commande qui l'active, `gh api -X PATCH repos/<propriétaire>/<dépôt> -F delete_branch_on_merge=true` (avec `--hostname` hors de github.com), que l'outil ne lance jamais ; vrai, elle le dit en une ligne ; illisible (droits insuffisants, `gh` absent, réseau, hôte inconnu de `gh`), elle dit pourquoi, sans changer le code de sortie. Sans `origin` GitHub, rien n'est appelé. `apv stack merge` et `apv stack batch --merge` suppriment de toute façon les branches qu'ils fusionnent ([`apv stack`](#apv-stack)).

Sortie : `0` succès, `1` hors d'un dépôt Git, modèle de consigne introuvable ou configuration détectée refusée par le schéma, `2` appel incorrect. En JSON : `repo`, `name`, `created`, `completed`, `existing`, `reuse` (`web`, `signals`, `gates` ajoutés, `section` écrite ou `null`, `map` : chemin de la carte ou `null` si elle n'a pu être écrite, `mapNote`, `apvOnPath`), `github` (`repo`, `host`, `deleteBranchOnMerge` vrai, faux ou `null`, `command` quand il est faux, `note` quand il n'a pas été lu).

## `apv onboard`

```
apv onboard [--repo <chemin>] [--specs <dossier>] [--dry-run] [--json]
```

Fait passer sous APV3 un projet déjà commencé (`/apv:onboard`, spécification section 14). Comme `apv init`, la commande crée seulement ce qui manque dans `.apv/`, **sans jamais écraser un fichier existant**, et se relance sans effet ; elle travaille à la racine du dépôt Git et refuse hors d'un dépôt. Le nom du projet est celui du dossier du dépôt. Tout est lu et vérifié avant la première écriture : un refus laisse le dépôt intact.

**Projet V2** (`pipeline.v2.json` et/ou `.agent-pipeline/DECISIONS.json`) :

| Source V2 | Dans `.apv/` |
|---|---|
| `pipeline.v2.json` | `config.json` : `name`, puis `gates`, `risk`, `validationRules`, `skills` et `environment.passEnv` recopiés tels quels et validés par le schéma d'APV3. Tout le reste (`agent`, `roles`, `roleProfiles`, `modelRouting`, `workflow`, `feedback`, `limits`, `setup`, `concurrency`, `maxRunMs`, `environment.id`...) est **ignoré** et listé : ces champs pilotaient le contrôleur retiré. |
| `.agent-pipeline/DECISIONS.json` | `DECISIONS.json` : copie à l'identique. Le format du registre n'a pas changé entre V2 et V3 (même schéma, même `apv ledger validate`) : aucune conversion. `DECISIONS.md` est régénéré depuis le registre, comme par `apv ledger apply`. |
| specs V2 | `specs/<id>.json`, voir ci-dessous |

Un `pipeline.v2.json` ou un registre V2 illisible, ou refusé par le schéma (le registre : par les mêmes règles que `apv ledger validate`), fait sortir en `1` avec toutes les erreurs, **sans rien écrire** : un registre vide créé dans `.apv/` masquerait les décisions V2, puisque `.apv/DECISIONS.json` est lu en priorité. Un fichier V2 dont la cible existe déjà dans `.apv/` n'est pas relu. Les fichiers V2 restent en place, jamais modifiés.

**Specs V2.** V2 garde ses specs dans sa base d'état (`~/.local/state/agent-pipeline-v2`), hors du dépôt : l'outil ne la lit pas. Il cherche les fichiers de spec gardés par le projet (les propositions passées à `apv2 spec draft --file`) dans `.agent-pipeline/specs/`, `specs/`, `docs/specs/` et dans le dossier `--specs` (qui peut être hors du dépôt). Chaque fichier `.json` qui a la forme d'une spec (`title` et `tasks`, ou `{ "request", "spec" }`) est validé comme par `apv spec validate --draft` sur le dépôt ; accepté, il est copié tel quel dans `.apv/specs/<id>.json`, où `<id>` est son nom en kebab-case sans le suffixe `-import`. Une demande de l'opérateur rangée à côté (`<id>-request.txt`, comme dans le projet pilote) est jointe : le fichier écrit a alors la forme `{ "request": "...", "spec": { ... } }`. Les fichiers refusés sont listés avec leurs erreurs, jamais copiés.

**Projet sans V2** : `config.json` propose les contrôles que le dépôt déclare déjà, avec `mandatory: false` et, dans la sortie, leur source et une note (à relire, `covers`, `resources` et `passEnv` à compléter) :

| Contrôle | `package.json` (scripts) | `Makefile` (cibles) | `pyproject.toml` |
|---|---|---|---|
| `check` | `check`, `typecheck`, `type-check` | `check`, `typecheck` | `[tool.mypy]` : `mypy .` |
| `lint` | `lint` | `lint` | `[tool.ruff]` : `ruff check .` |
| `test` | `test` | `test` | `[tool.pytest]` : `python -m pytest` |
| `build` | `build` | `build` | |
| `e2e` | `e2e`, `test:e2e` | `e2e`, `test-e2e` | |

Le gestionnaire de paquets vient de `packageManager`, sinon du fichier de verrouillage (`pnpm`, `yarn`, `bun`, sinon `npm run <script>`) ; les outils Python passent par `uv run` ou `poetry run` si le projet a leur fichier de verrouillage. La première source trouvée gagne ; aucune commande n'est inventée. Le registre créé est vide.

**Arborescence et réutilisation**, dans les deux cas, quand la configuration est créée : les contrôles `structure`, `code-map` et, pour un projet web, `reuse` sont ajoutés après les autres (sous un identifiant que V2 n'utilisait pas), avec la section `reuse` détectée comme par `apv init`. La carte du code est écrite (`.apv/code-map.md`). Pour un projet web, le rapport liste ce qui est **déjà** dupliqué ou refait sur tout le projet (règles de `apv reuse check` sans base : nombre par règle, 20 premiers constats, blocs copiés d'abord) : ces constats existent sur la référence et ne bloqueront pas ; leur résorption est une spec de rangement décidée par l'opérateur.

Le rapport liste aussi les dossiers à plat déjà présents avec leurs sous-dossiers proposés (signalés sans bloquer par le contrôle `structure` ; tout ajout y sera refusé). Dans les deux cas, le reste est celui d'`apv init` : `brief.md`, `specs/`, `state/`, `.gitignore`, `code-map.md`, la carte de l'architecture (`docs/carte-architecture.md`, jamais remplacée). La sortie liste aussi les fichiers de `.agent-pipeline/` non repris (rôles, compétences : le plugin les fournit) et les indices d'aperçu (script `preview` ou `apercu`, fichier de `scripts/`), à décrire dans la section `preview` avec l'opérateur ; puis la suite : relire `config.json` et `brief.md`, `apv ledger validate`, `apv gates run` (avec `--base` si un contrôle utilise `{{baseSha}}`), commit de `.apv/`. Rien n'est commité.

`--dry-run` prend les mêmes décisions et affiche le même plan (« Serait créé »), sans rien écrire.

Sortie : `0` succès, `1` hors d'un dépôt Git, fichier V2 illisible ou invalide, modèle de consigne introuvable, `2` appel incorrect (dont un dossier `--specs` introuvable). En JSON : `repo`, `name`, `dryRun`, `v2` (`config`, `ledger`, `notImported`), `config` (`status`, `source`, `kept`, `ignored`, `gates`, `detected`), `reuse` (comme `apv init`, plus `existing` : `counts` par règle et `examples`, ou `null` hors projet web ; `architecture` : `file`, `status`, `note`), `structure` (`crowded` : dossier, fichiers de code, sous-dossiers proposés), `ledger` (`status`, `source`, `decisions`, `hash`), `specs` (`searched`, `imported`, `existing`, `rejected`), `previewHints`, `created`, `completed`, `existing`, `next`.

## `apv spec validate`

```
apv spec validate <fichier> [--repo <chemin>] [--request <texte> | --request-file <fichier>]
                  [--config <fichier>] [--draft] [--json]
```

Valide une spec et liste **toutes** les erreurs d'un coup : schéma (propriétés manquantes ou inconnues, longueurs, énumérations), identifiants en double, critères inconnus, dépendances manquantes ou cycliques, motifs de chemins non pris en charge, couverture des décisions du registre, plan de sécurité.

Le minimum de sécurité est recalculé depuis le dépôt exactement comme au lancement en V2 (fin de l'incident 14 du journal) : analyse de la demande de l'opérateur, du type de projet (`skills.projectType`) et des fichiers concernés, à savoir les chemins du dépôt que la demande nomme et les chemins littéraux des tâches. La spec doit reprendre les sujets OWASP, les exigences, le modèle de menace et les tests négatifs que ce minimum impose.

La demande de l'opérateur vient, dans l'ordre :
1. de `--request` ou `--request-file` ;
2. du document de spec, s'il a la forme `{ "request": "...", "spec": { ... } }` ;
3. à défaut, de la demande rangée par `/apv:spec` dans `.apv/state/demande-<id>.md` (pour la spec `.apv/specs/<id>.json`), que `apv run start` lit de la même façon : même minimum de sécurité à la validation et au lancement ;
4. à défaut, du texte de la spec elle-même (titre, problème, périmètre, critères, tâches ; les exclusions ne comptent pas).

Seule une demande fournie (cas 1 ou 2) sert à vérifier les citations des résolutions de décisions ambiguës.

Par défaut, la spec est contrôlée comme au lancement : aucune question ouverte, aucune ambiguïté non résolue, chaque critère porté par une tâche. `--draft` relâche ces trois règles pour une spec en cours de rédaction.

**Décisions exigées.** Chaque décision `product` confirmée du registre doit être couverte par un critère (`decisionCoverage`), et chaque décision `product` ambiguë posée en question, **sauf si elle déclare un périmètre qui ne concerne pas la spec** : champ facultatif `scope` de la décision ([DECISIONS.md](DECISIONS.md#périmètre-dune-décision--scope)), avec `paths` (motifs de chemins, syntaxe des chemins autorisés) et/ou `specs` (identifiants de specs). Une décision avec `scope` est exigée quand un de ses motifs peut désigner un chemin que les `allowedPaths` d'une tâche autorisent (recoupement exact des deux motifs), ou quand `specs` nomme la spec (nom du fichier sans `.json`) ; une décision sans `scope` reste exigée de toute spec. Le message d'une décision non couverte dit pourquoi elle est exigée (« sans périmètre », « son périmètre src/** recoupe le chemin autorisé src/lib/x.ts », « son périmètre nomme la spec ») et propose la solution : la rattacher à un critère, ou, si elle ne concerne pas la spec, lui donner un périmètre par une décision qui la remplace (`supersedes`, `apv ledger plan` puis `apply`).

**Avertissements de taille et de profondeur** (jamais une erreur, sans effet sur le code de sortie) : au-delà des seuils de la section `spec` de `.apv/config.json` ([CONFIGURATION.md](CONFIGURATION.md#taille-des-specs--spec)), plus de `maxTasks` tâches (6 par défaut) ou de `maxAcceptance` critères (30), la validation propose de découper la demande en specs indépendantes de 4 à 6 tâches, livrées en parallèle, chacune avec sa PR (`SPEC_SIZE`) ; au-delà de `maxDepth` couches de dépendances (3, les vagues de `apv run start`), elle nomme le chemin le plus long et propose le motif « contrats d'abord » (`SPEC_DEPTH`). En sortie lisible, une section « N avertissement(s) » après le résultat.

Sortie : `0` spec valide, `1` spec invalide ou illisible, `2` appel incorrect. En JSON : `valid`, `issues` (`code`, `message`), `warnings` (`code`, `message`), `limits` (`maxTasks`, `maxAcceptance`, `maxDepth` appliqués), `security` (`minimumLane`, `topics`, `requiresThreatModel`, `negativeTestsRequired`, `signals`), `requestSource`, `ledgerFile`, `configFile`, `sha`.

## `apv spec new`

```
apv spec new <id> [--title <texte>] [--repo <chemin>] [--json]
```

Écrit le gabarit `.apv/specs/<id>.json` : une tâche exemple, un critère, des passages « À compléter » et une question ouverte (`Q-REDACTION`). Le gabarit passe `apv spec validate --draft` ; la question ouverte fait refuser un gabarit non rédigé par la validation de lancement et par `apv run start`. `<id>` est en kebab-case (minuscules, chiffres, tirets simples, 80 caractères au plus) ; le titre est `--title`, sinon l'identifiant. Un fichier existant n'est jamais écrasé.

Sortie : `0` gabarit écrit, `1` fichier existant ou hors d'un dépôt Git, `2` appel incorrect.

## `apv run`

```
apv run start <spec> [--base <branche>] [--repo <chemin>] [--json]
apv run set <spec-id> <cible> <statut> [--branch b] [--worktree w] [--agent id] [--commit ref]
            [--base ref] [--findings n] [--confidence prouve|probable|suppose] [--note texte]
            [--force-unintegrated] [--no-commit-state] [--repo <chemin>] [--json]
apv run save <spec-id> [--repo <chemin>] [--json]
apv run next <spec-id> [--repo <chemin>] [--json]
apv run status [<spec-id>] [--repo <chemin>] [--json]
apv run pause <spec-id> --until <HH:MM | date ISO> [--note texte] [--repo <chemin>] [--json]
apv run resume <spec-id> [--note texte] [--repo <chemin>] [--json]
```

État de reprise d'une exécution de spec (`/apv:run`, spécification section 8) dans `.apv/state/run-<spec-id>.json`, versionné avec le projet. Chaque écriture relit l'état, le modifie et le réécrit de façon atomique (fichier temporaire puis renommage) sous le verrou à bail `run:<spec-id>` (`apv lock`, attente de 60 s, ou `APV_RUN_LOCK_WAIT` secondes) : deux agents ne perdent jamais la mise à jour de l'autre. L'outil n'écrit rien d'autre : il ne crée ni branche ni worktree et ne lance aucun agent.

**Checkout de l'état.** `start` crée l'état dans le checkout courant (ou `--repo`), celui de l'exécution. Les autres sous-commandes sur une exécution (`set`, `next`, `status <id>`, `pause`, `resume`) lisent et écrivent l'état du checkout courant quand il a `.apv/state/run-<id>.json`, comme avant ; sinon elles le cherchent dans tous les worktrees du dépôt (`git worktree list --porcelain`), le disent par une note sur la sortie d'erreur et travaillent dans le worktree trouvé. Plusieurs copies : le worktree sur la branche `apv/<id>`, sinon le checkout principal, sinon refus `RUN_AMBIGUOUS` (sortie `1`) qui liste les emplacements. Plusieurs exécutions tournent ainsi côte à côte, chacune dans son worktree. Un worktree qui a sa propre copie de l'état (état versionné venu avec un commit) lit cette copie : lance `apv run` depuis le checkout de l'exécution ou depuis un worktree sans copie.

**`start`** valide la spec comme `apv spec validate` en mode lancement (refus en `1` avec toutes les erreurs), puis crée l'état. `<spec>` est un identifiant (`.apv/specs/<id>.json`) ou un chemin (l'identifiant est alors le nom du fichier). La base est `--base`, sinon la branche courante ; elle est enregistrée avec son commit (`baseSha`). Refus si l'état existe déjà : `apv run next` le reprend.

Vagues : les couches topologiques des `dependsOn` ; une tâche de profondeur d (0 sans dépendance, sinon un de plus que sa dépendance la plus profonde) est dans la vague d, dans l'ordre de la spec. Fondations : dans chaque couche, une tâche dont au moins **deux** autres tâches dépendent directement est marquée `foundation: true` dans l'état (le format de spec n'a pas de marqueur : ses tâches refusent les propriétés inconnues). Les fondations d'une vague sont écrites par un seul agent, ses autres tâches partent en parallèle ; une tâche dont une seule autre dépend reste une dépendance ordinaire (dans l'essai de la phase 3, BIN était devenue une fondation parce que DOCS en dépendait). `start` et `status` affichent, pour chaque vague qui en a, « fondations (un seul agent) : … » puis « en parallèle : … ».

Version de l'état : `schemaVersion` 2 depuis ce marqueur. Un état de version 1 (marqueur `foundation` porté par la vague 0) reste lisible : il est converti à la lecture, chaque tâche d'une vague marquée devenant une fondation (c'était la règle de la version 1) et les autres non, puis réécrit en version 2 à sa prochaine écriture. Les vagues et la vague de chaque tâche ne sont jamais recalculées : l'état garde le plan du lancement.

Forme de l'état :

```
{ schemaVersion: 2, specId, specFile, specSha256, base, baseSha, branch: "apv/<spec-id>", createdAt, updatedAt,
  steps: { "data-model" | plan | integration | reviews | fixes | delivery: { status, commit, note, updatedAt, confidence? } },
  waves: [{ index, tasks: [id...] }],
  tasks: { <id>: { title, dependsOn, wave, foundation, status, branch, worktree, agentId, base, commit, note, updatedAt, confidence? } },
  reviews: { securite | fidelite | donnees | rgpd: { status, findings, commit, note, updatedAt } },
  events: [{ at, target, from, to, note?, commit?, agentId?, unintegrated?, until?, confidence? }],
  pause?: { since, until, note } }
```

Les dates de l'état sont des dates ISO en UTC (`Date#toISOString`) ; l'outil les affiche en heure locale (fuseau du système, ou `TZ`), avec leur décalage : `2026-09-24 20:22 UTC+2`. `pause` n'existe que pendant une pause (`apv run pause`) : un état jamais mis en pause garde la forme antérieure. De même, `confidence` n'existe que sur une tâche ou l'étape `fixes` dont le niveau a été noté (`--confidence`) : un état écrit avant ce champ reste lisible et garde sa forme ; un état qui en porte un n'est pas lisible par une version antérieure de l'outil (propriété inconnue).

Statuts : `pending`, `running`, `done`, `failed`, `skipped`.

**`set`** change le statut d'une cible : une étape (`data-model`, `plan`, `integration`, `reviews`, `fixes`, `delivery`), `task:<id>` ou `review:<domaine>` (`securite`, `fidelite`, `donnees`, `rgpd`), et ajoute un événement horodaté. Règles :
- passages permis : `pending` vers `running`, `done`, `skipped`, `failed` ; `running` vers `done`, `failed`, `pending`, `skipped` ; `failed` vers `pending`, `running`, `skipped` ; `skipped` vers `pending`, `running` ; `done` vers `running`, `pending`. Garder le même statut met seulement à jour les champs (nouveau commit wip, autre agent) ;
- rouvrir un travail `done`, ou remplacer le commit enregistré d'une cible `done`, exige `--note` (la raison est journalisée) ;
- sauter une revue (`review:<domaine> skipped`) exige `--note` (la raison de `apv review plan`) ; `review:securite skipped` est toujours refusé : la revue sécurité n'est jamais sautée ;
- une tâche ne passe `running` que si toutes ses dépendances sont `done` **et intégrées** : le commit enregistré de chacune est un ancêtre de la tête de la branche de la spec (`branch` de l'état, `git merge-base --is-ancestor`), ou de la base de l'exécution (`baseSha`) tant que cette branche n'existe pas. Sinon refus en `1` qui nomme les dépendances et leur commit. `--force-unintegrated` passe outre pour les seules dépendances faites mais pas intégrées, avec `--note` obligatoire (sinon `2`) ; l'événement garde la note et la liste des dépendances (`unintegrated`). Une tâche déjà `running` qui met à jour ses champs n'est pas revérifiée ;
- une tâche `done` exige `--commit` ; `--commit` et `--base` acceptent un sha complet ou abrégé, ou un nom de branche, que l'outil résout par git (`git rev-parse --verify <ref>^{commit}`) : le sha complet est enregistré et affiché, suivi de « résolu depuis « <ref> » » quand il diffère de ce qui a été donné (JSON : `resolved.commit` et `resolved.base`, `{ input, sha }`). Un commit introuvable est refusé en `1` (`RUN_COMMIT`), et le message aide à trouver le bon : le commit que désignent ses 7 premiers caractères quand ils en désignent un (un sha recopié d'un rapport peut être inventé au-delà : projet pilote, 24 septembre 2026), et la tête de la branche de la tâche (`--branch`, sinon celle de l'état) ;
- `--confidence prouve|probable|suppose` note le niveau de confiance du travail terminé : seulement avec `done`, pour une tâche ou l'étape `fixes` (sinon `2`). Il est gardé dans l'état (`confidence`) et dans l'événement, affiché par `status`, et retiré quand le travail quitte `done` ; `done` sans `--confidence` garde le niveau déjà noté ;
- `--branch`, `--worktree` (chemin rendu absolu), `--agent` et `--base` (commit de départ de la tâche, pour la reprise) ne valent que pour une tâche ; `--findings` (nombre de constats) que pour une revue ; `--commit` vaut pour toute cible (facultatif sur une étape : commit du plan, tête intégrée ; sur une revue : commit revu), et reste vérifié dans le dépôt.

**État commité à la livraison** (3.0.0-alpha.5, spécification section 18.3). `set <id> delivery running` commite ensuite, dans le checkout de l'état, les seuls fichiers `.apv/state/run-<id>.json` et `.apv/state/resume.md` (s'ils ont changé ou ne sont pas suivis ; jamais un autre fichier, même indexé : `git commit -- <ces fichiers>`), en un commit « chore(apv) : état de l'exécution <id> (livraison) » avec le trailer `Generated-by: apv run set`, sous l'identité Git du dépôt (jamais devinée ; absente : rien n'est commité et le message donne la commande `git config user.name … && git config user.email …`). Les hooks Git du projet ne sont pas lancés pour ce commit (`core.hooksPath=/dev/null`, comme tout commit de l'outil). Seulement quand ce checkout est sur la branche de l'exécution (`apv/<id>` ou `apv/<id>-…`) : sur une autre branche ou en tête détachée, rien n'est commité et une ligne `ATTENTION : état non commité : …` le dit (la transition, elle, est enregistrée, sortie `0`). La suite complète de livraison part ainsi d'un arbre propre (projet pilote, 27 septembre 2026 : une suite verte n'a rien prouvé à cause d'un fichier d'état non suivi). `--no-commit-state` l'évite (tête déjà prouvée, aucune suite à relancer). JSON : `stateCommit` (`sha`, `files`, `note`, `refused`). **`save`** fait le même commit (« … (sauvegarde) », trailer `Generated-by: apv run save`) à n'importe quel point de sauvegarde ; sortie `1` s'il est refusé (autre branche, tête détachée, erreur Git).

**`next`** dit ce qu'il faut faire maintenant, de façon déterministe : c'est la base de la reprise après une coupure (`/apv:resume`).
- Étape courante : la première étape non terminée (`done` ou `skipped`), avec `waves` entre `plan` et `integration` tant qu'une tâche reste à faire, et la vague courante (la plus basse qui a une tâche non terminée).
- Tâches prêtes : `pending` dont les dépendances sont `done` et intégrées (même règle que `set`), avec leur vague et leur marqueur de fondation. Règle unique : une tâche se lance dès qu'elle est prête, quelle que soit sa vague ; l'action les propose toutes, les fondations à un seul agent, les autres en parallèle.
- Tâches en attente d'intégration (`awaitingIntegration`) : dépendances toutes `done`, mais au moins une pas encore intégrée ; l'action nomme chaque dépendance à intégrer et les tâches qui l'attendent. `integration` donne la tête mesurée (`head`) et ce qu'elle est (`where` : la branche de la spec, ou la base tant qu'elle n'existe pas).
- Tâches `running` : **à relancer** si leur worktree n'existe plus, si leur branche est introuvable, si ni branche ni worktree ne sont enregistrés, ou si leur tête n'a aucun commit après leur base (`--base` donné au lancement de la tâche, sinon la base de l'exécution) ; sinon **à reprendre**, avec branche, worktree, agent, tête, nombre de commits après la base et dernier commit enregistré. Une tâche signalée à relancer ne l'est que si son agent ne tourne plus : un agent qui vient de démarrer n'a pas encore de commit.
- Tâches en échec, tâches bloquées (dépendances attendues), revues à lancer (`pending` ou `failed`, une fois les tâches finies et l'intégration faite) et revues en cours.
- `specChanged` : la spec a changé depuis `start` (empreinte différente) ; l'état garde le plan du lancement, l'action le signale.
- `suite` : rythme de la suite complète lu dans `run.fullSuite` de `.apv/config.json` (`mode`, `final` par défaut ou `each-integration`, [CONFIGURATION.md](CONFIGURATION.md#exécution--run)), niveau de vérification attendu à l'étape courante (`level` : `task`, contrôles de tâche et tests ciblés vérifiés par `apv gates verify --stage task --base <base ciblée>` ; `full`, suite complète et `apv gates verify` ; `null` à une étape sans intégration) et base ciblée (`targetBase`, `targetBaseWhere`) : le dernier commit prouvé par la suite complète, soit la base de l'exécution tant qu'aucune n'est passée, puis la tête de la dernière intégration (`integration done --commit`) avec `final`, la tête d'intégration avec `each-integration`. Les actions disent la commande attendue : intégration intermédiaire au niveau tâche, dernière intégration en suite complète avant les revues, corrections au niveau tâche avec le test de chaque correction, livraison sans double suite. Une configuration illisible laisse `final`, signalé en première action. `apv gates run --stage full` applique ce même niveau : refus au niveau `task`, sauf `--reason` (section `apv gates run`).
- `pause` : la pause de quota en cours (`since`, `until`, `note`), ou `null` ; signalée en première action tant qu'elle dure.
- `unproven` : le travail fait noté en dessous de `prouve` (`{ target, confidence }`, les tâches puis `fixes`) ; une action par entrée : `probable`, une vérification d'abord ; `suppose`, prouver ou remonter à l'opérateur avant toute fusion, action sur la production ou annonce « corrigé ». Le travail fait sans niveau noté n'y figure pas.

**`status`** résume toutes les exécutions (étape, tâches faites sur le total, en cours, en échec, pause de quota en cours, date) ou détaille une exécution (dates, pause en cours, étapes, vagues avec l'état de chaque tâche et son niveau de confiance noté, revues, les cinq derniers événements avec leur note), heures en heure locale.

**`pause`** note que l'exécution attend la remise à zéro du quota, jusqu'à `--until` : `HH:MM` en heure locale (sa prochaine occurrence, demain si elle est passée) ou une date ISO avec fuseau (`2026-09-24T18:30:00Z`, `2026-09-24T20:30+02:00`) ; `--note` dit pourquoi (fenêtre, pourcentage). Elle écrit `pause` dans l'état et un événement `pause` (`running` vers `pending`, avec `until`) ; une nouvelle pause la prolonge en gardant son début et sa note. Refus en `1` sur une exécution terminée ou une fin déjà passée. **`resume`** la termine (événement `pause`, `pending` vers `running`) ; refus en `1` sans pause. Toute transition `apv run set` termine aussi une pause restée ouverte, journalisée avant elle. Un état illisible est signalé, jamais réécrit ; un état dont l'identifiant de spec diffère du nom de son fichier est refusé. `start`, `set`, `next` et `status <id>` lisent l'état visé comme le résumé : fichier ordinaire seulement (une FIFO ou un dossier nommé comme l'état est refusé sans bloquer), 4 Mio au plus ; l'erreur nomme le fichier par son chemin dans le dépôt et ne cite rien de son contenu. Le résumé est celui de `apv status` : 50 fichiers au plus, les plus récents, et 16 Mio au total, les autres comptés (`unread` en JSON).

Sortie : `0` succès, `1` refus (spec invalide, état déjà présent ou absent, transition refusée, commit introuvable, état illisible, verrou non obtenu), `2` appel incorrect (cible ou statut inconnu, option sans effet).

## `apv stack`

```
apv stack plan <pr...> [--target <branche>] [--ready] [--allow-behind --reason <texte>] [--json]
APV_ALLOW_MERGE=1 apv stack merge <pr...> [--method merge|squash|rebase] [--target <branche>] [--ready] [--allow-behind --reason <texte>] [--keep-branches] [--wait-ci <minutes>] [--json]
apv stack batch <pr...> [--target <branche>] [--dir <dossier>] [--bisect] [--dast] [--keep] [--stacks <pile>,<pile>] [--wait-ci <minutes>] [--json]
APV_ALLOW_MERGE=1 apv stack batch <pr...> --merge [--ready] [--target <branche>] [--dir <dossier>] [--bisect] [--dast] [--keep] [--keep-branches] [--stacks <pile>,<pile>] [--wait-ci <minutes>] [--json]
```

Pile de PR, donnée par ses numéros dans l'ordre de fusion (de la base vers le sommet). Fin de l'incident 30 : re-ciblage vérifié, sortie jamais masquée, arrêt à la première anomalie.

**Règles avant fusion** (3.0.0-alpha.12) : `plan` vérifie, pour chaque PR sans autre anomalie, les règles de `apv rules check` à sa tête contre `origin/<cible>`, dans le dépôt où la commande est lancée (reçus, relectures, journal de l'opérateur ; hors d'un dépôt : refus) ; `merge` les revérifie juste avant chaque fusion et s'arrête au premier refus (« Règles avant la fusion de la PR #n : respectées », dérogations de l'opérateur citées) ; `batch --merge` les vérifie pour chaque PR avant de construire le lot (la preuve est celle du lot, et un contrôle réussi seulement après relance le rend non prouvé). Le crochet Bash refuse toute fusion par un autre client (`gh pr merge`, `mergePullRequest`, `.../pulls/<n>/merge`), toute poussée vers la branche par défaut et toute fusion dans un sous-agent. Chaque fusion écrit une trace signée pour `apv audit merges` ; le rapport de `merge` commence par la protection de branche et l'audit. `--offline` n'existe pas pour `stack` : la cible est toujours vérifiée contre le dépôt distant.

**`plan`** lit chaque PR par `gh pr view <n> --json number,state,isDraft,baseRefName,headRefName,headRefOid,isCrossRepository,mergeable,mergeStateStatus,statusCheckRollup,url` et vérifie la pile : chaque PR ouverte ; la base de la première est la branche cible (`--target`, sinon sa base actuelle), celle de la PR n+1 est la tête de la PR n ; `mergeable` à `MERGEABLE` et état de fusion `CLEAN` (ou `HAS_HOOKS`) ; contrôles au vert (`SUCCESS`, `NEUTRAL`, `SKIPPED`) ou absents ; **base à jour** : la tête de chaque PR contient la tête actuelle de sa base (la branche cible pour la première, la branche de la PR précédente pour les suivantes ; voir plus bas). Un brouillon est une anomalie, sauf avec `--ready`. Chaque PR doit avoir une adresse (`url`) de la forme `https://<hôte>/<propriétaire>/<dépôt>/pull/<n>`, avec son propre numéro : c'est elle qui donne le chemin de la comparaison et du re-ciblage. Une mergeabilité encore en calcul (`UNKNOWN`) est relue quelques fois avant d'être une anomalie. Toutes les anomalies sont listées ; rien n'est modifié. Les appels `gh` en échec sont affichés en entier.

**Code de la pile dans `plan`** (leçons du projet pilote, 2 octobre 2026 : une suite refusée d'entrée sur une pile de 6 PR qui modifiait 13 fichiers de tests navigateur pour un plafond de 10, et une PR de configuration refusée par `reuse` au milieu d'une pile). Depuis le dépôt où la commande tourne, `plan` récupère la cible (`git fetch origin +refs/heads/<cible>:refs/remotes/origin/<cible>`) et la tête de chaque PR (déjà présente, sinon `refs/pull/<n>/head`, sinon son sha), sans rien extraire ni modifier d'autre, puis :
- **tests modifiés par étage** : pour chaque contrôle de la configuration de la cible qui déclare `repeatChanged` (un « projet de tests »), le nombre de fichiers de test ajoutés ou modifiés depuis la cible jusqu'à la tête de chaque PR, compté comme `apv gates run` le compte (fichiers dont seuls les imports ou des chemins déplacés changent exclus). Un étage au-delà de `repeatChanged.maxFiles` est marqué « AU-DELÀ DU PLAFOND », avec la **coupe proposée** : des parties consécutives qui tiennent chacune sous chaque plafond (chaque partie comptée depuis la tête de la dernière PR de la partie précédente, qui sera alors sur la cible), à prouver et fusionner l'une après l'autre. Une PR seule au-delà d'un plafond est à découper (`alone`) ;
- **configuration surveillée par `reuse`** : une PR qui change, contre sa propre base (la cible pour la première, la PR précédente sinon), les sections `reuse`, `map` ou `design.dir`, un contrôle qui juge la réutilisation (`apv reuse check`, `apv map --check`) ou un contrôle obligatoire, est signalée dans une pile de plusieurs PR : « à fusionner seule d'abord » (`apv reuse check` la refuse mêlée à du code ; même règle, `reuseConfigChanges` de `src/reuse/check.ts`) ;
- **PR sans contrôle au-dessus de la première** : notée (`NOTE`, `notes` en JSON) quand la première PR, qui vise la cible, a des contrôles : la CI de la cible peut ne tourner que sur les PR vers elle (voir `merge`).

Ces signalements ne changent ni la cohérence de la pile ni le code de sortie. En JSON : `checks` (`read`, `error`, `gates` avec leur plafond, `stages` : `pr`, `head`, `counts` par contrôle, `over` ; `parts`, `alone`, `reuseConfig`). Hors d'un dépôt, ou récupération impossible : « non lus », avec la raison.

**`merge`** fusionne, uniquement sur ordre explicite de l'opérateur. Il exige `APV_ALLOW_MERGE=1` dans l'environnement ; sinon il sort en `2` avec le message du hook, sans aucun appel `gh`. Déroulé :
1. la pile est vérifiée comme par `plan` ; une anomalie arrête tout avant la première fusion ;
2. pour chaque PR, dans l'ordre : relecture ; si la précédente vient d'être fusionnée et que la PR vise encore sa tête, re-ciblage par l'API REST, `gh api -X PATCH repos/<propriétaire>/<dépôt>/pulls/<n> -f base=<cible>` (avec `--hostname <hôte>` hors de github.com), puis **relecture** quel que soit le code de sortie : un appel en échec arrête la pile, et la nouvelle base est constatée par la relecture, jamais déduite du code de sortie. Propriétaire, dépôt et hôte viennent de l'adresse que `gh pr view` a rendue pour cette PR : le même dépôt que la lecture, sans appel de plus. `gh pr edit --base` n'est plus employé : sa requête GraphQL lit aussi les projets classiques de la PR et échoue depuis leur abandon par GitHub (« Projects (classic) is being deprecated », constaté à la fusion des PR #70 et #71) ;
3. vérification juste avant la fusion (ouverte, bonne base, fusionnable, contrôles) ; avec `--ready`, `gh pr ready <n>` puis relecture ; enfin la base à jour, contre la cible telle qu'elle est à cet instant (après la fusion de la PR précédente et le re-ciblage) ;
4. `gh pr merge <n> --<méthode> --match-head-commit <tête relue>` : si la branche a bougé depuis la vérification, GitHub refuse ;
5. relecture : état `MERGED` et base attendue, sinon arrêt ;
5 bis. **CI qui ne tourne que sur les PR vers la cible** (projet pilote, 2 octobre 2026) : une PR re-ciblée qui n'a aucun contrôle, alors que la première PR de la pile, qui visait la cible, en avait, est relue quelques fois (`APV_STACK_POLL_ATTEMPTS`), puis la pile s'arrête avant sa fusion : un re-ciblage ne déclenche pas une CI ouverte sur l'événement `pull_request` vers la cible, et des contrôles absents ne valent pas le vert. La marche est donnée : dans la branche, `git fetch origin` puis `git merge origin/<cible>` (fusion de la base, aucun fichier changé attendu ; jamais de rebase ni de force-push ; `git commit --allow-empty` si Git répond « Already up to date »), `git push` sans force, puis relancer `merge` sur les PR restantes avec `--wait-ci <minutes>`. Une pile dont la première PR n'a pas de contrôle non plus (dépôt sans CI) garde le sens actuel des contrôles absents ;
6. une fois les fusions finies (ou la pile arrêtée), suppression des branches des PR fusionnées (ci-dessous).

**Base à jour.** Incident du projet pilote (25 septembre 2026) : deux PR préparées en parallèle sur `main`, l'une ajoutant un test qui importe un module, l'autre déplaçant ce module, chacune au vert seule, fusionnées l'une après l'autre : `main` est devenue rouge, car la seconde n'avait jamais été vérifiée contre la `main` qui contenait déjà la première. Les contrôles d'une PR ne portent sur le résultat de sa fusion que si sa tête contient sa base. L'outil le lit par l'API REST : `gh api repos/<propriétaire>/<dépôt>/compare/<tête>...<base> --jq …` (même hôte que la PR), qui donne le nombre de commits de la base absents de la tête (`ahead_by`), ces commits (combien sont listés, combien sont des fusions) et les fichiers qu'ils changent depuis la base commune. Verdict :
- `à jour` : aucun commit de la base n'y manque ;
- `à jour en contenu` : les commits manquants sont tous listés, tous des commits de fusion, et ne changent aucun fichier (cas de la PR suivante d'une pile fusionnée par `--method merge` : la fusion de la précédente n'apporte rien que la tête n'ait déjà) ; fusionner la base dans la tête ne changerait rien ;
- `EN RETARD` : la base apporte des changements que la tête n'a jamais vus (ou GitHub ne les liste pas) : la PR est refusée (anomalie de `plan`, arrêt de `merge`, code `1`) avec la marche à suivre : dans la branche, `git fetch origin` puis `git merge origin/<base>` (une fusion, jamais de rebase ni de force-push) ; repasser au moins les contrôles de tâche sur la nouvelle tête (`apv gates run --stage task --base origin/<base>`, puis `apv gates verify --commit <nouvelle tête> --stage task --base origin/<base>` à `0`) ; `git push` sans force ; attendre les contrôles GitHub au vert ; relancer `apv stack plan` puis `apv stack merge` ;
- comparaison impossible (appel en échec, réponse illisible) : refus, jamais pris pour « à jour ».

Avec `--method squash` ou `rebase`, la fusion d'une PR crée sur la cible des commits neufs qui portent ses changements : la PR suivante d'une pile est alors en retard et doit être mise à jour avant sa fusion (la commande s'arrête sur elle). Avec `--method merge` (défaut), une pile dont chaque PR est à jour de la précédente passe d'un trait, sauf si autre chose arrive sur la cible entre-temps. La preuve locale au commit exact de la tête (`apv gates verify --commit <tête> --stage task --base origin/<base>`) n'est pas exigée par l'outil (elle dépend des reçus de la machine et bloquerait une PR sans reçus, de documentation ou venue d'ailleurs) : c'est une étape du chef de projet après chaque mise à jour (compétence `/apv:stack`) ; un projet qui ne déclare aucun contrôle de tâche s'en remet aux contrôles GitHub.

**Dérogation, exceptionnelle.** `--allow-behind --reason "<texte>"` (1 à 500 caractères, les deux ensemble, sinon code `2`) laisse passer une PR en retard sur sa base, jamais une comparaison impossible. `plan` la montre sans rien écrire ; `merge` la journalise **avant** la fusion dans `.apv/state/stack.log` du dépôt courant (une ligne JSON : date, `event` `allow-behind`, pile, méthode, PR, tête, base, commits manquants, fichiers, raison ; `state/*.log` n'est jamais versionné) et dans le rapport (`DÉROGATION`, champ `derogations` en JSON) ; un journal impossible à écrire refuse la fusion. Elle vaut pour toutes les PR de la commande : on la réserve à une commande d'une seule PR, sur ordre de l'opérateur qui connaît le risque (la cible peut devenir rouge), jamais pour gagner du temps.

La sortie complète de chaque appel `gh` (commande, sortie standard, sortie d'erreur, code) est affichée au fil de l'eau, sur la sortie d'erreur avec `--json` (et dans le champ `calls`). À la première anomalie, rien d'autre n'est fusionné et le rapport donne les PR fusionnées, la PR d'arrêt, ses raisons et les PR restantes.

**Attente de la CI** (`--wait-ci <minutes>`, `merge` et `batch`, 1 à 360 minutes entières, sinon code `2` ; refusé sur `plan`). Sans elle, un contrôle en cours est une anomalie (`batch` refuse le lot, `merge` s'arrête). Avec elle, chaque lecture d'une PR dont des contrôles sont en cours la relit toutes les 30 secondes (`APV_STACK_CI_POLL_MS`) jusqu'à leur fin, au plus ce délai, en le disant sur la sortie d'erreur (« attente de la CI », puis « CI terminée (n/m au vert) » ou « délai de --wait-ci écoulé ») ; le résultat est ensuite jugé comme d'habitude : un contrôle en échec, ou encore en cours au bout du délai, reste une anomalie. L'attente ne remplace aucune vérification.

**Branches fusionnées** (`merge` et `batch --merge`). Projet pilote, 1er octobre 2026 : les fusions laissaient leurs branches, et le dépôt n'avait pas le réglage GitHub « supprimer la branche après fusion » : 54 branches fusionnées s'étaient accumulées. Après les fusions (dans une pile, chaque PR suivante a donc déjà été re-ciblée), la branche de tête de chaque PR dont la fusion a été constatée est examinée, dans l'ordre, par l'API REST (même hôte que la PR, arguments séparés, jamais de shell) :
1. `gh api repos/<propriétaire>/<dépôt> --jq '{default_branch, fork, delete_branch_on_merge}'` (une fois par dépôt) ;
2. `gh api -X GET repos/<propriétaire>/<dépôt>/pulls -f state=open -f base=<branche>`, puis `-f state=open -f head=<propriétaire>:<branche>` (supprimer la base ou la tête d'une PR ouverte la fermerait), puis `-f state=all -f base=<branche> -f per_page=1` (une branche qui a déjà servi de base à une PR est une branche de longue durée ; dans une pile, la PR suivante a été re-ciblée, sa base n'est donc plus cette branche) ;
3. `gh api repos/<propriétaire>/<dépôt>/branches/<branche> --jq '{sha: .commit.sha, protected}'`, juste avant la suppression : absente (404), elle est notée « absente (404) », sans erreur (avec « le dépôt supprime les branches fusionnées » quand `delete_branch_on_merge` est vrai : GitHub l'a fait) ;
4. `gh api -X DELETE repos/<propriétaire>/<dépôt>/git/refs/heads/<branche>`, puis relecture de la branche : seule son absence prouve la suppression, quel que soit le code de sortie.

La branche est **gardée**, avec la raison, et sans appel de suppression : `--keep-branches` (aucun appel du tout) ; PR venue d'un fork (`isCrossRepository` vrai : la branche est dans un autre dépôt) ou dont l'origine n'a pas été lue ; dépôt lui-même fork (`fork` vrai ou non lu : la branche peut être la tête d'une PR ouverte du dépôt parent, que ce dépôt ne peut pas lister) ; branche cible ou branche par défaut du dépôt ; branche de longue durée nommée par `stack.keepBranches` de `.apv/config.json` (motifs, par défaut `develop`, `development`, `release/*`, `releases/*`, `staging`, `hotfix/*` ; [CONFIGURATION.md](CONFIGURATION.md#pile-de-pr--stack) ; configuration illisible : toutes gardées) ; base ou tête d'une PR encore ouverte (par exemple la PR suivante d'une pile arrêtée avant son re-ciblage) ; branche qui a déjà servi de base à une PR ; branche protégée (ou protection inconnue) ; tête qui n'est plus le commit fusionné (celui passé à `--match-head-commit` ; des commits poussés après la fusion ne sont jamais supprimés). Une lecture en échec garde aussi la branche (avertissement). Un lot interrompu par un signal, ou arrêté sur une anomalie (même après une fusion : contenu de la cible différent du lot prouvé, journal non écrit), ne supprime rien : ses branches restent pour l'examen. La branche est relue juste avant la suppression, qui n'est pas conditionnelle côté GitHub : un commit poussé entre cette relecture et la suppression serait perdu de la branche (fenêtre d'un lancement de `gh`, de l'ordre d'une seconde ; la ligne du rapport donne la tête supprimée). Piste pour fermer cette fenêtre, non retenue ici : une suppression conditionnelle par `git push --force-with-lease=refs/heads/<branche>:<tête> origin :refs/heads/<branche>`.

Rapport : une ligne par branche, après le verdict : « Branche <b> (PR #n) : supprimée, tête <sha> (à recréer au besoin : git push origin <sha>:refs/heads/<b>) », « gardée, <raison> », « absente (404) », ou « AVERTISSEMENT : branche <b> (PR #n) non supprimée : <raison> ; la fusion reste acquise » (réglages du dépôt, branche ou PR illisibles, suppression refusée ou non constatée). Un échec de suppression ne change ni la fusion ni le code de sortie. Si le dépôt a `delete_branch_on_merge` à faux, une dernière ligne donne la commande qui le passe à vrai, `gh api -X PATCH repos/<propriétaire>/<dépôt> -F delete_branch_on_merge=true` (avec `--hostname` hors de github.com), jamais lancée par l'outil. En JSON, champ `cleanup` : `branches` (`pr`, `branch`, `head`, `status` `deleted|kept|absent|failed`, `reason`) et `repositories` (`host`, `repo`, `defaultBranch`, `fork`, `deleteBranchOnMerge`, `error`). Tous ces appels `gh` sont affichés comme les autres. `--keep-branches` est refusé par `plan` et par `batch` sans `--merge` (code `2`).

Le hook de garde bloque `apv stack merge` (et `node …/dist/cli.js stack merge`) sans `APV_ALLOW_MERGE=1` en préfixe, comme `gh pr merge`, et refuse sa sortie envoyée vers `/dev/null`. La variable `APV_GH` remplace l'exécutable `gh` (tests avec un faux `gh`) ; `APV_STACK_POLL_MS` et `APV_STACK_POLL_ATTEMPTS` règlent la relecture d'une mergeabilité en calcul (3 s, 20 fois par défaut).

**`batch` : fusion par lot** (3.0.0-alpha.5, spécification section 18.5). Pour des PR **indépendantes**, chacune vers la même cible (livrées en parallèle), prouvées au niveau tâche : une seule suite complète pour toutes, au lieu d'une mise à jour et d'une suite par PR. Déroulé :
1. lecture de chaque PR (`gh pr view`) : ouverte, vers la cible (`--target`, sinon la base de la première), fusionnable, contrôles au vert ou absents ; un brouillon est admis dans le lot (son statut ne compte qu'à la fusion). Une anomalie arrête tout avant la construction ;
2. `git fetch origin <cible>`, têtes des PR récupérées (`refs/pull/<n>/head`, sinon leur sha), chacune vérifiée égale à `headRefOid` ;
3. identité Git exigée (sinon refus clair avant toute construction) ; branche `apv/lot-<AAAAMMJJ-HHMMSS>` (suffixe `-2`, `-3`... si elle existe déjà) créée depuis `origin/<cible>` dans un worktree (`--dir`, défaut `<répertoire git commun>/apv/lots/apv-lot-<date>`), têtes fusionnées dans l'ordre donné (`git merge --no-ff`, message « lot : fusion de la PR #n », trailer `Generated-by: apv stack batch` ; jamais de rebase). Une PR en conflit avec les précédentes reste **hors du lot** (`excluded`, avec les fichiers en conflit), **sauf** quand les seuls fichiers en conflit sont des **fichiers générés** (point b1 de la revue du pipeline du 2026-10-03 validée par l'opérateur (« oui à tout »), document suivie-pilotage/REVUE-PIPELINE-2026-10-03.md du projet pilote ; `src/stack/regenerate.ts`) : la carte du code (`map.file`, `.apv/code-map.md` par défaut), le registre des décisions (`.apv/DECISIONS.json`, ou sa place V2) et sa version lisible (`.apv/DECISIONS.md`). Le registre est alors fusionné par **union de ses décisions** (lue dans les trois étages de l'index : une décision gardée des deux côtés est gardée, modifiée d'un seul côté prend ce côté, retirée d'un côté et intacte de l'autre est retirée, ajoutée d'un côté ou identiquement des deux est ajoutée, les ajouts triés par identifiant ; une décision modifiée des deux côtés, ou ajoutée différemment, reste un conflit ; le registre obtenu est validé, et deux décisions ajoutées de part et d'autre qui remplacent la même décision, ou un remplacement d'une décision absente du registre fusionné, sont des conflits aussi), son Markdown est rendu depuis le registre fusionné, la carte du code (et les parties générées de la carte de l'architecture) régénérée par `apv map` sur l'arbre fusionné avec la configuration de la copie, le tout dans le commit de fusion du lot ; une carte fusionnée sans conflit mais périmée pour le code fusionné est régénérée de même, dans le même commit. Les fichiers régénérés sont nommés par PR (`members[].regenerated`, « fichiers générés régénérés dans le lot ») et le contrôle `code-map` de la suite vérifie la carte régénérée. Rien n'est jamais résolu à la main. Une fusion dont la régénération échoue après coup (carte de l'architecture illisible, carte non écrite, commit de fusion inattendu) ne laisse rien dans le lot : retour au commit d'avant (`git reset --hard`, `git clean`), PR hors du lot avec la raison « fichiers générés non régénérés après sa fusion (le lot reste à l'arbre d'avant) », la suivante entre ;
4. **configuration de la cible** : une PR qui change `gates`, `environment.passEnv`, `batch`, `stacks` ou `suite` de `.apv/config.json` (sa tête contre sa base commune avec la cible) fait refuser le lot avant toute construction, avec la marche à suivre (la prouver seule) ; le lot est prouvé avec la configuration lue à `origin/<cible>` : `batch.setup` de la cible (installation des dépendances, facultative), puis UNE suite complète (`apv gates run --stage full --base <cible>` dans le worktree du lot, la cible servant de base à la répétition des tests modifiés `repeatChanged` et de référence à la portée de la preuve `skipWhenOnly` : un lot dont chaque PR ne touche que des fichiers sans effet selon la liste de la cible laisse ce contrôle « non requis », `verify` le recalcule à la tête du lot ; arbre propre, file des suites, verrous et fin de suite comme toujours ; reçus copiés dans le magasin partagé) et `apv gates verify --commit <tête du lot>` : le lot est prouvé si les deux sont à `0` ;
4 bis. **piles de test** (`--stacks 2` ou `--stacks 1,2`) : la suite du lot reçoit ces piles comme `apv gates run --stacks` (ci-dessous) : chaque contrôle de pile tourne sur une pile donnée, avec ses variables (`envFile`, `env`, `fileEnv` du verrou) et sous son verrou ; avec une seule pile, tous sur elle. Les piles sont vérifiées contre la configuration de la copie avant toute lecture (inconnue ou en double : code `2`), et la cible doit les déclarer aussi (sinon suite refusée, jamais bissectée). Sans `--stacks`, la suite ne reçoit que l'environnement de la commande. **Panne d'infrastructure** : une suite dont tous les contrôles en échec le sont par leur infrastructure (variable d'environnement absente, pile injoignable, copie non préparée ; voir `apv gates run`) n'est pas un échec de code : ni bissection ni PR fautive, arrêt avec la marche (« donner l'environnement des piles de test : --stacks <pile> (déclarées : …) », redémarrer la pile) ;
4 ter. `--dast` (décision D3 de la revue du pipeline du 2026-10-03 validée par l'opérateur (« oui à tout »), document suivie-pilotage/REVUE-PIPELINE-2026-10-03.md du projet pilote) : lot prouvé, le scan dynamique que la **cible** déclare (`review.dast`, le même que [`apv dast run`](#apv-dast-run)) tourne sur la tête du lot, dans son worktree, sous son verrou (`review.dast.resource`, 30 min d'attente au plus), rapports hors de la copie (`<temporaire>/apv-dast/<lot>-<sha>-<date>/`, `summary.json` écrit en dernier), **avant toute fusion** : un scan par lot sur le contenu fusionné, jamais après la fusion. Scan en échec, au délai, verrou non obtenu ou non déclaré à la cible : arrêt (« scan dynamique du lot en échec »), rien n'est fusionné ; `--dast` sans `review.dast` dans la copie : appel incorrect (`2`). Le résultat est dans `lots[].dast` (`ok`, `status`, `reportDir`, `summary`) et dans le rapport (« Scan dynamique du lot »). Le lot est **la voie normale de fusion** dès que deux PR indépendantes sont prêtes (décision D5 de la même revue ; compétence `/apv:stack`) : une suite par lot au lieu d'une suite par PR, plus de reprise « base en retard » ; les règles par PR (relectures, captures, maquette, contrôles) restent exigées pour chaque PR, seules `preuve` et `instable` sont jugées sur le lot ;
5. `--bisect`, lot non prouvé : il est coupé en deux, chaque moitié reconstruite et prouvée (branches `apv/lot-<date>-b<n>`), récursivement jusqu'à isoler la ou les PR fautives (`culprits`), qui sortent du lot ; le reste est prouvé une dernière fois (`apv/lot-<date>-final`). Lot entier en échec mais chaque moitié verte : échec d'interaction (`interaction: true`), rien n'est isolé ni fusionné ;
6. `--merge`, lot prouvé : exige `APV_ALLOW_MERGE=1` (sinon sortie `2` avec le message du crochet, sans appel `gh`). Pour chaque PR dans l'ordre du lot : relecture (ouverte, vers la cible, fusionnable, contrôles ; tête identique à celle fusionnée dans le lot, sinon arrêt ; `--ready` retire le brouillon), **arbre de la cible identique à celui du lot avant cette PR** (celui de la cible au départ pour la première, sinon celui du commit de fusion précédent du lot ; sinon la cible a changé hors du lot : arrêt), `gh pr merge <n> --merge --match-head-commit <tête>`, fusion constatée par relecture, puis **arbre de la cible identique à celui du commit de fusion de cette PR dans le lot** (sinon arrêt : le contenu fusionné n'est pas celui prouvé ; rien d'autre n'est fusionné). L'écart de la tête de chaque PR, qui ne contient pas les fusions précédentes du lot, est ainsi toléré : le contenu qui arrive sur la cible est exactement celui qui a été prouvé. **Branche mise à jour par le lot** : une PR dont la fusion dans le lot a régénéré des fichiers générés ne peut pas être fusionnée telle quelle par GitHub (il fusionnerait le texte, et verrait un conflit une fois les PR précédentes arrivées). Juste avant sa fusion, une fois la cible vérifiée au contenu du lot avant elle, l'outil fusionne la cible dans sa branche, dans un worktree détaché à sa tête, avec la même régénération ; le commit obtenu doit avoir **exactement l'arbre prouvé dans le lot** pour cette PR et pour parents sa tête et la cible (sinon arrêt, rien n'est poussé, avec le `git diff` à faire) ; il est poussé **sans force** sur sa branche (`git push origin <sha>:refs/heads/<branche>`, un descendant de la tête ; jamais pour une PR venue d'un fork, ni sur la cible du lot, la branche par défaut du dépôt (`origin/HEAD` en local, `default_branch` lu par `gh api repos/<propriétaire>/<dépôt>`), une branche de longue durée (`stack.keepBranches`, défauts de l'outil) ou une branche protégée sur GitHub (`gh api .../branches/<b>` ; protection illisible : refusée aussi), ni sur une branche qui est la base d'une PR ouverte (`gh api .../pulls?state=open&base=<b>` : une branche d'intégration ; liste illisible : refusée aussi) : arrêt avant toute poussée, avec la marche, « le lot ne pousse jamais sur une telle branche »), journalisé (`batch-refresh` : PR, branche, `from`, `to`, fichiers), relu par `gh pr view` jusqu'à ce que GitHub montre la tête poussée, puis fusionné à cette tête (`mergedHeads`, trace signée). La poussée relance les contrôles GitHub de la PR : avec une CI, `--wait-ci <minutes>` les attend, sans elle des contrôles en cours arrêtent le lot comme toute anomalie. Sans `--dast` alors que la cible déclare `review.dast`, le rapport le dit (« Scan dynamique non lancé (--dast absent) », `dastSkipped` en JSON) : le scan par PR reste dû avant la fusion. Les relectures restent celles de la tête d'origine : le commit de mise à jour n'ajoute que la fusion de la cible et les fichiers régénérés, et c'est ce contenu que la suite du lot a prouvé. `refreshed` en JSON, « Branche <b> (PR #n) mise à jour avant sa fusion » dans le rapport. À la fin, arbre de la cible identique à celui de la tête prouvée du lot (`finalTree`). Chaque fusion et chaque arrêt sont journalisés dans `.apv/state/stack.log` (`batch-merge` : PR, tête, cible après, commit du lot, `sameContent` ; `batch-refresh` ; `batch-stop`) ; un journal impossible à écrire arrête tout.
**Lot partiel** : dès qu'une PR demandée reste hors du lot prouvé (conflit, ou isolée par `--bisect`), le reste est prouvé (et fusionné avec `--merge`) mais la sortie est `1`, avec « Lot PARTIEL : #n (raison) » (`status: "partiel"`, `left` en JSON). **Interruption** : SIGINT, SIGTERM ou SIGHUP annulent la suite en cours ; le lot s'arrête à l'étape suivante, et toujours juste avant un `gh pr merge` : « Lot interrompu », PR déjà fusionnées nommées, sortie `128 + signal` (`status: "interrompu"`, `interrupted: true`). Statuts JSON : `prouvé`, `fusionné`, `partiel`, `arrêté`, `interrompu`.
Les worktrees des lots sont retirés à la fin (`--keep` les garde) ; les branches `apv/lot-*` restent, locales, jamais poussées. `--merge` sans lot prouvé ne fusionne rien. Seule la méthode `merge` de GitHub est employée (`--method` refusé) : c'est elle qui garde le contenu prouvé. La suite dure : lancer la commande en arrière-plan et l'attendre par `apv wait --pid`. Le crochet de garde bloque `apv stack batch … --merge` sans `APV_ALLOW_MERGE=1` en préfixe, comme `apv stack merge`.

Sortie : `0` pile cohérente (`plan`), entièrement fusionnée (`merge`), lot prouvé (`batch`) et fusionné (`batch --merge`), `1` anomalie (lot non prouvé compris), `2` appel incorrect ou `APV_ALLOW_MERGE` absent. En JSON, `batch` rend `target`, `base`, `prs` (`number`, `pr`, `anomalies`), `lots` (`name`, `dir`, `base`, `members` : `number`, `head`, `mergeCommit`, `tree`, `regenerated` ; `excluded`, `head`, `tree`, `proof` : `ok`, `runId`, `summary` ; `dast` ; `removed`), `culprits`, `interaction`, `proven`, `merged`, `refreshed` (`pr`, `branch`, `from`, `to`, `files`), `stopped`, `finalTree` (`target`, `lot`, `identical`), `mergedHeads`, `cleanup`, `calls`. En JSON : `plan` rend `target`, `ok`, `prs` (`number`, `pr`, `expectedBase`, `anomalies`, `freshness` : `base`, `head`, `state` `up_to_date|same_content|behind|unknown`, `missing`, `files`, `mergeBase`, `error`), `calls` ; `merge` rend aussi `method`, `merged`, `stopped` (`pr`, `reasons`), `freshness` (la base de chaque PR juste avant sa fusion), `derogations`, `mergedHeads` (`pr`, `branch`, `head` fusionnée, `crossRepository`, `url`) et `cleanup`.

## `apv ledger`

```
apv ledger validate [--repo <chemin>] [--json]
apv ledger plan --file <mise-a-jour.json> [--repo <chemin>]
apv ledger apply --file <mise-a-jour.json> --hash <empreinte> --note <texte>
                 [--reviewer <nom>] [--commit] [--repo <chemin>]
```

- `validate` lit le registre de l'arbre de travail et liste toutes ses erreurs (schéma, identifiants en double, citation manquante d'une décision de l'opérateur, décision ambiguë sans question ni deux interprétations, `scope` vide ou motif non pris en charge (`DECISION_SCOPE`)...). Un projet sans registre a un registre vide (sortie `0`).
- `plan` calcule le registre obtenu par une mise à jour `{ "decisions": [ ... ] }` : les nouvelles entrées s'ajoutent, une entrée qui en remplace une autre la nomme dans `supersedes` et l'ancienne quitte le registre actif (elle reste dans l'historique Git). Le plan affiche une empreinte. Une entrée peut porter le champ facultatif `scope` (`{ "paths": ["src/routes/accueil/**"], "specs": ["accueil"] }`) : `apv spec validate` n'exige alors sa couverture que des specs qu'il concerne ; donner un périmètre à une décision existante, c'est la remplacer (`supersedes`) par la même décision avec `scope`. Un registre sans `scope` garde son empreinte.
- `apply` écrit exactement le plan relu : l'empreinte doit correspondre, sinon rien n'est écrit. Il met à jour le JSON et sa version lisible (`DECISIONS.md` à côté), et commite ces deux fichiers seulement avec `--commit`. Le relecteur est `--reviewer`, sinon le `user.name` de Git.

Le commit de `--commit` est fait sous l'identité Git du dépôt (`user.name` et `user.email`, du dépôt ou de la configuration globale), comme auteur et comme commiteur : l'outil n'invente jamais d'auteur. Sans identité configurée, `apply --commit` refuse avant d'écrire quoi que ce soit (sortie `1`, erreur `GIT_IDENTITY`, avec la commande à lancer : `git config user.name "Votre Nom" && git config user.email "vous@exemple.fr"`, `--global` pour tous les dépôts). Sans `--commit`, aucune identité n'est demandée. L'origine du commit reste lisible dans son message, par le trailer final `Generated-by: apv ledger apply` (`git log --format='%(trailers:key=Generated-by)'`). Tout commit créé par l'outil suit cette règle.

Le registre reste à son emplacement : un projet V2 est mis à jour dans `.agent-pipeline/`, un projet V3 (ou sans registre) dans `.apv/`.

## `apv scope check`

```
apv scope check --spec <fichier> --task <id> [--base <ref>] [--repo <chemin>] [--json]
```

Compare les fichiers modifiés par les commits de la tâche aux `allowedPaths` de cette tâche dans la spec. La base est le point de divergence entre `<ref>` et `HEAD` (`main`, sinon `master`, par défaut) : le travail arrivé sur la branche principale depuis n'est pas imputé à la tâche. Les motifs suivent les règles de V2 (`*`, `**`, `?` ; crochets et parenthèses littéraux ; accolades et `!` refusés).

Tous les fichiers hors périmètre sont listés. Les modifications non commitées ne sont pas vérifiées : elles sont signalées, car la vérification stricte a lieu à la fin de la tâche, sur ses commits. La carte du code commitée par une tâche est hors périmètre, avec la marche à suivre (`codeMap` en JSON). La carte de l'architecture (`structure.architectureMap`) est acceptée quand seul son bloc écrit « Rôles » change (la tâche y décrit ce qu'elle crée), hors périmètre sinon (`architectureMap` en JSON : `none`, `roles-only` ou `other`).

Sortie : `0` dans le périmètre, `1` hors périmètre, `2` appel incorrect (spec illisible, tâche inconnue, base introuvable).

## `apv gates run`

```
apv gates run [--stage task|full] [--only a,b] [--config <fichier>] [--base <ref>]
              [--concurrency N] [--keep-going] [--skip-proven] [--run <spec-id>] [--since <commit prouvé>]
              [--reason <texte>] [--allow-dirty] [--stacks <pile>,<pile>] [--repo <chemin>] [--json]
```

Exécute les contrôles déclarés dans `gates` depuis la racine du dépôt, avec l'ordonnanceur de V2 :
- **dépendances** (`dependsOn`) : un contrôle attend les siens ; si l'un échoue, ses dépendants sont « bloqués » ;
- **ressources** (`resources`) : deux contrôles qui partagent une ressource nommée ne tournent jamais en même temps ;
- **lecture seule** (`readOnly`) : seuls les contrôles déclarés en lecture seule tournent en parallèle, un contrôle qui écrit a l'espace de travail pour lui seul ;
- **environnement** : chaque commande reçoit seulement `environment.passEnv` (par défaut `PATH`, `SystemRoot`, `WINDIR`, `TMPDIR`, `TEMP`, `TMP`, `LANG`) et le `passEnv` du contrôle ;
- **délais** : `timeoutMs` par contrôle (120 s par défaut) ; au-delà, le groupe de processus est arrêté ;
- **secrets** : les valeurs des variables dont le nom contient TOKEN, KEY, PASSWORD, SECRET ou CREDENTIAL sont masquées dans les diagnostics.

Paramètres des commandes (argument entier uniquement, jamais d'interprétation par un shell) : `{{workspace}}` (racine du dépôt), `{{candidateSha}}` (HEAD), `{{baseSha}}` (commit de `--base`, obligatoire si un contrôle l'utilise).

**Stage** : chaque contrôle peut déclarer `"stage": "task"` (contrôle rapide, lancé après chaque tâche) ou `"stage": "full"` (réservé à la suite complète, par exemple les tests navigateur). Champ absent : `task`, si bien qu'une configuration sans stage garde son sens (tout tourne partout). Un contrôle `task` ne peut pas dépendre d'un contrôle `full` (configuration refusée). `--stage task` exécute seulement les contrôles de stage `task` ; les contrôles `full` sélectionnés sont listés dans le tableau comme « réservé à la suite complète », dans `reserved` en JSON et dans `summary.json`, sans reçu : ils ne sont jamais comptés comme réussis. `--stage full` (défaut, comportement antérieur) exécute tout. Voir [RUN.md](RUN.md#contrôles--par-tâche-et-suite-complète) pour l'usage pendant un run.

**Contrôle ciblé** (`affected`) : un contrôle de stage `full` peut déclarer, en plus de `command`, une commande `affected` qui lance seulement les tests concernés par les changements depuis la base, par exemple `["apv", "lock", "run", "e2e", "--", "npx", "playwright", "test", "--only-changed={{baseSha}}", "--pass-with-no-tests"]` (exemple complet dans [CONFIGURATION.md](CONFIGURATION.md#graphe-de-contrôles)). `--stage task` exécute alors cette commande à la place du contrôle complet, avec le même identifiant, les mêmes dépendances, ressources, variables et délai. Le contrôle est signalé « ciblé » : `e2e (ciblé)` dans le tableau et les diagnostics, une phrase dans le verdict, `targeted: true` dans son reçu et sa ligne JSON, sa liste dans `targeted` en JSON et dans `summary.json`. Un reçu ciblé ne prouve jamais le contrôle complet : `apv gates verify` au niveau complet l'ignore ; au niveau tâche (`--stage task --base <ref>`), il prouve le contrôle quand la base de son exécution couvre `<ref>`. `--stage full` exécute toujours la commande complète. Si `affected` utilise `{{baseSha}}`, `--base` est obligatoire.

**Preuve incrémentale d'un tour de corrections** (`--since <commit prouvé>`, 3.0.0-alpha.15) : `apv gates run --stage task --since <commit>` (à la place de `--base`) lance les contrôles de tâche, les commandes ciblées (`affected`, `{{baseSha}}` = le commit prouvé) et la répétition des tests modifiés depuis ce commit (`repeatChanged`). Refus `GATE_SINCE`, sortie `1`, rien n'est lancé : arbre avec des modifications non commitées (le diff classé est celui des commits), HEAD égal au commit ou qui n'en descend pas, suite complète non prouvée à ce commit (`apv gates verify --commit <commit>` avec cette configuration des contrôles) ou prouvée avec un contrôle réussi après relance, diff de **risque élevé** depuis ce commit (classement de `apv review plan`, configuration de revue lue au commit prouvé ; la raison et les fichiers sont listés). Appel incorrect (sortie `2`) : `--since` sans `--stage task`, avec `--base`, ou avec `gates verify`. Refus aussi, avant toute exécution de contrôle, quand HEAD change entre le classement et les contrôles. Chaque refus dit quoi faire dans son cas (commiter, `apv gates verify --commit HEAD`, stabiliser, lancer la suite complète). La sortie et `summary.json` portent `since` (commit prouvé, tête classée `head`, niveau, raison). **Jamais une preuve de la suite complète** : `apv gates verify --commit <tête>` et `apv rules check` exigent toujours la suite complète au commit exact fusionné ; flux recommandé : corrections, `--since`, relecture ciblée du nouveau commit, puis une seule suite complète sur le commit final.

**Suite déjà prouvée** : avant d'exécuter la suite complète entière (`--stage full`, sans `--only`), l'outil regarde si elle est déjà prouvée sur ce commit exact, arbre propre (la vérification de `apv gates verify --commit HEAD` à `0`). Si oui, il le signale en tête de sortie (`alreadyProven: true` en JSON) avant de la relancer ; avec `--skip-proven`, il ne relance rien et sort en `0` (`skipped: true` en JSON, avec les reçus qui font la preuve). Arbre modifié, reçu manquant, échec plus récent ou autre configuration : pas de preuve, la suite tourne. `--skip-proven` avec `--stage task` ou `--only` : appel incorrect.

**Rythme d'une exécution** (`/apv:run`, [CONFIGURATION.md](CONFIGURATION.md#exécution--run)) : quand la commande exécuterait au moins un contrôle de stage `full` en entier (`--stage full` ou sans `--stage`), elle cherche l'exécution dont elle fait partie : `--run <spec-id>` (l'état doit exister dans un worktree du dépôt, sinon `RUN_MISSING`, sortie `1`), sinon la branche courante du dépôt, `apv/<id>` ou `apv/<id>-<suffixe>` (branches de tâche, d'intégration, de correction ; l'identifiant le plus long d'abord), quand un worktree du dépôt a `.apv/state/run-<id>.json`. L'état est cherché dans tous les worktrees (`git worktree list --porcelain`), pas seulement dans le checkout principal : chaque exécution tourne dans son propre checkout. Plusieurs copies : celle du worktree sur `apv/<id>` (le checkout de l'exécution), sinon celle du checkout principal, sinon refus `RUN_AMBIGUOUS` (sortie `1`) qui liste les emplacements. Elle calcule le niveau attendu comme `apv run next` (`suite.level`, avec `run.fullSuite` du checkout qui a l'état) ; le JSON donne ce checkout (`rhythm.checkout`) :
- niveau `task` (intégration intermédiaire ou passe de corrections avec `"final"`) : refus, sortie `1`, `Erreur [GATE_RHYTHM]`, avec l'étape, le niveau attendu, la commande à lancer à la place (`apv gates run --stage task --base <base ciblée>`, puis `apv gates verify --commit <tête> --stage task --base <base ciblée>` à `0`) ; rien n'est exécuté ni écrit ;
- `--reason "<texte>"` (1 à 500 caractères, jamais avec `--stage task`) : dérogation motivée, la suite tourne ; un événement `gates:full` (raison et commit) est journalisé dans l'état de l'exécution par l'API d'état, sous le verrou `run:<id>`, et la raison est écrite dans chaque reçu et dans `summary.json` (`override` : `run`, `reason`) ; ces reçus prouvent la suite complète comme les autres ;
- niveau `full` (dernière intégration, livraison, `"each-integration"`) ou aucun niveau à cette étape : rien ne change ;
- hors exécution (autre branche, tête détachée, aucun état ; un état trouvé par la branche mais illisible est signalé par une note) : rien ne change.
Un `--reason` sans effet est signalé par une note. `--stage task` et une sélection `--only` sans contrôle `full` ne sont jamais concernés.

**Suite complète : arbre propre, file, ports** (3.0.0-alpha.4, spécification section 17). Quand la commande exécute au moins un contrôle de stage `full` en entier (même prédicat que le rythme ; `--stage task` et `--only` sans contrôle `full` ne sont jamais concernés), dans cet ordre, avant le premier contrôle :
1. **Arbre propre** : des fichiers suivis modifiés ou des fichiers non suivis non ignorés (`git status --porcelain --untracked-files=all`) font refuser la suite, sortie `1`, `GATE_DIRTY`, avec la liste des fichiers (50 au plus) ; le refus du rythme (`GATE_RHYTHM`), plus utile, passe avant, et une dérogation `--reason` n'est journalisée qu'après ce contrôle. `--allow-dirty` la lance quand même : ses reçus portent `dirty: true` et ne prouvent rien (`apv gates verify` les refuse, comme avant), la sortie le rappelle.
2. **File des suites complètes** (section `suite.queue`, active par défaut, [CONFIGURATION.md](CONFIGURATION.md#suite-complète--suite)) : un verrou à bail du mécanisme de `apv lock` ([LOCKS.md](LOCKS.md)), fichier `<répertoire git commun>/apv/locks/full-suite.lock` par défaut (commun à tous les worktrees du dépôt ; un chemin absolu le partage entre dépôts). Une suite attend son tour en FIFO, le détenteur et la position s'affichent sur la sortie d'erreur ; au-delà de `waitMs` (2 h par défaut) : refus `SUITE_QUEUE`, sortie `1`, rien n'est exécuté. Avec `maxLoad`, elle attend ensuite, verrou tenu, que la charge moyenne sur 1 minute passe sous ce seuil, au plus `loadWaitMs` (30 min), puis démarre quand même en le notant. Le verrou est libéré à la fin, quelle que soit l'issue. Si HEAD a bougé pendant l'attente, refus ; si l'arbre a changé, refus sauf `--allow-dirty`. **Places** (`suite.queue.slots`, 3.0.0-alpha.20) : la suite tient aussi la place de chaque pile qu'elle utilise (`full-suite-stack-<pile>`), et selon `slots` la file entière (`1`, défaut), rien de plus (`"per-stack"` : une suite par pile en même temps) ou une des N places numérotées (`full-suite-slot-<k>`) ; deux suites ne partagent jamais une pile. Avant toute autre place, la suite tient celle de sa copie (`full-suite-copy-<empreinte du chemin canonique>`) : deux suites ne tournent jamais dans la même copie, quel que soit `slots` (elles partageraient `node_modules` et les dossiers de build, et chacune arrêterait les serveurs de l'autre comme orphelins de la copie). Une suite dont un contrôle lance `apv web audit` tient **toutes** les places (file entière, chaque place numérotée, chaque pile) : dans une suite (`APV_SUITE_RUN`), l'audit ne prend aucune place lui-même, c'est la suite qui les prend pour lui, et aucune autre suite ne tourne pendant la mesure. Les places tenues sont dans la sortie et dans `summary.json` (`queue.places`, `queue.slots`).
3. **Ports** (`suite.ports`) : les processus qui y écoutent et dont le répertoire courant est dans la copie où tourne la suite (un worktree lié) sont arrêtés comme par `apv procs stop` (SIGTERM, SIGKILL après 5 s, pid réutilisé épargné) ; ceux d'une autre copie, du checkout principal, hors du dépôt, les outils protégés et la session ne sont jamais arrêtés (`other-copy`, `main-checkout`, `outside`, `tool`, `protected`, `unknown-cwd`) et **font refuser la suite** (3.0.0-alpha.12), sauf, depuis la revue du pipeline du 3 octobre 2026 (point b8), ceux d'une **autre copie du dépôt** (`other-copy` : une relecture qui capture des écrans, un scan dynamique, une autre suite, tous finis en quelques minutes) quand aucun autre motif ne refuse : la suite **attend leur libération**, relue toutes les 5 s (`APV_PORTS_POLL_MS` pour les tests), jusqu'au plus long `lock.waitMs` des contrôles qui verrouillent (sinon 30 min), chaque attente dite au départ, toutes les minutes et à la fin (« libérés après … : la suite démarre », ou refus `GATE_BUSY` « après … d'attente des ports », ou refus dès qu'un processus hors d'une copie prend un port) et consignée dans `summary.json` (`ports.wait` : `ms`, `holders`, `outcome` `freed|timeout|foreign`) ; après une attente, HEAD et l'arbre sont revérifiés comme après la file. Un port tenu par le checkout principal, un processus hors du dépôt ou un outil n'est jamais attendu, et un verrou de pile tenu refuse d'emblée, comme le verrou tenu d'une pile que la suite utilise (`stacks`, `flock` non libre ; depuis 3.0.0-alpha.20, seules les piles de `--stacks`, sinon celles que verrouillent ses contrôles, sont vérifiées, avec leurs ports : `--stacks 2` ne refuse plus pour un verrou ou un port de la pile 1 ; un contrôle dont le verrou n'est celui d'aucune pile déclarée fait vérifier toutes les piles, comme avant ; une suite dont aucun contrôle ne verrouille une pile déclarée n'en vérifie aucune, et le dit au journal ; la sortie nomme les piles réellement vérifiées, « toutes » dans le cas d'un verrou hors pile ; `stacksUsed`, `stacksChecked` et `stacksUnmapped` en JSON), sauf s'il est tenu par un processus parent de la suite (`flock <verrou> apv gates run` : les contrôles qui le demandent tournent alors sous lui, un à la fois par un verrou compagnon (un par fichier de verrou réel, dans `<APV_LOCK_DIR, sinon ${XDG_STATE_HOME:-~/.local/state}/apv/locks>/under/`, avec ses replis décrits dans [CONFIGURATION.md](CONFIGURATION.md)), chacun dans son `lock.waitMs` et avec son délai propre) : refus `GATE_BUSY`, sortie `1`, rien n'est exécuté, avec chaque port ou pile en cause et quoi faire (attendre, ou `apv procs stop --port <p>` pour un orphelin). Jamais deux suites complètes sur une même pile ni dans une même copie (une seule à la fois sur la machine avec `slots` à `1`, défaut ; une par pile avec `"per-stack"` ; N avec un nombre), et aucun e2e d'agent sur une pile qu'une preuve utilise ([REGLES.md](REGLES.md)).
4. **Préparation de la copie** (3.0.0-alpha.20) : une copie avec `package-lock.json` sans `node_modules` (un worktree neuf) est préparée par `batch.setup` ([CONFIGURATION.md](CONFIGURATION.md#lot-et-copies--batch)), sous la place de la copie dans la file et après tout refus (`SUITE_QUEUE`, `GATE_BUSY`) : une suite refusée n'a rien lancé. Un échec, ou des fichiers non ignorés écrits par la préparation, refusent la suite (`GATE_SETUP`, rien n'est exécuté) ; la sortie de la préparation est masquée comme celle des contrôles (secrets de l'environnement). Jamais dans le checkout principal : refus `GATE_SETUP`, installer les dépendances soi-même ou lancer la suite depuis un worktree lié. Sans `batch.setup`, la suite le signale (« copie de la suite non préparée ») et continue. `summary.json` porte `setup` (`status` `done|missing`, `command`, `durationMs`, `reason`).
Les délais (`timeoutMs`) des contrôles ne commencent qu'après ces étapes. **Délai presque atteint** (3.0.0-alpha.12) : un contrôle dont la plus longue passe a pris au moins 85 % de son `timeoutMs` (toutes étapes) le dit sur la sortie d'erreur, sous le tableau (« délai presque atteint ») et dans son reçu (`nearTimeout` : `timeoutMs`, `percent`) ; `apv gates verify` le rappelle (`nearTimeout` en JSON). Augmenter le délai avant qu'il ne casse une preuve. La sortie résume la file (attente, détenteur, charge au démarrage) et les ports ; `summary.json` porte `suite: true`, `queue` (`lockFile`, `waitedMs`, `heldBy`, `load` : `max`, `atStart`, `waitedMs`, `exceeded`), `ports` (`stopped`, `left`, `unsupported`) et `flaky`.

**Fin de suite** (3.0.0-alpha.5, spécification section 18.4). Chaque commande d'un contrôle d'une suite complète reçoit la variable `APV_SUITE_RUN=<exécution>` (hors de l'empreinte d'environnement du reçu), que ses descendants héritent. À la fin de la suite, qu'elle réussisse, échoue ou soit interrompue, les processus encore vivants qui portent cette marque (`/proc/<pid>/environ` : un serveur sorti du groupe de processus de son contrôle, qu'une fin normale ne tue pas) sont arrêtés comme par `apv procs stop` (SIGTERM, SIGKILL après 5 s, pid réutilisé épargné ; jamais la session ni un outil protégé), puis les orphelins de cette copie sur `suite.ports` (même règle qu'au démarrage). **Interruption** : SIGINT, SIGTERM ou SIGHUP reçus par `apv gates run` annoncent l'arrêt sur la sortie d'erreur, annulent les contrôles en cours (reçus `cancelled`, groupes de processus arrêtés), font cette fin de suite, écrivent les reçus et `summary.json`, libèrent la file, puis sortent en `128 + signal` (`interrupted` en JSON). C'est la seule façon d'arrêter une suite : jamais `kill` d'un parent ni `pkill -f` (le crochet Bash les refuse). Ce qui a été arrêté est dans la sortie et dans `summary.json` (`cleanup` : `stopped`, `left`, `ports`, `unsupported`).

**Préparation de la copie** (3.0.0-alpha.20) : une suite complète dont la copie a un `package-lock.json` sans `node_modules` lance d'abord `batch.setup` à sa racine (comme pour ses copies sur d'autres piles et comme `apv dast run`), avant la file ; un échec ou des fichiers non ignorés écrits par la préparation : refus `GATE_SETUP`, sortie `1`, rien n'est exécuté ; sans `batch.setup` : « ATTENTION : copie de la suite non préparée », la suite continue (`setup` en JSON et dans `summary.json` : `status` `done|missing`, `command`, `durationMs`, `reason`).

**Pile relue après une interruption** (3.0.0-alpha.20) : un contrôle dont la commande a démarré sous le verrou d'une pile et qui est arrêté (annulation par SIGINT, SIGTERM, SIGHUP, ou délai dépassé) a pu couper une remise à zéro de la pile. Une fois les processus de la suite arrêtés, l'outil relit la pile : ses conteneurs (`dockerProject` : `docker ps -a`, label `com.docker.compose.project` ou `com.supabase.cli.project`, ou nom finissant par `_<dockerProject>`), comparés à ceux relevés au départ de la suite ; un conteneur disparu (la base supprimée au milieu d'un `db:reset`) ou hors marche est dit, avec la marche (`apv stacks status`, puis au besoin `apv stacks start <pile>`). Rien n'est redémarré ni modifié. Sans `dockerProject`, l'état est « non vérifié ». `interruptedStacks` en JSON et dans `summary.json` : `stack`, `gates`, `health` (`state` `running|degraded|absent|unknown`, `detail`, `containers`, `missing`).

**Répartition sur les piles** (`--stacks 1,2`, 3.0.0-alpha.5, spécification section 18.6 ; une seule pile admise, `--stacks 2` : tous les contrôles de pile tournent sur elle, dans la copie de la suite, avec ses variables et sous son verrou) : suite complète seulement, piles différentes déclarées (section `stacks`, [CONFIGURATION.md](CONFIGURATION.md#piles-de-test--stacks)). Les contrôles « de pile » (ceux dont le `lock`, tel que configuré, est le verrou d'une pile déclarée : même fichier, ou même bail) sont distribués sur les piles données, tour à tour dans l'ordre de la configuration ; un contrôle qui a des dépendances, ou dont d'autres dépendent, reste sur la première pile. Chaque contrôle de pile reçoit les variables de sa pile (`envFile`, puis `env`, puis la variable `fileEnv` de son verrou pointée sur le verrou de la pile ; seulement les noms de son `passEnv` et de `environment.passEnv`) et tourne sous le verrou de sa pile. Sur la première pile, dans la copie de la suite ; sur une autre, dans une copie détachée du même commit, `<répertoire git commun>/apv/copies/<exécution>-<pile>`, préparée par `batch.setup` (arbre propre exigé ensuite) et retirée à la fin. Chaque copie a son propre ordonnanceur (ressources et exclusion d'écriture propres à son espace de travail) : les copies tournent en même temps ; sous `failFast`, un échec les arrête toutes. Une copie impossible à préparer : ses contrôles ne sont pas lancés (reçu `spawn_error` avec la raison). Une variable de `env` d'une pile que le contrôle ne reçoit pas (absente de son `passEnv` et de `environment.passEnv`) fait refuser la répartition (`GATE_STACKS`, sortie `1`, rien n'est lancé) ; les clés de `envFile` non reçues sont listées (note, `notPassed`). Tous les reçus vont dans l'exécution de la suite, chacun avec `stack`, et prouvent la suite comme les autres. La sortie donne la répartition (`spread` en JSON et dans `summary.json` : `gate`, `stack`, `workspace`, `notPassed`, `error`).

**Panne d'infrastructure** (projet pilote, nuit du 2 octobre 2026 : `Variable SUPABASE_TEST_URL absente` d'un lot lancé sans les piles, conteneur Docker resté « Created » sous charge, comptés comme des tests en échec). Un contrôle en échec, en délai dépassé ou non lancé dont la sortie nomme une variable de son `passEnv` absente de son environnement, ou dit une variable d'environnement absente dans les mots usuels des outils (« Variable X absente », « environment variable X is not set », « Missing environment variable: X »...), une pile ou un service injoignable (`ECONNREFUSED`, connexion refusée, `supabase start is not running`, « failed to set up container networking », démon Docker injoignable, conteneur arrêté), une copie de pile non préparée ou un exécutable introuvable, est signalé sous le tableau : « Panne d'infrastructure probable », une ligne par contrôle, puis la marche (donner l'environnement des piles par `--stacks`, exporter les variables, redémarrer la pile). C'est une lecture de la sortie, jamais une preuve : le reçu garde son statut, le contrôle reste en échec. En JSON et dans `summary.json` : `infrastructure` (`causes` : `gateId`, `kind` `environment`, `unreachable` ou `setup`, `detail` ; `all` : tous les échecs le sont ; un contrôle annulé par le premier échec ou bloqué par une dépendance n'est pas un échec propre). `apv stack batch` s'en sert pour ne jamais bissecter ni accuser une PR pour une panne d'infrastructure.

**Pile arrêtée par `apv stacks idle-stop`** : si un contrôle verrouille une pile arrêtée par `idle-stop` et que rien ne montre qu'elle ait redémarré depuis (ni `apv stacks start`, ni contrôle réussi sous son verrou), la suite l'annonce avant ses contrôles (`ATTENTION : …, apv stacks start <id>`), sous son tableau et dans `stoppedStacks` (JSON, `summary.json`). Pile inconnue : `STACK_UNKNOWN`, sortie `1` ; une seule pile, deux fois la même ou `--stage task` : `2`.

**Verrou d'un contrôle** (`lock`, [CONFIGURATION.md](CONFIGURATION.md#graphe-de-contrôles)) : le contrôle attend sa ressource partagée (la pile de test) avant que son délai commence ; un bail de `apv lock` (`{ "resource": "e2e" }`, tenu pendant les deux passes d'une relance, `APV_LOCK_HELD` transmise à la commande ; déjà tenu par l'appelant, par `apv lock run e2e -- apv gates run`, il n'est pas repris) ou un `flock` du noyau sur un fichier (`{ "file": "...", "fileEnv": "VAR" }`, pris par `flock(1)` dont la commande est un descendant, repris pour la relance). L'attente est notée dans le reçu (`lockWaitMs`, hors `durationMs`) et, au-delà d'une seconde, sous le tableau. Verrou non obtenu dans `waitMs` : reçu `timed_out` avec la raison, commande jamais lancée.

**Relance des échecs** (`retryFailed`) : un contrôle qui échoue de lui-même (statut `failed` ; jamais un délai dépassé, une annulation, une commande introuvable ni un verrou non obtenu) et qui déclare `retryFailed.command` (par exemple `["npm", "run", "test:e2e", "--", "--last-failed"]` pour Playwright) est relancé UNE fois par cette commande, après vérification que HEAD et l'état de l'arbre sont ceux du départ (sinon : « Relance refusée », échec). Réussite : statut `passed_after_retry`, « réussi après relance » dans le tableau, compté comme réussi (dépendants lancés, sortie `0`), et listé sous le tableau « Instables » avec les tests concernés (lignes de la première passe qui répondent à `retryFailed.testPattern`) ; son reçu garde la première passe (`retry.first` : statut, code, durée, empreintes des sorties, extrait), la commande, un extrait de la seconde (`retry.output`) et les tests (`retry.tests`). Échec de la relance : échec normal (statut et code de la relance, diagnostic « Relance (retryFailed) en échec aussi », les deux passes dans `retry`). Jamais plus d'une relance. La garde ne baisse pas : chaque test a réussi sur le code exact du commit, arbre inchangé ; un test qui échoue deux fois fait échouer le contrôle ; l'instabilité reste visible et se traite comme un constat.

**Répétition des tests modifiés** (`repeatChanged`, 3.0.0-alpha.6, spécification section 19, configuration dans [CONFIGURATION.md](CONFIGURATION.md#graphe-de-contrôles)) : une exécution qui lancerait un contrôle qui déclare `repeatChanged` (en entier ou ciblé) exige `--base <ref>` : sans elle, appel incorrect, sortie `2`, avant toute recherche de preuve (`--skip-proven` compris) et toute attente ; une base dont HEAD ne descend pas strictement (égale à HEAD, ou en aval) : refus `GATE_BASE`, sortie `1`. Avant toute attente, l'outil liste pour chaque tel contrôle les fichiers de test ajoutés ou modifiés depuis la base commune de `<ref>` et de HEAD et, pour un contrôle lancé en entier à l'étape `full`, aussi depuis la base commune de la **référence** (`repeatChanged.reference`, obligatoire ; introuvable : appel incorrect, sortie `2`, avant toute attente, message qui dit de la récupérer ou de la corriger) et de HEAD, si bien qu'une `--base` trop proche ne réduit pas la liste (arbre de travail et fichiers non suivis non ignorés compris, fichiers supprimés jamais ; ceux qui répondent à `repeatChanged.paths`). **Tests dont seuls les imports changent** : un fichier de test dont les seules différences avec chaque base sont les chemins de ses imports (un rangement ou un renommage de modules les réécrit) n'est pas répété ni compté dans `maxFiles` : `import` statique et `import type`, `export … from`, `import '…'`, `vi.mock('…')` (`jest.mock`, `importActual`…), `import('…')` à chaîne littérale, import réécrit par Prettier sur plusieurs lignes, fichier renommé ou déplacé par Git (suivi du renommage) sans autre changement. Seul le chemin cité peut changer : un nom importé, un `as`, l'ordre des instructions, un `import()` calculé ou toute autre ligne en font un test modifié. Ces fichiers sont listés dans la sortie (« tests dont seuls les imports changent : non répétés ») et dans le reçu (`repeat.importsOnly`), jamais sautés en silence ; la commande du contrôle les exécute comme les autres. **Tests dont seuls des chemins de fichiers déplacés changent** : de même, un fichier de test dont chaque ligne modifiée ne diffère que par le remplacement de l'ancien chemin d'un fichier renommé sans changement dans le même diff (par exemple une maquette rangée par `git mv`) par son nouveau chemin n'est pas répété ni compté dans `maxFiles`. Sans changement : même blob et même mode aux deux chemins (`git diff -M --raw` ; dans l'arbre de travail, le nouveau fichier est haché), jamais un lien symbolique ; une similarité de 100 % ne suffit pas (lignes permutées, mode changé). Lignes comparées dans l'ordre, même nombre de lignes : une ligne ajoutée, retirée, réécrite sur plusieurs lignes ou changée en plus du chemin en fait un test modifié. Un chemin cité n'est remplacé que dans une chaîne (`'…'`, `"…"`, gabarit `` `…` `` hors `${…}`) ou un commentaire (`//`, `/* */`, `<!-- -->`, `#`), jamais dans le code (un identifiant, une division `a/b`) ; il est complet (éventuellement après `./` ou `../`) ou en est un suffixe coupé sur un `/` qui nomme encore un dossier commun aux deux chemins (`design/x-validee.html` pour `docs/design/x-validee.html` devenu `docs/design/produit/x-validee.html`), toujours avec un « / » (un fichier à la racine renommé n'ouvre rien), jamais s'il n'en reste que le nom relatif au dossier commun (`x-validee.html`) ni à l'intérieur d'un chemin ou d'un nom plus long. Limite : le dossier depuis lequel un chemin cité est résolu à l'exécution n'est pas connu ; l'outil garantit que le fichier renommé a le même contenu, pas que le test lit bien cette ressource. Un renommage avec modification n'ouvre pas l'exemption ; un test lui-même renommé n'est comparé que sur ses imports. Un fichier dont chaque ligne modifiée est un import ou un chemin déplacé entre dans cette catégorie, listée dans la sortie (« tests dont seuls des chemins de fichiers déplacés changent : non répétés ») et dans le reçu (`repeat.movedPathsOnly`), jamais sautée en silence. La définition du contrôle est celle de la base, comme le reste. Plus de fichiers que `repeatChanged.maxFiles` (10 par défaut), ou un fichier dont le chemin commence par `-` (il serait lu comme une option) : refus `GATE_REPEAT`, sortie `1`, fichiers listés, rien n'est lancé (jamais un saut silencieux). Puis, une fois la commande du contrôle réussie (après sa relance `retryFailed` comprise), dans la même copie, sous le même verrou et la même file, HEAD et arbre vérifiés identiques à leur état relevé juste avant la commande du contrôle (sinon « Répétition des tests modifiés refusée », avec les entrées de `git status` apparues ou disparues), l'outil lance `repeatChanged.command` (`{{repeat}}` remplacé par `repeatChanged.times`, 5 par défaut, partout dans un argument ; `repeatChanged.stressArgs` ajoutés ; puis les fichiers), bornée par `repeatChanged.timeoutMs` (sinon le délai du contrôle). Tout échec rend le contrôle rouge, même « réussi après relance » : la répétition n'est jamais relancée par `retryFailed`. Diagnostic « Test instable : … échoue » avec, pour chaque test que nomme `repeatChanged.testPattern` (sinon `retryFailed.testPattern`), « échoue X fois sur N » (nombre de lignes de la sortie qui le nomment ; Playwright `--repeat-each` avec `--retries=0` écrit une ligne par répétition en échec) ; délai dépassé : statut `timed_out`, « Refus : … a dépassé son plafond de durée ». Sous le tableau, « Tests modifiés répétés (repeatChanged) » donne, par contrôle, les fichiers, N et l'issue ; « Attentes à durée fixe dans les tests modifiés » liste les lignes ajoutées par le changement qui attendent une durée (`waitForTimeout(`, `sleep(`, `new Promise(r => setTimeout(r, …))` ; lignes de commentaire ignorées) : avertissement par défaut, refus `GATE_REPEAT` avant toute attente avec `repeatChanged.fixedWaits` à `"refuse"`, rien avec `"off"`. Le reçu porte `repeat` : `base`, `reference` (base commune avec la référence, ou `null`), `files`, `importsOnly` (tests dont seuls les imports changent, non répétés), `movedPathsOnly` (tests dont seuls des chemins de fichiers déplacés changent, non répétés), `times`, `status` (`passed`, `failed`, `timed_out`, `cancelled`, `spawn_error` ; `none` sans fichier de test modifié, `not_run` quand la commande du contrôle n'a pas réussi ; `no_base`, reçus de la première version sans `--base`, jamais une preuve), `command`, `durationMs`, `exitCode`, `failures` (`test`, `count`), `output` (extrait) et `fixedWaits` ; `summary.json` le résume par contrôle. La suite complète avant une PR se lance donc avec `--base <base de la PR>` ; `apv stack batch` passe la cible comme base et comme référence, applique `maxFiles` (et le refus des attentes à durée fixe) PR par PR avant de construire le lot, jamais à leur somme, et un refus de la suite du lot n'est jamais pris pour un échec ni bissecté. `apv gates verify` recontrôle la répétition (ci-dessous).

**Portée de la preuve** (`skipWhenOnly`, 3.0.0-alpha.8, spécification section 21, configuration dans [CONFIGURATION.md](CONFIGURATION.md#graphe-de-contrôles)) : une PR qui ne change que de la documentation, des décisions ou des specs ne paie pas une suite navigateur de 35 minutes, sans rien retirer à la preuve d'une PR qui touche le code. À l'étape `full` seulement, un contrôle qui déclare `skipWhenOnly` exige `--base <ref>` (sans elle, appel incorrect, sortie `2`, avant toute recherche de preuve et toute attente), une base dont HEAD descend strictement (sinon refus `GATE_BASE`, sortie `1`) et une référence `skipWhenOnly.reference` qui se résout par sa ref complète (`refs/remotes/<nom>`, `refs/heads/<nom>`, `refs/tags/<nom>`, `refs/<nom>` : introuvable ou ambiguë, par exemple une branche locale ou un tag `origin/main` à côté de la branche de suivi, appel incorrect, sortie `2` ; jamais un repli sur `--base` seule ; même résolution pour `repeatChanged.reference` et la base de `apv web audit`). Avant toute attente, l'outil liste les fichiers changés (ajoutés, modifiés, supprimés, avec leur mode : `git diff --raw --no-renames`) entre le commit et la base commune de `--base`, et entre le commit et la base commune de la référence ; le contrôle est **non requis** seulement si CHACUN de ces fichiers répond à `skipWhenOnly.paths` **de la référence** (la configuration lue à la référence, jamais celle du changement), à aucun `skipWhenOnly.except` de la référence, à aucun fichier toujours requis (ci-dessous ; `except` et fichiers toujours requis comparés sans la casse), garde son mode et son type, n'est nommé, ni lui ni (s'il est atteint par un motif à joker) l'un de ses dossiers, dans aucun autre fichier suivi (`git grep -F -i` au commit dans tout l'arbre, sauf les fichiers que la liste dispense, `.apv/config.json`, `.apv/DECISIONS.*`, `.apv/specs/**`, `.apv/state/**`, `pipeline.v2.json` et `**/.*ignore` ; chemin, nom, chemin Windows, dossier comme segment `docs/`, `/docs`, `\docs`, `docs\` ou nom cité `'docs'`, `"docs"`, `` `docs` `` : un dossier cité rend requis tout fichier changé dessous ; les commentaires comptent ; un fichier listé exactement n'est cherché que par son chemin et son nom ; fichiers supprimés compris ; recherche impossible ou au-delà de 1000 motifs : requis), et n'est la cible d'aucun lien symbolique du commit (cible résolue en chemin réel ; un lien vers la racine ou un ancêtre rend tout requis ; plus de 500 liens : requis). `skipWhenOnly` est refusé sur un contrôle qui lance `apv web audit` ; si la configuration déclare `web`, tout fichier que l'audit web jugerait « web » rend requis tout contrôle qui a `skipWhenOnly`, quelle que soit sa commande. Sinon il est **requis** et tourne comme avant, avec la raison. Toujours requis, quelle que soit la configuration : `.apv/config.json` et `pipeline.v2.json` (et le fichier de `--config` s'il est dans le dépôt), les manifestes et verrous de dépendances (`package.json`, `package-lock.json` et les autres verrous, `pyproject.toml`, `Cargo.toml`, `go.mod`...), la CI (`.github/**`, `.gitlab-ci.yml`...), `**/.gitattributes`, `.gitmodules`, le dossier des maquettes (`design.dir`, `docs/design` par défaut), le contenu servi, compilé ou chargé par convention (`.md`, `.mdx`, `.svx`, `.html` sous `src/`, `static/`, `public/`, `content/`, `app/`, `pages/`, à toute profondeur), la configuration de build et de test (`**/*.config.*`, `tsconfig*.json`, `.env*`, `Dockerfile*`, `Makefile`...), les tests et scripts de test (`scripts/**`, `**/*.sh`, `test/**`, `tests/**`, `e2e/**`, `**/*.test.*`, `**/*.spec.*`, `**/*.e2e.*`, les `testPaths` et `repeatChanged.paths` du contrôle, les chemins que nomment ses commandes), les migrations (`**/migrations/**`, `**/*.sql`), et tout fichier dont le mode ou le type change (lien symbolique, sous-module, exécutable) ; liste complète : `ALWAYS_REQUIRED` de `src/gates/proof-scope.ts`. Requis aussi : un arbre modifié (`--allow-dirty`), un commit déjà contenu dans la référence (rien à comparer), une référence sans base commune avec le commit, une configuration de la référence illisible, qui ne déclare pas `skipWhenOnly` pour ce contrôle ou qui y déclare une autre `reference` que celle du contrôle (une PR qui pointe sa référence ailleurs n'est jamais dispensée), plus de 2000 fichiers changés. La référence doit être la branche cible protégée (spécification section 21, limite assumée). Un contrôle requis rend requises ses dépendances (transitivement) : un contrôle ne tourne jamais sans ce dont il dépend. Un contrôle non requis n'est pas lancé (s'il était le seul contrôle `full`, ni file, ni ports, ni fin de suite) : son reçu a le statut `not_required` (code `null`, rien d'exécuté) et porte `scope` : `required`, `reason`, `base` (base commune de `--base`), `reference` (base commune de la référence), `referenceName`, `referenceSha` (le commit où la liste a été lue), `fileCount`, `files` (tous les fichiers changés) et `blocking` (ceux qui le requièrent, 50 au plus) ; un contrôle requis porte aussi `scope`, avec sa raison. La sortie le dit (« non requis (portée) » dans le tableau, « Portée de la preuve (skipWhenOnly) » sous lui, verdict « Tous les contrôles requis passent ; N non requis… ») et `summary.json` résume `scope` par contrôle. Une PR ne peut pas se donner de dispense : changer la liste touche `.apv/config.json`, toujours requis, et la liste lue est celle de la référence. `apv gates verify` recalcule la portée (ci-dessous) ; `apv stack batch` passe la cible comme référence.

`--only` choisit des contrôles et ajoute leurs dépendances. Par défaut, le premier échec arrête les contrôles suivants ; `--keep-going` les laisse tous s'exécuter. `--concurrency` borne le parallélisme (3 par défaut).

Chaque exécution écrit dans `.apv/receipts/<exécution>/` un reçu JSON par contrôle (statut, code de sortie, durée, empreintes des sorties, empreinte de preuve liée au commit, à la configuration, à l'environnement et à l'exécutable, diagnostic en cas d'échec) et un `summary.json`. Le dossier `.apv/receipts/` contient un `.gitignore` : les reçus sont des preuves locales, jamais commitées. Chaque reçu note le commit (`candidateSha`), le stage demandé (`stage`) et l'état de l'arbre (`dirty`), et `override` pour une suite complète lancée avec `--reason` ; le résumé reprend `stage`, `dirty`, `selected`, `added`, `reserved`, `targeted` et `override`. Le reçu d'un contrôle exécuté par sa commande ciblée porte `targeted: true`. Si l'arbre de travail avait des modifications non commitées (`dirty: true`), les reçus décrivent plus que le commit : `apv gates verify` ne les retient pas.

**Magasin partagé des reçus** : à la fin de chaque exécution, l'outil la copie aussi dans le magasin partagé du dépôt, `<répertoire git commun>/apv/receipts/<exécution>/` (le répertoire que donne `git rev-parse --git-common-dir`, `.git` du checkout principal : commun à tous les worktrees du dépôt, jamais versionné). La copie reprend les reçus et `summary.json` à l'identique, plus un `manifest.json` (`version`, `runId`, `candidateSha`, `worktree` où l'exécution a tourné, `copiedAt`, `files` : l'empreinte sha256 de chaque fichier). Elle passe par un dossier temporaire renommé à la fin : un lecteur ne voit jamais une copie partielle. Ainsi les reçus survivent au retrait du worktree (la copie détachée de livraison, retirée par `git worktree remove` une fois la PR ouverte), et `apv gates verify --commit <sha>` prouve le commit depuis n'importe quel checkout du dépôt. Une copie impossible (magasin non inscriptible, par exemple) est signalée par une ligne « Attention » et `sharedError` en JSON, jamais fatale : l'exécution et ses reçus locaux restent. Le dossier `.apv/receipts/` du worktree garde exactement sa forme (reçus et `summary.json`, sans manifeste). Après chaque copie, la rétention du magasin s'applique (section `receipts` de `.apv/config.json`, [CONFIGURATION.md](CONFIGURATION.md#reçus--receipts) : les 1000 exécutions les plus récentes de moins de 30 jours par défaut) ; les reçus des worktrees ne sont jamais touchés.

Différences avec V2 : pas d'espace de travail jetable (l'implémenteur exécute les contrôles dans le worktree qu'il possède, sauf les copies de `--stacks`), pas de cache de reçus (`cacheTtlMs` est ignoré), pas de commandes de préparation par contrôle (`setup` ; `batch.setup` prépare seulement une copie neuve).

En JSON : `ok`, `runId`, `candidateSha`, `baseSha`, `dirty`, `alreadyProven`, `stage`, `notRequired` (contrôles non requis par leur portée, non lancés), `config`, `legacyConfig`, `ignoredSections`, `added`, `reserved`, `targeted`, `receiptsDirectory`, `sharedDirectory` (copie dans le magasin partagé, ou `null`), `sharedError` (raison d'une copie impossible, ou `null`), `pruned` (exécutions retirées du magasin par la rétention), `gates` (contrôles exécutés, chacun avec `targeted`, et selon le cas `lockWaitMs`, `retriedTests` et `repeat` : `status`, `base`, `files`, `times`, `failures`, `fixedWaits`), `suite`, `queue`, `ports`, `flaky` (contrôles réussis après relance), `cleanup` (fin de suite), `spread` (répartition sur les piles, ou `null`), `stoppedStacks`, `interrupted` (signal reçu, ou `null`), `rhythm` (`run`, `source` : `option` ou `branch`, `step`, `level`, `override`, ou `null` hors exécution), `notes`.

Sortie : `0` tous les contrôles exécutés passent (réussis après relance compris), `128 + signal` interruption, `1` au moins un échec, une configuration invalide ou une suite complète refusée (rythme de l'exécution `GATE_RHYTHM`, arbre modifié `GATE_DIRTY`, file `SUITE_QUEUE`) ou une répétition refusée (`GATE_REPEAT` : plafond `repeatChanged.maxFiles`, attente à durée fixe refusée), `2` appel incorrect (dont `--base` absent alors qu'un contrôle lancé déclare `repeatChanged`, ou à la suite complète `skipWhenOnly`, une référence `skipWhenOnly.reference` introuvable, un `--stage` inconnu, `--commit`, propre à `verify`, un `--run` invalide ou un `--reason` vide, trop long ou avec `--stage task`).

### Contrôles de la base

Un commit porte sa propre `.apv/config.json` : lue seule, elle pourrait retirer ou relâcher les contrôles qui le prouvent. `apv gates run` et `apv gates verify` lisent donc aussi la configuration de la **base** : la base commune du commit et de `--against <ref>`, sinon de `--base`, sinon de la branche par défaut du dépôt distant (`origin/HEAD`, `origin/main`, `origin/master`). La référence se résout par sa ref complète (un nom ambigu, une branche locale `origin/main` à côté de la ref de suivi, est refusé ; un sha, même abrégé, est pris tel quel). Une ref de suivi distante est comparée au dépôt distant (`git ls-remote`, 15 s au plus). Le commit distant absent localement (une autre PR fusionnée depuis le dernier fetch) : cette seule branche est récupérée (`git fetch` limité à elle, sans étiquettes ni sous-modules ni hooks, environnement filtré, 60 s au plus), puis la base est celle du dépôt distant ; récupération impossible, avertissement « non vérifié : git fetch ». Refus `GATE_BASE` seulement quand il est prouvé que la ref locale n'est pas dans l'historique distant (déplacée). Ref en retard (ancêtre du distant) : `run` avertit, `verify` refuse (« git fetch ») : une base reculée ne fait jamais accepter une preuve. Distant illisible (réseau absent), ou commit distant impossible à récupérer : `run` avertit « base non vérifiée » ; `verify` refuse (`GATE_BASE`), sauf `--offline`, qui l'accepte avec un avertissement. Le fetch automatique ne lance jamais de nettoyage (`--no-auto-gc`). Une branche locale qui a une jumelle distante (`--against main` quand `origin/main` existe) est signalée, et un dépôt qui a un distant sans aucune base appliquée aussi. **Tout** contrôle de la base, obligatoire ou non, reste exigé avec sa définition de base (commande, étape, dépendances, verrou...) quand le candidat le retire, le rend facultatif ou le modifie ; ses dépendances de base le suivent. Un contrôle `full` gardé est réservé à la suite complète à l'étape `task`, jamais abandonné. La sortie le dit (`Contrôles de la base maintenus…`, sur la sortie d'erreur de `run` et en tête de `verify` ; `baseGates` en JSON : `reference`, `mergeBase`, `file`, `differences` avec `id` et `kind`, `removed`, `optional`, `changed` ou `dependency`). Le candidat peut seulement **ajouter** des contrôles ou les **durcir** (un contrôle nouveau, ou la même définition rendue obligatoire ; toute autre différence fait tourner la définition de base). Avertissements : `baseGates.warnings`, et des lignes « Attention : » dans le texte. Sans référence, ou si la base n'a pas de configuration (adoption d'APV), les contrôles du candidat s'appliquent tels quels (`file: null`). Sans base commune entre la référence et le commit (clone superficiel, référence sans lien) : refus `GATE_BASE`, jamais un repli sur les contrôles du candidat. Un `--config` explicite est jugé de la même façon. `--against HEAD` juge un commit contre lui-même : ses reçus ne se vérifient que par un `verify` qui lit la même base, jamais contre la vraie branche cible. Une référence qui ne se résout pas : refus `GATE_BASE`, « git fetch ou --against ».

`run` et `verify` doivent lire la même base pour qu'une preuve se vérifie (l'empreinte de configuration des reçus est celle de la liste maintenue) : passer la même `--base` (étape `task`) ou la même `--against`.

**Changer la liste des contrôles** : c'est une décision de l'opérateur, par une **PR de configuration seule**. Elle est prouvée par les contrôles de sa base (ceux qu'elle retire tournent encore, sur un code inchangé : ils passent), puis l'opérateur la fusionne ; les changements suivants sont jugés par la nouvelle liste. Une PR qui mêle ce changement à du code reste jugée par l'ancienne liste, et `apv reuse check` le signale en bloquant ([REUSE.md](REUSE.md#28-échec-fermé--aucun-fichier-du-changement-ne-sort-du-contrôle-sans-déclaration)).

## `apv gates verify`

```
apv gates verify --commit <sha> [--stage full|task] [--base <ref>] [--config <fichier> | --commit-config] [--repo <chemin>] [--json]
```

Vérifie, sans rien exécuter, que les reçus prouvent que chaque contrôle exigé a réussi sur ce commit exact. Contrôles exigés : tous avec `--stage full` (défaut) ; avec `--stage task` (niveau tâche, celui des intégrations intermédiaires et des corrections sous `run.fullSuite` à `final`), ceux de stage `task` et les contrôles `full` qui déclarent `affected`, les autres contrôles `full` étant listés dans `reserved`, jamais prouvés. `--commit` accepte toute révision que Git résout en commit (SHA complet ou abrégé, `HEAD`) ; la comparaison se fait sur le SHA complet.

Pour chaque contrôle exigé, seuls comptent les reçus de ce commit, écrits sur un arbre propre (`dirty: false` ; pour un reçu plus ancien sans ce champ, celui du `summary.json` de son exécution, sinon inconnu donc refusé) et avec la configuration actuelle des contrôles (même `configHash`). Les reçus de toute exécution comptent (une exécution `--stage task` prouve ses contrôles autant qu'une suite complète), mais seul le plus récent de chaque contrôle est retenu : un échec plus récent l'emporte toujours sur une réussite plus ancienne. États : `passed` (réussi ; un reçu `passed_after_retry` compte comme réussi, affiché « réussi après relance (instable) », listé sous le tableau et dans `flaky` en JSON, et le verdict dit « dont N instable(s) »), `failed` (échec, avec le statut du reçu), `dirty` (reçus seulement sur un arbre modifié), `missing` (aucun reçu), `unrepeated` (« tests modifiés non répétés » : le reçu retenu a réussi mais, le contrôle déclarant `repeatChanged`, il ne prouve pas la répétition des tests que le commit ajoute ou modifie), `unaudited` (« audit web non prouvé » : le reçu porte un relevé `web` qui dit « non requis », quelle que soit la commande qui a lancé l'audit (enveloppée dans `apv lock run` ou un script compris), et le recalcul depuis le commit, fichiers changés depuis la base commune de la référence enregistrée et depuis la base enregistrée, règles de `web.neutralPaths` et des fichiers toujours web, dit l'audit requis ; référence introuvable, base égale au commit ou relevé sans référence ni base : non prouvé non plus ; sans relevé, seul un contrôle dont la commande montre `web audit --preview --base` est refusé, par repli sur sa ligne de commande). Pour un contrôle qui déclare `repeatChanged`, `verify` recalcule lui-même, depuis le commit, les fichiers de test ajoutés ou modifiés depuis la base enregistrée dans le reçu et, au niveau complet pour un reçu complet, depuis la référence (`repeatChanged.reference` ; la cible pour `apv stack batch`), et refuse : une référence introuvable, un reçu sans répétition (`no_base`, sans `repeat`), une répétition qui n'a pas réussi, une base égale au commit, un fichier modifié absent de `repeat.files` (listé), une attente à durée fixe avec `fixedWaits` à `"refuse"`. Une répétition rouge ne s'efface donc ni par une suite relancée sans base ni par une base trop proche ; `--skip-proven` suit la même preuve. Les fichiers illisibles et les reçus d'une autre configuration sont ignorés et signalés. Au niveau complet, les reçus ciblés (`targeted: true`, commande `affected` lancée par `--stage task`) ne comptent jamais, ni comme réussite ni comme échec : seule la suite complète prouve un contrôle `full` ; ils sont comptés dans `targeted` et signalés si le contrôle n'est pas prouvé.

**Portée recalculée** (`skipWhenOnly`, 3.0.0-alpha.8) : un reçu `not_required` ne prouve rien par lui-même. Pour lui, `verify` recalcule la portée depuis le commit, avec la base enregistrée dans le reçu (`scope.base`), la référence de la configuration (`skipWhenOnly.reference` ; la cible pour `apv stack batch`) et la liste lue à cette référence : le contrôle est prouvé (« non requis (portée recalculée) », état `passed`, listé dans `notRequired` en JSON) seulement si ce recalcul le dit non requis. Sinon état `required` (« requis (dispense non prouvée) »), avec la raison et les fichiers qui le requièrent : un reçu sans base, une base égale au commit ou en aval, une référence introuvable, un contrôle qui ne déclare plus `skipWhenOnly`, une référence qui ne le déclare pas (ou plus), un fichier avec effet. `--skip-proven` suit la même preuve.

**Où les reçus sont lus** : d'abord `.apv/receipts/` du worktree (comme avant), puis le magasin partagé du dépôt (section `apv gates run`) pour les exécutions que le worktree n'a pas : une exécution présente dans le worktree est lue là seulement. Les exigences ne changent pas selon l'emplacement : même commit exact, arbre propre, configuration actuelle, reçu le plus récent de chaque contrôle. Une exécution du magasin partagé ne compte que si elle est intacte : son `manifest.json` la nomme, liste exactement ses fichiers avec leur empreinte sha256, `summary.json` est présent, et chaque reçu appartient à l'exécution (même `runId`, même `candidateSha` que le manifeste, fichier au nom de son contrôle). Sinon aucun de ses reçus ne compte, et elle est signalée : « Exécutions du magasin partagé refusées (altérées) », `altered` en JSON (`runId`, `reason`). Les exécutions dont le manifeste nomme un autre commit ne sont pas lues (elles ne prouvent rien ici). Limite assumée : le manifeste détecte une altération des fichiers (édition, fichier ajouté ou retiré, copie tronquée), pas un faussaire qui réécrit aussi le manifeste ; il n'y a pas de clé secrète, et les reçus du worktree n'ont pas de manifeste. Le tableau marque « (magasin partagé) » un reçu retenu dans le magasin et donne son chemin. Le chef de projet principal vérifie donc la preuve de livraison depuis n'importe quel checkout du dépôt, la copie de livraison retirée.

`--commit-config` : la configuration des contrôles est lue au commit vérifié (`git show <commit>:.apv/config.json`, sinon `pipeline.v2.json` ; aucune : aucun contrôle, refus `NO_GATES`) plutôt que dans le checkout ; `config` vaut alors `<sha>:.apv/config.json` en JSON. Utile depuis un checkout dont la configuration diffère de celle du commit (le checkout principal sur `main` quand la PR change les contrôles) : sans elle, les reçus comptent comme « configuration des contrôles différente ». Avec `--config` : appel incorrect.

Au niveau tâche, un contrôle `full` qui déclare `affected` est prouvé par son reçu ciblé ou par un reçu complet, le plus récent des deux décidant. `--base <ref>` est alors obligatoire (sinon refus `GATE_BASE`, sortie `1`) : le dernier commit prouvé par la suite complète, que donne `apv run next`. Un reçu ciblé ne compte que si la base de son exécution (le `baseSha` du `summary.json` de son exécution) est `<ref>` ou l'un de ses ancêtres, c'est-à-dire s'il a couvert au moins tous les changements depuis `<ref>` ; les autres sont comptés dans `otherBase` et signalés. Un reçu complet compte quelle que soit la base. `--base` sans `--stage task` : appel incorrect. Une vérification du niveau tâche ne remplace jamais la suite complète avant une PR.

En JSON : `ok`, `commit`, `stage`, `base`, `config`, `configHash`, `required`, `targeted` (contrôles exigés par leur variante ciblée), `reserved`, `gates` (`gateId`, `state`, `status`, `receipt`, `runId`, `otherConfig`, `targeted`, `viaTargeted`, `proof` : `full`, `targeted` ou `null`, `otherBase`, `source` : `local`, `shared` ou `null`), `unreadable`, `store` (chemin du magasin partagé), `altered`, `flaky` (contrôles prouvés par un reçu « réussi après relance »), `repeating` (contrôles exigés qui déclarent `repeatChanged`), `auditing` (contrôles exigés qui lancent `apv web audit --preview --base` d'après leur commande, ou dont un reçu porte un relevé `web`), chaque ligne de `gates` avec `repeat` (`missing`, `reason`, ou `null`) `web` (`files`, `reason`, ou `null`) et `scope` (portée recalculée d'un reçu `not_required` : `required`, `reason`, `files`, `blocking`, ou `null`), `notRequired` (contrôles prouvés non requis par leur portée), `missing` (contrôles non prouvés).

Sortie : `0` preuve complète, `1` preuve incomplète (ce qui manque est listé, avec la commande à relancer), commit introuvable, aucun contrôle exigé, `--base` manquant pour des contrôles ciblés ou configuration invalide, `2` appel incorrect (`--commit` absent, `--base` sans `--stage task`, `--commit-config` avec `--config`, option propre à `run`).

## `apv gates receipts`

```
apv gates receipts list [--commit <ref>] [--limit N] [--repo <chemin>] [--json]
apv gates receipts export <exécution> --out <dossier> [--repo <chemin>] [--json]
apv gates receipts prune [--keep-days N] [--keep-runs N] [--config <fichier>] [--repo <chemin>] [--json]
```

Les exécutions de `apv gates run` du worktree (`.apv/receipts/`) et du magasin partagé du dépôt (section `apv gates run`).

`list` : les plus récentes d'abord, 20 par défaut (`--limit N`), avec commit, stage, verdict, état de l'arbre et emplacement (`worktree`, `magasin partagé`, les deux, ou « altérée » avec la raison) ; `--commit <ref>` garde celles de ce commit. En JSON : `store`, `total`, `runs` (`runId`, `candidateSha`, `stage`, `ok`, `dirty`, `local`, `shared`, `intact`, `reason`).

`export <exécution> --out <dossier>` : copie l'exécution dans `<dossier>/<exécution>/` avec un `manifest.json` (empreinte sha256 de chaque fichier ; `sha256sum` suffit à les recontrôler), depuis le worktree s'il l'a, sinon depuis le magasin partagé, où elle doit être intacte (sinon refus `RECEIPT_EXPORT`, sortie `1`). Pour joindre la preuve d'une livraison à un dossier que l'opérateur garde. La destination ne doit pas exister.

`prune` : applique tout de suite la rétention au magasin partagé : garde les `keepRuns` exécutions les plus récentes de moins de `keepDays` jours (d'après l'heure de début inscrite dans leur identifiant), retire les autres et les copies interrompues de plus d'une heure ; les autres entrées du dossier et les reçus des worktrees ne sont jamais touchés. `--keep-days` (1 à 3650) et `--keep-runs` (1 à 100000) remplacent la section `receipts` de la configuration. `apv gates run` applique la même rétention après chaque copie.

Sortie : `0`, `1` exécution introuvable ou altérée, destination existante, commit introuvable, `2` appel incorrect (sous-commande inconnue, `--out` manquant, option d'une autre sous-commande).

## `apv wait`

```
apv wait --pid <pid> [--timeout <secondes>] [--json]
apv wait --file <chemin> [--contains <texte>] [--timeout <secondes>] [--json]
```

Attente bornée, pour une session qui n'a pas le droit d'attendre par le shell : en session non interactive, `sleep`, `tail --pid` et les boucles sur `kill -0` sont refusés par les permissions (projet pilote, 24 septembre 2026 : la session a bricolé des scripts node pour attendre la suite complète). Une seule condition par appel :
- `--pid` : la fin du processus. Un processus absent, ou zombie (il n'attend plus que son parent), compte comme terminé ; un processus d'un autre utilisateur (`EPERM`) comme vivant. Le code de sortie du processus n'est pas connu de l'outil : on lit son journal ou ses reçus. `0`, `1` et le pid de `apv wait` lui-même sont refusés (`2`).
- `--file` : l'existence du fichier ; avec `--contains <texte>` (non vide), la présence du texte dans le fichier. Chaque relevé ne relit que les octets ajoutés depuis le précédent (plus la longueur du texte, pour un texte à cheval sur deux lectures) ; un fichier raccourci est relu depuis le début ; seul un fichier ordinaire est ouvert (une FIFO ne bloque pas l'attente). Chemin relatif au dossier courant.

`--timeout` : de 1 à 580 secondes (défaut 580), sous la limite de dix minutes d'un appel Bash de Claude Code ; au-delà, refus en `2`, et on relance simplement `apv wait`. Relevé toutes les secondes (`APV_WAIT_POLL_MS` pour les tests). Sortie texte : « Terminé : … » ou « Délai dépassé : … Relancer apv wait pour attendre encore. » ; JSON : `condition`, `pid` ou `file` et `contains`, `met`, `immediate` (condition remplie au premier relevé), `waitedSeconds`, `timeoutSeconds`.

Sortie : `0` condition remplie, `1` délai dépassé, `2` appel incorrect (aucune condition ou les deux, `--contains` sans `--file`, délai hors bornes).

## `apv procs`

```
apv procs list [--repo <copie>] [--port <p>]... [--include-main] [--all] [--json]
apv procs stop [--repo <copie>] [--port <p>]... [--include-main] [--grace <secondes>] [--json]
```

Serveurs de test orphelins. Une suite navigateur qui dépasse le délai d'un appel Bash (600 s) est coupée, mais les serveurs qu'elle a lancés (`vite preview`, serveur web de Playwright) restent à l'écoute sur les ports de la pile de test ; une session non interactive n'a pas le droit de `kill` et attendait (projet pilote, 25 et 26 septembre 2026). `apv procs` les trouve et les arrête, sans jamais toucher un processus étranger au dépôt.

Les processus sont lus dans `/proc` (Linux) : répertoire courant (`/proc/<pid>/cwd`), ports TCP en écoute (IPv4 et IPv6), parent, heure de démarrage. Sur un système sans `/proc` (macOS, Windows), refus clair (`PROCS_UNSUPPORTED`, sortie `1`). Un processus **appartient au dépôt** quand son répertoire courant est dans un de ses worktrees (`git worktree list` : copie principale, copies liées, copies détachées d'un dossier de session).

Cibles :
- `--port <p>` (répétable, ou `--port 4173,4174`) : les processus qui écoutent sur ces ports ; `--repo` ne sert alors qu'à trouver le dépôt (défaut : dossier courant) ;
- sans `--port`, `--repo <copie>` : tous les processus lancés dans cette copie, qu'ils écoutent ou non ; la copie doit être un worktree lié du dépôt, jamais la copie principale, qui porte la session et ses outils (refus `2`) ;
- sans l'un ni l'autre : les processus qui écoutent sur les **ports de test déclarés**, section `resources` de `.apv/config.json` et `ports` des piles de `stacks` ([CONFIGURATION.md](CONFIGURATION.md#ressources-de-test--resources)) ; `stop` sans port déclaré est refusé (`2`) ; `list` montre alors aussi tous les processus des worktrees.

`list` affiche pour chaque cible son pid, ses ports, son worktree (ou son répertoire hors du dépôt), sa commande et son état (`arrêtable (apv procs stop)` ou la raison du refus) ; les ports visés libres sont nommés. Par défaut, `list` ne montre que ce que `stop` arrêterait et ce qui écoute sur un port visé (ports déclarés, ou `--port`) ; le nombre des autres processus des worktrees est indiqué, et `--all` les montre aussi (checkout principal, outils protégés). Les autres commandes du pipeline qui lance `apv` (`apv procs list | tail | cut`) n'apparaissent jamais : les enfants d'un shell parent de `apv` qui sont dans le même groupe de processus que lui, comme `apv` et ses parents.

`stop` n'arrête que les cibles du dépôt : `SIGTERM` à toutes, puis `SIGKILL` à celles qui tournent encore après `--grace` secondes (défaut 5, de 0 à 60), puis vérification. Jamais arrêtés, et signalés :
- un processus hors du dépôt (autre projet, autre utilisateur, aperçu de `apv preview` qui tourne dans sa propre copie) ou dont le répertoire est illisible ;
- `apv` lui-même et ses parents (la session, son shell) ;
- un **outil protégé**, où qu'il tourne et quel que soit son port (`protégé : outil (...)`) : serveur d'éditeur distant (exécutable ou commande sous `.vscode-server/`, `.cursor-server/`, `.windsurf-server/`...), extension d'éditeur, serveur de langage (`language-server`, `tsserver`, `svelteserver`, `gopls`, `rust-analyzer`...), serveur MCP (`mcp`, `mcp-server`, `modelcontextprotocol`, comme `npx @sveltejs/mcp`), session Claude Code ; motifs relevés sur l'exécutable (`/proc/<pid>/exe`) et la ligne de commande ;
- un processus du **checkout principal** (premier worktree de `git worktree list`, où tournent l'éditeur et les serveurs de l'opérateur) : `protégé : checkout principal`, sortie `1`, même s'il écoute sur un port visé. `--include-main` l'autorise pour un processus qui écoute sur un **port de test déclaré** (`resources`) et visé, jamais pour un outil protégé ; tous les ports visés doivent alors être déclarés (sinon refus `2`), et `--include-main` avec `--repo <copie>` seul est refusé (`2`).

Un pid réutilisé entre le relevé et le signal n'est pas visé (heure de démarrage comparée).

Sortie : `0` toutes les cibles arrêtées, ou aucune ; `1` une cible refusée (hors du dépôt, protégée, checkout principal, signal refusé) ou encore vivante après `SIGKILL`, ou système sans `/proc` ; `2` appel incorrect (dont `--all` avec `stop`). JSON : `action`, `mode` (`ports`, `copy`, `all`), `repository`, `worktrees`, `copy`, `ports`, `declaredPorts`, `freePorts`, `includeMain`, `hidden` (processus masqués par `list` sans `--all`), `processes` (`pid`, `ppid`, `ports`, `cwd`, `worktree`, `command`, `exe`, `stoppable`, `refusal` : `outside`, `protected`, `unknown-cwd`, `tool` (avec `tool`, le nom de l'outil) ou `main-checkout`, et pour `stop` `outcome` : `terminated`, `killed`, `survived`, `gone` ou `denied`), `ok`.

## `apv stacks`

```
apv stacks status [--repo <chemin>] [--json]
apv stacks idle-stop [--after <durée>] [--stack <id>]... [--dry-run] [--watch] [--interval <s>] [--repo <chemin>] [--json]
apv stacks start <id> [--repo <chemin>] [--json]
```

Piles de test déclarées (section `stacks`, [CONFIGURATION.md](CONFIGURATION.md#piles-de-test--stacks), spécification section 18.4). Des piles Docker de test restées démarrées des heures consomment mémoire et processeur de la machine qui fait tourner les suites ; `idle-stop` n'arrête que celles dont l'inactivité est **prouvée**, jamais sur une impression.

**Occupée** : son verrou tenu (`lockFile` : `flock -n` ne l'obtient pas ; `resource` : bail vivant de `apv lock`), une suite complète en cours (file `suite.queue` tenue, ou la place de cette pile dans la file, 3.0.0-alpha.20), ou un processus à l'écoute sur ses `ports`. **Inactive depuis** : chaque passage note la pile libre ou occupée dans `<répertoire git commun>/apv/stacks/<id>.json` ; la période d'inactivité commence au premier passage qui la trouve libre après une utilisation, et se rompt si deux passages sont séparés de plus de 2 min (rien ne prouve qu'elle soit restée libre entre les deux) ou si une utilisation est connue depuis son début : fin d'un contrôle de `apv gates run` sous son verrou (notée par l'outil), événement de son bail dans le journal de `apv lock`. Un passage isolé n'arrête donc jamais rien.

`status` : pour chaque pile, occupée (et pourquoi) ou libre, dernière utilisation connue, libre depuis, arrêtée, redémarrée, commandes d'arrêt et de redémarrage. `idle-stop` : arrête chaque pile libre depuis au moins `--after` (`30m`, `1h`, `1800` ; défaut : `idleAfterMs` de la pile, sinon 30 min ; une minute au moins) et pas déjà arrêtée depuis sa dernière utilisation, par sa commande `stop`, **sous son verrou et celui de la file des suites (avec la place de la pile dans la file), pris sans attendre** : pris entre-temps, la pile est en usage, rien n'est lancé. `--stack <id>` (répétable) limite aux piles nommées ; `--dry-run` dit ce qui serait arrêté ; `--watch` repasse toutes les `--interval` secondes (30 par défaut, de 0,1 à 110) jusqu'à ce que chaque pile visée soit arrêtée, ou SIGINT (à lancer en arrière-plan). Chaque décision (arrêt, échec, raison de garder) est journalisée dans `<répertoire git commun>/apv/stacks/events.log`.

**Redémarrage** : `apv stacks start <id>` lance la commande `start` de la pile sous son verrou (pris sans attendre : tenu, la pile est en usage donc démarrée, sortie `1`), note le redémarrage (une nouvelle période d'inactivité pourra l'arrêter de nouveau) et le journalise. Sans commande `start` déclarée : refus `STACK_START`. Une commande qui trouve sa pile arrêtée échoue sur une connexion refusée : `apv stacks status` le montre, `apv stacks start <id>` la relance, puis on relance la commande.

Sortie : `0` succès (aucune pile déclarée compris), `1` commande `stop` ou `start` en échec, pile inconnue (`STACK_UNKNOWN`) ou occupée au redémarrage, `2` appel incorrect. JSON : `status` rend `stacks` (`id`, `lock`, `lockFree`, `busy`, `lastUsedAt`, `freeSince`, `stoppedAt`, `startedAt`, `stop`, `start`, `idleAfterMs`) ; `idle-stop` rend `passes`, `decisions` (du dernier passage : `id`, `action` `stopped|failed|would-stop|kept`, `idleMs`, `reason` ou `output`) et `all`.

## `apv review plan`

```
apv review plan --base <ref> [--head <ref>] [--force <domaine>]... [--repo <dépôt>] [--json]
```

Propose les domaines de revue de `/apv:review` d'après la nature du diff, pour tous les projets ; le chef de projet la lance avant les revues et ne lance que les domaines retenus. Projet pilote, 25 septembre 2026 : une spec de pur rangement (77 renommages, imports, aucun changement de comportement, aucune migration, aucun écran) est passée par les quatre revues, 40 à 70 minutes, dont trois n'avaient rien à relire. Lecture seule : aucun fichier écrit.

- Diff lu : `git diff -M` depuis la base commune de `--base` (la base de la PR ou de l'exécution) et `--head` (défaut `HEAD`), noms (`--name-status`) et lignes changées. `--repo` : le dépôt (défaut : le dossier courant), où la configuration est lue.
- Chaque fichier a une nature : **renommage pur** (similarité 100 %), **chemins seuls réécrits** (les lignes changées ne font que renommer des références à des fichiers déplacés dans le même diff : imports, `vi.mock`, chemins cités en commentaire ; un spécificateur relatif est résolu depuis le fichier qui le porte ; imports réordonnés ou remis en forme par un formateur), ou **contenu changé** (fichier ajouté, supprimé, binaire, toute autre ligne). Une chaîne modifiée, un nom importé en plus, un autre module de même nom, deux instructions permutées restent des changements de contenu.
- Et des classes, d'après ses chemins (ancien et nouveau) : `ui` (composants, styles, gabarits), `data` (requêtes, dépôts, modèles), `migrations` (migrations et schémas, plus `db.migrations`), `personal` (export, cookies, consentement, traceurs, `.apv/rgpd/`), `legal` (mentions, confidentialité, CGU), `neutral` (tests, documentation, outillage : compte seulement si aucune autre classe ne s'applique), `tooling` (mocks, fixtures, utilitaires de test), `server` (code serveur et configuration : aucun domaine en propre, garde la prudence d'un fichier non classé), `personal` comprend aussi les modèles de messages (`**/email*/**`, `**/emails/**`, `**/mail/**`, `**/notifications/**`), les maquettes validées (`design.dir`) ; aucune classe de domaine : **non classé**. Motifs : `review.paths` ([CONFIGURATION.md](CONFIGURATION.md#revues--review)).
- Règles :
  - `securite` : **toujours**, sans exception ; aucune clé de configuration ni option ne la saute. Les fichiers sensibles de la voie `high` (`sensitivePaths` et `risk.highPaths`) touchés sont cités.
  - `fidelite` : un fichier `ui` au contenu changé, ou une maquette validée touchée (renommée comprise).
  - `donnees` : une migration touchée (renommage compris : l'outil de migration suit les noms), ou un fichier `data` au contenu changé, ou un terme de données (`review.terms.data`, par exemple `.from('`, `insert into`) dans les lignes changées d'un fichier `ui` ou `data`.
  - `rgpd` : une migration touchée, un fichier `personal` ou `legal` au contenu changé, ou un terme RGPD (`review.terms.personal`, par exemple `cookie`, `localStorage`, `email`, `analytics`) dans les lignes changées d'un fichier `ui` ou `data`.
  - **Prudence** : un fichier non classé au contenu changé garde `fidelite`, `donnees` et `rgpd`. Un domaine n'est sauté que sur preuve positive qu'il n'a rien à relire ; une fausse alerte garde une revue, jamais l'inverse.
  - **Plus fort que tests et outillage** (3.0.0-alpha.15) : un fichier `neutral` ou `tooling` qui est aussi du code serveur (`server`), un chemin sensible de la voie `high` ou une configuration (`.apv/config.json`, `pipeline.v2.json`, `*.config.*`, configurations de lint et de format, `package.json` et fichiers de verrouillage, `tsconfig*.json`, `.env*`, `.github/**`...) garde `fidelite`, `donnees` et `rgpd` comme un fichier non classé ; seul un fichier nommé comme un test (`*.test.*`, `*.spec.*`, `*.e2e.*`) y échappe, jamais une configuration. Les lignes changées des tests, de la documentation et de l'outillage sont lues pour les termes : un terme de données garde `donnees`, un terme RGPD ou une adresse e-mail réelle (domaine non réservé aux exemples) garde `rgpd`.
  - Termes par défaut (3.0.0-alpha.15) : `review.terms.data` comprend aussi `update `, ` set `, ` where `, `grant `, `revoke `, `truncate `, `drop table` (SQL dans une chaîne) ; `review.terms.personal` aussi `donnée`, `data`, `conserv`, `retention`, `héberg`, `hosting`, `prestataire`, `sous-trait`, `processor`, `transfert`, `supprim`, `delet`, `effac`, `traceur`, `audience` (ce qu'un texte dit des données).
- **Niveau de risque** (3.0.0-alpha.15), décidé par le **chemin** seul, jamais en lisant le contenu comme du texte : `faible` quand chaque fichier est un test (nommé `*.test.*`, `*.spec.*`, `*.e2e.*`, ou sous un dossier `test/` ou `tests/`), de la documentation (`*.md` classée neutre (`docs/`, `README`, `CHANGELOG`) hors dossiers servis `src/`, `static/`, `public/`, `content/`, `app/`, `pages/`, et hors texte légal) ou une maquette validée, sans terme de données ni RGPD ni adresse e-mail réelle dans ses lignes changées ; `eleve` pour tout le reste : migration, configuration, chemin sensible (authentification, session, permissions, dépendances, configuration de sécurité, CI ou instructions des agents), code serveur, terme de données ou RGPD, données, données personnelles, texte légal, **interface** (même un `.svelte` dont seul le texte change), outillage hors dossier de tests, fichier non classé ; le plan est alors celui de 3.0.0-alpha.14. Un test sous un chemin serveur ou sensible reste un test s'il est nommé comme tel ; sous un dossier `tests/` seulement, le code serveur et les chemins sensibles l'emportent (`src/routes/tests/+server.ts`). À risque faible, le plan ne retient que `securite` et, pour une maquette, `fidelite` (plus ce que `--force` ou `review.always` imposent) ; l'outil refuse (`REVIEW_RISK`) un plan qui dirait autre chose. Le niveau ne retire jamais `securite`. Les instructions des agents (`agents/**`, `workflows/**`, `skills/**`, `SKILL.md`, `.apv/brief.md`, `CLAUDE.md`, `AGENTS.md`, `.claude/**`) sont des chemins sensibles, de risque élevé ; un `.md` non classé (`articles/`) aussi. L'outillage (`fixtures/`, `__mocks__/`) hors d'un dossier `test/` ou `tests/` garde tous les domaines (`src/lib/fixtures/demo.ts`), et un dossier `tests/` sous un dossier de routage (`routes/`, `pages/`, `app/`) n'est jamais un dossier de tests (`src/routes/tests/+page.svelte`). Un fichier qu'un plan de risque faible ferait relire par un autre domaine que la fidélité d'une maquette est toujours de risque élevé : `REVIEW_RISK` ne peut plus se déclencher sur un diff valide.
  - Forcés : `review.always` (configuration) et `--force <domaine>` (opérateur, répétable ou liste séparée par des virgules) gardent un domaine quoi que dise le diff ; `--force` inconnu : `2`.
- Sortie texte : domaines retenus (raison, fichiers qui décident, 50 au plus) et sautés (raison), puis la commande à noter. JSON : `tool`, `base` et `head` (`ref`, `sha`), `mergeBase`, `counts` (`files`, `renames`, `paths`, `content`, `neutral`, `unclassified` : non classés et fichiers plus forts que tests et outillage), `risk` (`level` `faible` ou `eleve`, `reason`, `files[]` des fichiers à risque élevé avec `path` et `why`, `fileCount`), `domains[]` (`domain`, `decision` `retained` ou `skipped`, `reason`, `files`, `fileCount`, `forced` `config`, `operator` ou `null`), `retained`, `skipped[]` (`domain`, `reason`), `files[]` (`path`, `from`, `status`, `change` `none`, `paths` ou `content`, `classes`, `keeps[]` avec `domain` et `why`, `risk`, `riskWhy`). La sortie texte donne aussi la ligne « Risque : faible|élevé : <raison> » et les fichiers à risque élevé (10 au plus).
- Un domaine sauté se note dans l'état : `apv run set <id> review:<domaine> skipped --note "<raison>"` (la raison de la sortie ; `--note` exigé pour sauter une revue, et `review:securite` n'est jamais accepté sauté), et va au workflow `apv:revues` (`skipped`) et au fichier de consolidation.

Sortie : `0` plan établi, `1` référence introuvable (`REVIEW_REF`), Git en échec (`REVIEW_GIT`) ou configuration invalide, `2` appel incorrect (`--base` manquant, domaine inconnu).

## `apv rules check`

```
apv rules check --commit <sha> [--target <branche distante>] [--offline] [--repo <chemin>] [--json]
```

Les règles vérifiées avant toute fusion (3.0.0-alpha.12, [REGLES.md](REGLES.md)), les mêmes que celles de `apv stack merge`, `plan` et `batch --merge` : `preuve` (suite complète prouvée au commit, `apv gates verify` avec les contrôles de la base), `instable` (aucun contrôle `passed_after_retry`), `relecture` (chaque domaine que `apv review plan` retient a sa relecture enregistrée à ce commit par son agent, sans constat critique ni haut), `captures` (fidélité retenue par le plan : captures de sa relecture, `rules.captures` ; sans objet pour un projet sans écran à la base qui n'en ajoute pas, comme un outil en ligne de commande), `controles` (projet web : `reuse`, `code-map`, `structure` et `rules.requiredGates`, obligatoires, dans la configuration que la preuve utilise), `maquette` (chaque écran ajouté ou modifié couvert par une maquette validée, déjà sur la cible ou validée par des mots que l'opérateur a tapés). Configuration, maquettes et plan des revues se lisent à la base commune de `--target` (défaut : `origin/HEAD`) et du commit ; la cible est vérifiée contre le dépôt distant comme par `apv gates verify` (`--offline` : avec un avertissement).

La protection de la branche par défaut sur GitHub (`gh api` : PR obligatoire, pas de force-push, administrateurs compris) est dite en une ligne, jamais un refus : absente (avec quoi régler), faible, en place, ou indisponible (dépôt privé en plan gratuit). Chaque règle est `ok`, `REFUSÉ` (avec ce qui manque et quoi faire), `sans objet` ou `DÉROGATION` : l'opérateur a tapé lui-même dans la session « dérogation <règle> <12 premiers caractères du commit au moins> : <raison> » (journal de l'opérateur, [REGLES.md](REGLES.md), section 3). Aucune option ne lève un refus. JSON : `commit`, `target`, `mergeBase`, `ok`, `rules[]` (`rule`, `title`, `status` `ok`, `refused`, `waived` ou `not_applicable`, `detail`, `problems`, `todo`, `waiver`), `warnings`.

Sortie : `0` règles respectées, `1` au moins un refus (ou commit, cible, configuration illisibles), `2` appel incorrect.

## `apv audit merges`

```
apv audit merges [--since <date>] [--target <branche distante>] [--repo <chemin>] [--json]
```

Parcourt l'historique de la branche par défaut (`origin/HEAD`, premier parent) et nomme chaque commit qu'aucune trace signée de `apv stack merge` ou `apv stack batch --merge` n'explique : fusion faite à la main sur GitHub, poussée directe. Une trace (`<répertoire git commun>/apv/merges/`, signée par la clé d'ancrage) lie la PR, sa tête et le commit de fusion ; un commit de fusion est expliqué par la trace de son commit ou de la tête qu'il fusionne (second parent), un squash par celle de son commit. Contrôle a posteriori, qui ne bloque rien : il compense une protection de branche absente (dépôt privé en plan gratuit). Depuis `--since` (défaut : la première fusion tracée, sinon 30 jours). Lancé aussi par `apv status` et en tête du rapport de `apv stack merge`. Sortie : `0` aucun commit hors de l'outil, `1` au moins un ou branche introuvable, `2` appel incorrect.

## `apv review record` et `apv review show`

```
apv review record --commit <sha> --domain <domaine> --reviewer <agent> --report <fichier>
                  --critical <n> --high <n> --medium <n> --low <n> [--capture <largeur>:<thème>:<fichier>]... [--repo <copie>] [--json]
apv review show --commit <sha> [--repo <chemin>] [--json]
```

`record` enregistre une relecture au commit exact, lancé par l'agent relecteur depuis sa copie relue : HEAD au commit, fichiers suivis inchangés (sinon refus `REVIEW_RECORD`, sortie `1`). Domaine et agent : `securite` et `apv:qa-securite`, `fidelite` et `apv:qa-fidelite`, `donnees` et `apv:architecte-donnees`, `rgpd` et `apv:dpo` ; tout autre agent est refusé par l'outil, et le crochet Bash du plugin refuse la commande à tout autre que l'agent du domaine, sous son nom. Rapport complet, 200 octets au moins, qui cite les 12 premiers caractères du commit ; captures `desktop`, `phone` ou `tablet`, `light` ou `dark`, en PNG, JPEG ou WebP d'au moins 1 Ko, jamais la même image deux fois (plusieurs écrans : plusieurs captures par largeur et thème). Le tout est copié sous son empreinte dans `<répertoire git commun>/apv/reviews/<commit>/<domaine>/`, jamais versionné ; la sortie commence par « Enregistrement <id> ». Le crochet `PostToolUse` du plugin scelle aussitôt l'enregistrement (HMAC avec la clé d'ancrage, `<id>.sig`) quand la commande vient de l'agent relecteur du domaine ; une relecture non scellée, ou un fichier modifié ensuite, est inutilisable ([REGLES.md](REGLES.md), section 3). Une relecture avec des constats critiques ou hauts s'enregistre aussi : la fusion de ce commit est alors refusée. `show` affiche la dernière relecture de chaque domaine à ce commit, avec ce qui la rend inutilisable.

## `apv dast run`

```
apv dast run [--repo <copie>] [--out <dossier>] [--commit <ref>] [--wait <durée>] [--json]
```

Scan dynamique de sécurité (ZAP ou l'outil du projet) déclaré dans `review.dast` de `.apv/config.json` ([CONFIGURATION.md](CONFIGURATION.md#revues--review)), lancé par le chef de projet avant les revues : les agents de revue n'ont pas le droit de lancer Docker, et sur le projet pilote le scan prévu n'a jamais tourné (quatre livraisons de suite, septembre 2026). La revue sécurité lit ensuite ses rapports.
- `--repo` : la copie détachée du commit revu (défaut : le dossier courant) ; la configuration y est lue. `--commit` vérifie qu'elle est bien sur ce commit (sha, abrégé ou branche ; sinon `1`, `DAST_COMMIT`).
- `--out` : le dossier des rapports, hors de la copie (refus en `1`, `DAST_OUT`, s'il est dedans : la copie est retirée après les revues) et neuf (refus s'il contient déjà un `summary.json`). Défaut : `<dossier temporaire>/apv-dast/<nom de la copie>-<sha court>-<horodatage>`, jamais à côté du dépôt. Sous `/apv:run`, le dossier de session du chef de projet.
- La commande (`review.dast.command`, argv sans shell) tourne dans la copie, sous le verrou `review.dast.resource` (défaut `dast`, attente `--wait`, défaut 30 min, comme `apv lock run`), bornée par `review.dast.timeoutMs` (défaut 1 h ; puis SIGTERM, SIGKILL 10 s plus tard). Jokers, arguments entiers seulement : `{{reportDir}}`, `{{commit}}`, `{{repo}}`. Variables : celles de `DEFAULT_PASS_ENV` et de `review.dast.passEnv` seulement, plus `APV_DAST_REPORT_DIR`, `APV_DAST_COMMIT`, `APV_DAST_REPO` et `APV_LOCK_HELD`. La commande prépare ce qu'il lui faut (dépendances, build, serveur), écrit ses rapports dans le dossier et arrête ce qu'elle a lancé.
- Sortie de la commande dans `<dossier>/dast.log` ; en dernier, écrit de façon atomique, `<dossier>/summary.json` : `tool`, `version`, `commit`, `repo`, `clean` (aucun fichier suivi modifié), `resource`, `command` (jokers remplacés), `description`, `startedAt`, `finishedAt`, `durationMs`, `status` (`passed`, `failed`, `timed_out`, `lock_timeout`), `exitCode`, `timeoutMs`, `log`, `files` (fichiers du dossier, 200 au plus). Un scan lancé en arrière-plan s'attend par `apv wait --file <dossier>/summary.json`.
- **Copie préparée par l'outil** (3.0.0-alpha.15) : une copie qui a un `package-lock.json` reçoit `npm ci --ignore-scripts --no-audit --no-fund` (aucun script de paquet : ils tourneraient hors du verrou), lancé dans la copie avant la commande et avant le verrou (sortie dans `dast.log`, borné par `review.dast.timeoutMs`, variables de la commande, jamais celles du fichier d'environnement, plus `HOME` et `USERPROFILE` pour le cache de npm), sauf si `node_modules/.apv-dast-install` porte l'empreinte de ce même `package-lock.json` (écrite après une installation réussie : une installation interrompue laisse un `node_modules` partiel, jamais le marqueur ; un `node_modules` installé à la main est réinstallé). Échec : statut `failed` ; délai dépassé : `timed_out` ; dans les deux cas le scan ne tourne pas. Un projet dont le build exige les scripts de paquets les lance dans sa propre commande. Autre gestionnaire de paquets (pnpm, yarn) : rien n'est installé, à la charge de la commande. `summary.json` porte `install` (`status` `done`, `skipped`, `failed` ou `timed_out`, `reason`, `command`, `exitCode`, `durationMs`).
- **Fichier d'environnement** (`review.dast.envFile`, 3.0.0-alpha.15) : lignes `KEY=valeur` (`export` admis, guillemets retirés, `#` commentaires) chargées dans l'environnement de la commande ; `~` est le dossier personnel (`HOME`), un chemin relatif part de la copie. Refus `DAST_ENV`, sortie `1`, avant toute écriture et tout lancement : fichier absent ou illisible, ligne illisible, variable réservée (`APV_*`, `PATH`, `NODE_OPTIONS`, `NODE_PATH`, `HOME`, `LD_*`, `DYLD_*`), ou valeur qui ressemble à une adresse hors bouclage. **Liste d'autorisation** : chaque mot de la valeur est lu (liste séparée par des virgules, objet JSON, chaîne libpq `host=… port=…`) ; une URL (`schéma://`, `//`), `utilisateur@hôte`, `host=`, une adresse IPv4 ou IPv6, un nom d'hôte avec un point (lettres accentuées et point final compris) doivent être en bouclage ; dans une variable d'adresse (`*HOST*`, `*URL*`, `*URI*`, `*ADDR*`, `*ENDPOINT*`, `*SERVER*`, `*DSN*`, `*DOMAIN*`, `*ORIGIN*`, `*PROXY*`, `*TARGET*`, `*SITE*`, `*BASE*`, `*API*`, `*DATABASE*`, `DB` ; sauf `*_KEY`, `*_TOKEN`, `*_SECRET`, `*_PASSWORD`, `*_USER`, `*_NAME`, `*_ID`, `*_PORT`...) ou après `host`, un nom sans point (`prodserver`) et un nombre au-delà d'un port aussi. Les `%XX` sont décodés avant la lecture ; tout préfixe `schéma:` est lu comme une URL (schémas imbriqués `jdbc:postgresql:`, sans `//`, avec `/` ou `\\`) ; `hôte:port` exige un hôte en bouclage, avec ou sans point (`prodserver:8080` refusé). Seuls `localhost`, `*.localhost`, `127.0.0.0/8` et `::1` sont admis : le scan ne vise jamais la production. Une adresse e-mail sur un domaine réservé aux exemples (`demo@example.org`, `*.test`) est un compte de test, admis ; toute autre adresse e-mail est refusée. Le refus nomme les clés et le genre d'adresse, jamais les valeurs. `summary.json` porte `envFile` (`file`, `loaded`, `variables` : leur nombre ; jamais les valeurs), `null` sans `envFile`.

Sortie : `0` scan terminé à `0`, `1` scan en échec, arrêté au délai, verrou non obtenu, installation en échec, fichier d'environnement refusé (`DAST_ENV`), rien de déclaré (`DAST_NONE`) ou refus, `2` appel incorrect.

## `apv design`

```
apv design register <fichier.html> --name <nom> --quote "<mots de l'opérateur>"
                    [--title "<titre>"] [--screens a,b] [--artifact <url>] [--scope <motif,motif>]
                    [--group <dossier>] [--repo <chemin>] [--json]
apv design list [--screen <écran>] [--repo <chemin>] [--json]
apv design check [--repo <chemin>] [--json]
apv design organize [--dry-run] [--repo <chemin>] [--json]
```

Maquettes validées par l'opérateur, référence absolue des implementers et de la revue de fidélité. Méthode complète : [DESIGN.md](DESIGN.md).

- `register` verse une maquette que l'opérateur vient de valider :
  1. copie le fichier vers `docs/design/<nom>-validee.html` (dossier : `design.dir` de `.apv/config.json`), ou vers `docs/design/<groupe>/<nom>-validee.html` quand la configuration déclare des groupes (ci-dessous) ;
  2. calcule son sha256 ;
  3. inscrit au registre, par l'API de mise à jour du registre (comme `apv ledger apply`), la décision `maquette-<nom>-validee` : `confirmed`, source `operator`, `sourceQuote` = la citation, `enforcement` `product`, valeur avec le chemin et l'empreinte (et les écrans, l'adresse de l'artefact) ;
  4. ajoute à `.gitattributes` (créé ou complété) la ligne `<dossier>/**/*.html -whitespace` (racine du dossier et sous-dossiers des groupes) quand Git ne l'applique pas déjà au dossier et à chaque groupe (`git check-attr whitespace`) ; l'ancienne ligne `<dossier>/*.html -whitespace` suffit sans groupes, et avec des groupes elle est remplacée à sa place, ce que la sortie dit (« remplacée par ») : une maquette est figée par son empreinte, ses espaces de fin de ligne ne peuvent pas être nettoyés, et sans cette ligne `git diff --check` (contrôle `diff-check`, CI des projets) échoue (projet pilote, 25 septembre 2026 : ligne ajoutée à la main) ;
  5. affiche les fichiers à commiter (maquette, registre JSON et Markdown, `.gitattributes` s'il a changé). Rien n'est commité.

  **Groupe.** Le premier groupe de `design.groups` dont un motif reconnaît le nom donne le sous-dossier, sinon `design.defaultGroup`, sinon la racine de `design.dir`. `--group <dossier>` choisit un groupe déclaré (`design.groups` ou `design.defaultGroup` ; sinon refus `DESIGN_GROUP`, rien n'est écrit) ; ce choix est noté dans la décision (`Groupe : <dossier>.`), puis gardé par les versements suivants et suivi par `check` et `organize`. Sans `--group`, un nouveau versement d'une maquette déjà versée garde son groupe actuel (groupe noté, ou dossier de son fichier s'il est la racine ou un groupe déclaré) : `register` ne la déplace pas, `organize` le fait. Exception : un fichier dans un dossier qui n'est plus un groupe déclaré (groupe retiré de la configuration, ancien `design.dir`) ; la nouvelle version va alors dans le groupe des motifs. Dans ce cas, comme quand `--group` change le dossier, l'ancien fichier reste en place et la sortie le nomme (à retirer par `git rm`). Le groupe `brouillons` est réservé aux brouillons de la boucle. Une cible qui passe par un lien symbolique (dossier des maquettes, sous-dossier de groupe, fichier) et une source qui est un lien sont refusées (`DESIGN_LINK`) : l'écriture pourrait sortir du dépôt ; les fichiers enregistrés se lisent par leur chemin réel, un lien qui sort du dépôt vaut fichier absent. Un titre ou un nom d'écran qui contient « Groupe : », « Écrans : », « Artefact : » ou « fichier … sha256 » est refusé (`DESIGN_TITLE`, `DESIGN_SCREENS`) : ces mentions ne se lisent qu'après le chemin et l'empreinte. Sans `design.groups` ni `design.defaultGroup`, rien ne change.

  `--scope <motif,motif>` donne un périmètre à la décision (`scope.paths`, syntaxe des chemins autorisés) : seules les specs dont les tâches peuvent toucher ces chemins doivent la couvrir ([`apv spec validate`](#apv-spec-validate)). Sans `--scope`, le périmètre de l'enregistrement actif est gardé ; un nouveau périmètre sur le même fichier fait un nouvel enregistrement.

  La citation est obligatoire : sans les mots de l'opérateur, rien n'est versé (le pipeline n'invente jamais une approbation). Une validation avec réserve (« je valide sauf … ») est refusée. Le registre doit être commité avant (`LEDGER_DIRTY` sinon) ; en cas d'échec, le fichier copié est retiré. Le nom : minuscules, chiffres et tirets, 50 caractères au plus, sans le mot `validee`. Verser de nouveau une maquette déjà versée ajoute `maquette-<nom>-validee-v2` (puis `-v3`…), qui remplace l'ancienne décision (`supersedes`) ; un contenu identique à la version enregistrée ne change rien.
- `list` affiche les maquettes validées du registre de l'arbre de travail : nom, groupe (colonne affichée quand la configuration déclare des groupes, « (à ranger) » pour une maquette hors du dossier de son groupe), décision, fichier, empreinte, écrans et état du fichier : `ok`, `MODIFIÉE` (empreinte différente), `ABSENTE`, ou `sans empreinte` pour une décision écrite avant l'outil (projet pilote). `--screen` filtre sur un écran (nom ou écran déclaré, sans tenir compte de la casse ni des accents).
- `check` sort en `1` si un fichier de maquette validée a changé ou disparu sans nouvel enregistrement ; les décisions sans empreinte sont listées comme non vérifiables. Il signale aussi l'absence de la ligne de `.gitattributes` (projet avec des maquettes validées ou un dossier de maquettes) : « Attention » si aucune maquette ne porte d'espace de fin de ligne, « Erreur » et sortie `1` sinon, puisque `git diff --check` échoue alors. Une maquette hors du dossier de son groupe est signalée (« Attention », sans échec) : `organize` la range. À déclarer comme contrôle (`gates`) dans les projets qui ont des maquettes.
- `organize` range dans le dossier de leur groupe les maquettes validées (décision confirmée avec fichier et empreinte) qui n'y sont pas : `git mv` quand Git suit le fichier, déplacement simple sinon ; le nom du fichier est gardé. Il réécrit le chemin dans la valeur de **leur** décision, en place, dans le registre JSON et sa vue Markdown régénérée : pas de nouvelle version de la décision, le contenu validé n'a pas changé (empreinte vérifiée après le déplacement). Il ne déplace que des fichiers HTML (`.html`, `.htm`) réguliers sous `design.dir`, jamais à travers un lien symbolique (source ou cible). Tout ou rien : une maquette modifiée ou absente depuis sa validation, hors de `design.dir`, non HTML ou liée, une cible qui existe déjà (fichier sur le disque ou suivi par Git) ou qui passe par un lien, ou deux maquettes vers la même cible bloquent tout déplacement (sortie `1`, motif de chacune) ; le registre doit être commité (`LEDGER_DIRTY` sinon) ; en cas d'échec en cours de route, les déplacements sont annulés (ceux qui n'ont pas pu l'être sont nommés), les dossiers créés retirés s'ils sont vides et le registre remis comme avant (`DESIGN_ORGANIZE`). Aucun autre fichier n'est modifié (ni `.gitattributes`, dont l'absence de la ligne est signalée) : la sortie liste les fichiers suivis qui citent encore un ancien chemin (`git grep`), à mettre à jour par le chef de projet. `--dry-run` montre le plan et ces fichiers sans rien toucher. Rien n'est commité : la commande affiche `git add` et `git commit` à lancer. Les décisions sans empreinte ne sont jamais déplacées.

Configuration (facultative) :

```json
{
  "design": {
    "dir": "docs/design",
    "groups": [
      { "dir": "admin", "match": ["admin-*", "console"] }
    ],
    "defaultGroup": "produit"
  }
}
```

`groups` (liste ordonnée, facultative) : `dir`, sous-dossier de `design.dir`, et `match`, motifs (`*`, `?`) sur le nom de la maquette, sans `/`. `defaultGroup` (facultatif) : sous-dossier des noms qu'aucun motif ne reconnaît ; absent, la racine de `design.dir`. Validation stricte (`CONFIG`) : sous-dossier relatif sans `..` ni espace (lettres, chiffres, `.`, `_`, `-`, segments séparés par `/`), jamais sous `brouillons/` (réservé aux brouillons), motifs non vides et valides, jamais deux groupes au même dossier, `groups` non vide s'il est présent. Méthode : [DESIGN.md](DESIGN.md#6-configuration).

Sortie : `0` succès (maquettes intactes pour `check`, rangement fait ou plan sans blocage pour `organize`), `1` refus, dérive ou rangement bloqué, `2` appel incorrect (citation ou nom manquant, `--group` hors de `register`, `--dry-run` hors d'`organize`). En JSON, `register` rend `decisionId`, `supersedes`, `target`, `group` (null : racine), `previousFile`, `sha256`, `ledgerFile`, `toCommit`, `unchanged`, `attributes` (`file`, `line`, `status` : `present`, `added`, `replaced` avec `previous`, l'ancienne ligne, ou `ineffective` quand un autre fichier d'attributs la contredit) ; `list` rend `mockups` (avec `group`, `folder`, `placed`, `recordedGroup`) ; `check` rend `ok`, `checked`, `broken`, `legacy`, `misplaced` (`decisionId`, `file`, `group`, `folder`), `attributes` (`status` : `present`, `missing` ou `not-applicable` ; `previous` quand l'ancienne ligne ne couvre pas les groupes ; `whitespace`, maquettes aux espaces de fin de ligne ; `blocking`) ; `organize` rend `ok`, `dryRun`, `applied`, `moves` (`decisionId`, `from`, `to`, `group`, `sha256`, `tracked`), `blocked` (`decisionId`, `file`, `to`, `reason`), `legacy`, `ledgerFile`, `ledgerMarkdown`, `references` (`path`, `files`), `toAdd`, `toCommit`, `attributes`.

## `apv structure check`

```
apv structure check [--base <ref>] [--path <dossier>]... [--all] [--repo <chemin>] [--json]
```

Analyse déterministe de l'arborescence ([STRUCTURE.md](STRUCTURE.md)) : les fichiers de code suivis par Git (`git ls-files`, sans `--base`), jamais les fichiers ignorés (TypeScript, JavaScript, Svelte, Vue, Python, Go, Rust...). Exclusions par défaut : `node_modules/` partout ; `dist/`, `build/`, `coverage/`, `vendor/` et les dossiers qui commencent par un point (`.github`, `.claude`...) seulement à la racine du dépôt ou d'un paquet, et seulement pour l'existant : avec `--base`, ce que le changement crée est toujours analysé. Chaque dossier est examiné pour ses fichiers directs ; un fichier et ses compagnons (`x.ts`, `x.svelte.ts`, `x.d.ts`) comptent pour un, ses tests (`x.test.ts`, `x.spec.ts`, `x.fixture.ts`, dossiers `tests/`, `__tests__/`, `e2e/`) sont comptés à part et le suivent quand il est déplacé.

| Constat | Quand | Proposition |
|---|---|---|
| `flat-folder` | plus de `maxFlatFiles` fichiers de code directement dans le dossier (12 par défaut) | ranger par domaine selon le plan : règles de noms d'abord, puis **découpage par usage**, même sans préfixe commun (graphe des imports de la carte du code : qui importe quoi, routes et dossiers de composants qui s'en servent, fichiers importés ensemble, mots des noms et des exports) ; socle gardé à la racine ; chaque sous-dossier nommé par le vocabulaire du projet (dossiers, domaines ; une route seulement pour un dossier de routes ; jamais un synonyme d'un dossier voisin), jamais d'après un de ses fichiers, avec ses raisons et la convention de la pile suivie ; sans nom qui s'impose, groupe « à nommer par l'opérateur » (`groups`, `core`, `unnamed` en JSON) ; dossier de primitives (`components/ui`) jamais découpé (`primitives`) |
| `repeated-prefix` | plusieurs fichiers commencent par le même mot de domaine, singulier et pluriel rapprochés (`application-actions.ts`, `applications-repository.ts`) : deux fichiers qui ont un rôle, trois fichiers, ou un mot qui est déjà le nom d'un dossier du projet ou un domaine déclaré | `<domaine>/` avec des noms sans préfixe (`applications/actions.ts`) ; des composants (`QuickAddDialog.svelte`) gardent leur nom et ne sont regroupés, par trois au moins, que dans un dossier trop plein |
| `mixed-roles` | au moins trois fichiers à rôle, deux rôles et deux domaines côte à côte (`*-actions`, `*-repository`, `*-client`, utilitaires HTTP ou d'authentification) | un dossier par domaine (`settings/repository.ts`), les utilitaires transverses regroupés par rôle (`http/`, `auth/`) sans changer leur nom |
| `stray-file` | un fichier dont le nom commence par celui d'un dossier voisin (`email-templates.ts` à côté de `email/`) | le ranger dans ce dossier (`email/templates.ts`) |

Les rôles se reconnaissent par suffixe (`-actions`, `-action`, `-repository`, `-repo`, `-client`, `-service`, `-controller`, `-handler`, `-middleware`, `-utils`, `-helpers`) ou par un mot du nom (`http`, `headers`, `cookie`, `cors`, `csrf`, `request`, `response`, `body`, `ip` pour le rôle `http` ; `auth`, `oauth`, `login`, `logout`, `sign-in`, `sign-out`, `sign-up`, `session`, `password` pour `auth`). Dans un dossier à rôles mêlés, des noms composés qui s'enchaînent sont un même sujet : `account-deletion.ts`, `deletion-purge.ts` et `purge-schedule.ts` vont ensemble dans `account/`. Un déplacement n'écrase jamais un fichier suivi : le nom est gardé, sinon le fichier reste en place. Les fichiers qu'aucune règle ne place sont listés « restent en place, à décider avec l'opérateur ».

Le plan (`ancien -> nouveau`) n'est **jamais appliqué** par l'outil : il se valide avec l'opérateur, puis se fait par `git mv`, imports, configuration des outils et documentation mis à jour, sans changement de comportement (compétence `apv:structure`).

**`--base <ref>`** (le contrôle `structure` écrit par `apv init` et `apv onboard` passe `{{baseSha}}`) : comparaison avec la base commune de `<ref>` et HEAD, arbre de travail compris (fichiers non suivis non ignorés), configuration lue **à la base** (un changement de la section `structure` est signalé, bloquant quand le changement touche aussi du code) :

| Constat | Bloquant (nouveau) | Existant (sans bloquer) |
|---|---|---|
| `flat-growth` | tout fichier de code créé ou déplacé (tests à part) dans un dossier qui a plus de `maxFlatFiles` modules (déjà à plat, ou qu'il y fait passer), sauf un compagnon connu d'un module présent (tests, `.svelte.ts`, `.server.ts`, `.client.ts`, `.d.ts`) ; un nom de fichier généré seulement s'il est déclaré dans `reuse.generated` de la base ; le message nomme le sous-dossier où le mettre, d'après le découpage proposé | le dossier à plat, en `flat-folder` |
| `architecture-map` | dossier de premier ou deuxième niveau (et deux niveaux sous les ancres de la pile), route principale ou point d'entrée ajouté sans rôle dans le bloc « Rôles » (clé exacte ou motif déjà présent à la base ; trois mots au moins) ; marqueur dupliqué ; lien de la carte cassé par le changement ; carte supprimée | ce qui existait sans rôle, lien déjà cassé |
| `coverage` | lien symbolique ou sous-module ajouté par le changement, sauf déclaré dans `structure.ignore` de la base | |
| constat d'analyse de gravité `error` | sur un fichier créé ou déplacé par le changement | les autres |

Toujours accepté : un renommage dans le même dossier (similarité de Git, même réécrit), un fichier qui descend d'un dossier à plat dans l'un de ses sous-dossiers (rangement) ; le sous-dossier ainsi créé reçoit un rôle proposé, en avertissement. Sans `--base`, rien n'est comparé et la carte est signalée sans bloquer.

- `--path` limite les constats à un dossier et à ses sous-dossiers (chemin relatif à la racine du dépôt, répétable) : l'architecte l'utilise sur les dossiers que touche son plan.
- `--all` liste tous les constats existants de la comparaison (par défaut : 10).
- Configuration facultative, section `structure` de `.apv/config.json` : [CONFIGURATION.md](CONFIGURATION.md#arborescence--structure).

Sortie : `0` aucun constat bloquant (sans `--base` : aucun constat de gravité `error` ; par défaut l'analyse est en `warning`), `1` au moins un, configuration invalide ou base introuvable, `2` appel incorrect (sous-commande, option, `--path` hors du dépôt, `--base` vide). En JSON : `ok`, `analyzedFiles`, `maxFlatFiles`, `folders` (dossier, fichiers de code, tests, compagnons, fichiers non placés), `findings` (`code`, `severity`, `folder`, `files`, `proposal`, `moves`, `isNew`, `blocking` ; pour `flat-folder` : `groups` avec `dir`, `members`, `existing`, `reasons`, `conventions`, `naming`, et `core`), `plan` (tous les déplacements, tests et compagnons compris), `base`, `changes` (`code`, `severity`, `isNew`, `blocking`, `path`, `message`), `architectureMap` (`path`, `exists`, `profile`, `items`, `described`), `usageError`, `repo`, `paths`.

```
apv map [--check] [--repo <chemin>] [--json]
```

Écrit la carte du code, `.apv/code-map.md` (ou `map.file`), depuis l'inventaire du dépôt ([REUSE.md](REUSE.md#1-la-carte-du-code-apv-map)) : composants partagés (rôle, props, variantes, où ils sont utilisés), modules partagés (exports, utilisateurs), routes, et ce qui est propre à une fonctionnalité avec les doublons possibles, et une section « Dossiers » (chemin de la carte de l'architecture, dossiers à plat et sous-dossiers proposés pour chacun). Sortie : `0` écrite ou à jour, `1` absente ou périmée (`--check`), chemin refusé (`MAP_PATH`) ou configuration invalide, `2` appel incorrect. ## `apv quota`

```
apv quota [--repo <chemin>] [--no-log] [--json]
```

Relève l'usage avec `claude -p "/usage" --setting-sources ''` (délai de 150 s) et lit deux lignes :

```
Current session: 21% used · resets Sep 23, 2:30am (Europe/Paris)
Current week (all models): 7% used · resets Sep 25, 7pm (Europe/Paris)
```

Le niveau se calcule sur la plus haute des deux fenêtres, la fenêtre la plus contraignante (`binding` : `session` ou `week`, la semaine en cas d'égalité), nommée dans la sortie (spécification, section 9) :

| Pourcentage | Niveau | Consigne |
|---|---|---|
| moins de 70 % | `ok` | continuer |
| 70 % | `slow_down` | ralentir, doser les vagues |
| 85 % | `finish_only` | finir les tâches en cours sans en lancer de nouvelles |
| 95 % | `save_now` | sauvegarder (commits « wip », push, notes de reprise) et prévenir l'opérateur |
| illisible | `unknown` | le relevé a échoué ; la sortie de la commande est affichée |

La sortie dit aussi combien d'exécutions `/apv:run` peuvent tourner en même temps : au niveau `ok`, autant que de piles de test libres ; à `slow_down`, une de plus au maximum ; au-delà, aucune nouvelle, celles en cours se terminent.

Chaque relevé est ajouté à `.apv/state/quota.log` (un objet JSON par ligne : `at`, `session`, `week`, `percent`, `level`, `binding`), sauf avec `--no-log` ; le hook de démarrage de session lit la dernière ligne. `apv quota` crée ou complète aussi `.apv/.gitignore` (`state/*.log`, `state/task.json`, `state/preview.json`, `receipts/`) pour que ces fichiers machine ne soient jamais commités. La variable d'environnement `APV_CLAUDE_BIN` remplace l'exécutable `claude` (tests, installation particulière).

Sortie : `0` relevé lu, `1` relevé illisible, `2` appel incorrect.

## `apv preview`

```
apv preview update [branche] [--wait 30m] [--repo <chemin>] [--json]
apv preview status [--repo <chemin>] [--json]
apv preview stop [--wait 30m] [--repo <chemin>] [--json]
apv preview logs [--lines 50] [--update] [--repo <chemin>]
```

Aperçu vivant du projet (spécification, section 12), décrit par la section `preview` de `.apv/config.json` : dossier de la copie, fichier d'environnement, étapes `install`, `migrate`, `build`, `seed`, commande et port du serveur, contrôle de santé, adresse annoncée.

- `update` prend le verrou du projet (`preview:<projet>`), arrête le serveur d'aperçu, copie la branche (`preview.branch`, sinon `main`) par `git archive` dans un dossier neuf, lance les étapes, démarre le serveur détaché (journal `.apv/state/preview.log`, état `.apv/state/preview.json`) et attend sa réponse. Il affiche « aperçu prêt : <adresse> (branche X, commit abc1234) » et les commits arrivés depuis l'aperçu précédent. Un échec nomme l'étape et donne le chemin du journal ; aucun serveur ne reste.
- `status` : en marche (groupe de processus vivant et contrôle de santé réussi), adresse, branche, commit, durée, dernier échec.
- `stop` : arrête le serveur (tout son groupe de processus).
- `logs` : dernières lignes du journal du serveur, ou de la dernière mise à jour avec `--update`.

Chaque étape a un délai maximal (`timeoutSec`, 900 s par défaut, réglable par étape) ; au-delà, tout son groupe de processus est arrêté. Les valeurs du fichier d'environnement sont masquées dans le journal de mise à jour et les sorties ; le journal du serveur, écrit par le serveur lui-même, n'est masqué qu'à l'affichage (`logs`) et reste en droits 600. Un port occupé par un processus qui n'est pas l'aperçu n'est jamais libéré de force : `update` refuse. Configuration, forme des commandes (chaîne pour `sh -c`, tableau sans shell), masquage, sûreté et exemple Supabase : [PREVIEW.md](PREVIEW.md).

Sortie : `0` succès (pour `status` : aperçu en marche), `1` échec ou aperçu arrêté, `2` appel incorrect.

## `apv web audit`

```
apv web audit (--url <origine> | --production | --preview) [--page <chemin>]... [--runs N]
              [--form-factor mobile|desktop] [--base <ref>] [--readiness-only] [--wait <durée>]
              [--repo <chemin>] [--json]
```

Qualité mesurable des pages publiques d'un site (spécification, section 20), déclarée par la section `web` de `.apv/config.json` ([CONFIGURATION.md](CONFIGURATION.md#qualité-web--web)). Constat du projet pilote (28 septembre 2026) : Lighthouse lancé à la main dans DevTools a rendu un faux 0 partout (`NO_FCP`, onglet en arrière-plan), quand une mesure sans interface donnait 89/100/100/100/100 ; la qualité se mesure donc par la pipeline, de façon reproductible.

**Cible** (une et une seule) :
- `--url <origine>` : un site en ligne, lu seulement (Lighthouse charge les pages comme un navigateur ; les contrôles de préparation ne lisent que cette origine). Le chemin de l'adresse est ignoré : les pages sont celles de `web.pages`.
- `--production` : l'origine `web.productionUrl` ; c'est l'étape d'après déploiement, à lancer une fois une fusion déployée en ligne.
- `--preview` : l'aperçu local d'APV (section `preview`, [PREVIEW.md](PREVIEW.md)) sur le commit HEAD, sous le verrou `preview:<projet>` (`--wait`, 30 min par défaut), pris **après** la file des suites complètes (la construction de l'aperçu comprise : aucune suite ne démarre pendant qu'il se construit et se mesure) ; un signal annule l'attente du verrou et la construction (groupe de processus de l'étape arrêté). S'il sert déjà ce commit, il est réutilisé et laissé comme il était ; sinon il est construit (copie du commit, étapes, serveur), audité, puis **arrêté à la fin**, quelle que soit l'issue (interruption comprise) : aucun serveur ne reste. Un aperçu en marche sur un autre commit est remplacé puis arrêté (la sortie le dit, avec la commande qui le relance). L'arbre de travail non commité n'est pas audité (note).
- `--base <ref>` (avec `--preview` seulement, pour le contrôle d'une PR) : l'audit est **requis par défaut**, dès qu'un fichier changé entre la base commune de `<ref>` et de HEAD, et HEAD, est hors de la liste des fichiers sans effet web (`web.neutralPaths`, par défaut `tests/**`, `e2e/**`, `.github/**`, `*.md` à la racine seulement et `docs/**`) ; `.apv/config.json`, tout `package.json`, les fichiers de verrouillage, les contenus `.md`, `.mdx`, `.svx` et `.html` sous un dossier `src/`, `content/`, `static/` ou `public/` (`src/routes/blog/+page.md`, `src/content/post.md`), le HTML de `docs/` (site publié depuis `docs/`) et les fichiers de `web.paths` comptent toujours, même dans cette liste. Sur la branche principale elle-même (après la fusion), `--preview --base origin/main` n'a rien à comparer (sortie `2`) : y utiliser `apv web audit --production` ou `--url <origine>`. Seul un changement limité à des fichiers sans effet web rend « audit web non requis », sortie `0`, rien n'est construit ni mesuré (`skipped: true` en JSON). `<ref>` introuvable, sans base commune, ou dont la base commune est HEAD lui-même (HEAD égal à `<ref>` ou en amont : rien à comparer) : appel incorrect, sortie `2`. Dans une suite complète (`APV_SUITE_RUN`), `--preview` sans `--base` est un appel incorrect : la preuve doit dire depuis quelle base l'audit était requis. `<ref>` est résolu par sa ref complète (3.0.0-alpha.8) : un nom qui désigne à la fois une branche de suivi distante et une branche locale ou un tag (`origin/main`) est ambigu, refusé comme une référence introuvable ; `refs/remotes/origin/main`, un identifiant de commit ou une expression de révision (`HEAD~1`) sont pris tels quels.
- **Relevé pour le reçu** : lancé par `apv gates run`, l'audit écrit dans le fichier que nomme `APV_WEB_RECORD` (posé par `apv gates run`, hors empreinte d'environnement) ce qu'il a décidé : requis ou non, base commune, référence, fichiers à effet web (50 au plus), audit fait (`auditId`) et son issue ; le reçu du contrôle le porte (`web`). `apv gates verify` recalcule « non requis » depuis le commit (voir plus haut) : un reçu « non requis » ne prouve rien si le recalcul dit requis.

**Mesure** :
- Lighthouse est la version épinglée `web.lighthouse` (13.5.0 par défaut) : la dépendance du projet si Node résout `lighthouse` depuis le dépôt vers le vrai paquet (nommé `lighthouse`, jamais un alias `npm:autre`) exactement à cette version, sinon `npx -y lighthouse@<version>` ; lancé sans shell, dans un dossier temporaire (aussi son `TMPDIR` : le profil de Chrome et ses fichiers partent avec lui), borné par `web.timeoutMs` (180 s par passage, puis tout son groupe de processus est arrêté). Catégories `web.categories` (performance, accessibility, best-practices, seo, agentic-browsing ; la performance tourne toujours, car le statut du document et les métriques qui rendent une mesure valide en viennent, mais seules les catégories déclarées sont jugées), langue `web.locale`, `--chrome-flags` de `web.chromeFlags` (`--headless=new` ; refusées : les options qui lancent un autre programme, ouvrent le navigateur au réseau ou détournent son trafic, comme `--renderer-cmd-prefix`, `--remote-debugging-address`, `--load-extension`, `--user-data-dir`, `--proxy-server`), bureau par `--preset=desktop`.
- Chrome : `web.chrome`, sinon `CHROME_PATH`, sinon le Chromium le plus récent de Playwright (`PLAYWRIGHT_BROWSERS_PATH`, `~/.cache/ms-playwright`), sinon Chrome ou Chromium du système ; aucun : refus `WEB_CHROME`. Chaque passage marque ses processus (`APV_WEB_AUDIT`) : un Chrome resté en vie après un passage est arrêté (jamais la session ni un outil protégé), et tous le sont avant que la file des suites soit libérée.
- Pour chaque page (`web.pages`, ou `--page`) et chaque appareil (`web.formFactors`, ou `--form-factor`) : `web.runs` passages **valides** (3 par défaut, `--runs`). Un passage est **invalide**, jamais compté, s'il a une erreur Lighthouse (`runtimeError`, dont `NO_FCP`), un avertissement de mesure (`runWarnings`), un document servi avec un autre statut que 200, une redirection hors de la page demandée, un score de catégorie ou une métrique absents, une autre version de Lighthouse ou un autre appareil que ceux demandés, ou s'il n'a pas produit de rapport (délai, erreur) ; il est écarté avec sa raison et refait, au plus `runs` fois de plus. Moins de `runs` passages valides : « mesure invalide », sortie `1`.
- Médiane par catégorie (score sur 100) et par métrique (FCP, LCP, TBT et SI en millisecondes, CLS sans unité) ; le passage le plus proche des médianes représente la page : son rapport JSON et HTML complet est gardé, ses trois principales opportunités ou diagnostics (audits en échec des catégories mesurées, métriques exclues, classés par économie estimée la plus grande, puis points de catégorie perdus, puis octets) sont affichés.
- **Seuils** (`web.thresholds`) : une catégorie sous son minimum ou une métrique au-dessus de son maximum est un seuil manqué, marqué `!` dans le tableau et détaillé sous lui (« performance 89 < 90 ; LCP 2,6 s > 2,5 s ») avec les opportunités.
- **File et charge** : la mesure prend la file des suites complètes (`suite.queue`, même verrou à bail que `apv gates run` ; depuis 3.0.0-alpha.20, toutes ses places : la file entière, chaque place numérotée de `slots` et la place de chaque pile déclarée, pour qu'aucune suite ne tourne à côté), sauf quand elle tourne déjà dans une suite complète (`APV_SUITE_RUN` : la suite tient la file) ou avec `web.queue` à `false` ; puis, avant **chaque** passage, elle attend que la charge moyenne sur 1 minute passe sous `web.load.max` (défaut : `suite.queue.maxLoad`, sinon la moitié des processeurs) ; `web.load.waitMs` (30 min) borne le temps passé **à attendre** la charge, cumulé sur l'audit (le temps de mesure ne le consomme pas) ; au-delà, la mesure s'arrête : refus `WEB_LOAD`, sortie `1` (`load.refused`), les mesures valides déjà faites restent au rapport et les pages non mesurées sont marquées « non mesuré » (une mesure sous charge fausse la performance ; contrairement à une suite, elle ne démarre jamais « quand même »). La charge au départ et la plus haute relevée sont dans la sortie et le résumé.

**Préparation à la recherche et aux IA** (sans réseau tiers : seulement l'origine auditée ; redirections suivies à la main, sur la même origine seulement, 5 au plus, une redirection ailleurs jamais suivie mais signalée ; corps lus en flux, 5 Mio au plus, décodés selon leur `charset`, BOM retiré ; un sitemap déclaré sur une autre origine, par exemple celui de la production dans l'aperçu, est lu sur l'origine auditée, note à l'appui) : chaque contrôle de `web.checks` vaut `refuse` (sortie `1`), `warn` (signalé) ou `off`.
- `status` : chaque page servie avec 200, sans redirection (une redirection sur l'origine est suivie pour nommer l'adresse finale, et refusée) (HTML du serveur lu tel quel : ce que lisent les robots qui n'exécutent pas de script) ;
- `robots` : `/robots.txt` accessible ; aucune page interdite aux robots de `web.robotsAgents` (lecture de Google : jeton de produit du robot, groupes d'un même robot fusionnés, sinon les groupes `*` ; règle la plus longue, `Allow` à égalité, `*` et `$` ; chemins comparés encodés, échappements en majuscules, RFC 9309) ; aucune page marquée `noindex` (balise meta `robots` ou en-tête `X-Robots-Tag`) ;
- `sitemap` : un sitemap déclaré dans robots.txt (sinon `/sitemap.xml` est lu et l'absence de déclaration signalée), lisible (`<urlset>`, index suivis, 20 au plus), qui liste chaque page (comparaison par chemin exact : `/faq/` n'est pas `/faq`) ;
- `canonical` : une seule balise, adresse absolue, vers la page elle-même (une autre origine, celle de la production vue depuis l'aperçu, est notée sans refus) ;
- `title`, `description` : présents, non vides, un seul par page, **uniques entre les pages** auditées ;
- `lang` : attribut `lang` valide sur `<html>` ;
- `jsonLd` : chaque bloc `application/ld+json` est du JSON valide, avec `@context` et `@type` (nœuds de `@graph` compris) ; aucune donnée structurée n'est seulement notée ;
- `hreflang` (si la page en déclare) : valeurs valides, sans double, adresses absolues, la page se cite elle-même, réciprocité entre pages auditées ;
- `llmsTxt` (`off` par défaut ; `warn` ou `refuse` quand le projet en attend un) : `/llms.txt` servi avec 200, en texte, commençant par un titre Markdown.
`--readiness-only` ne lance que ces contrôles (ni navigateur, ni file, ni charge).

**Rapports** : `web.reportsDir` (`.apv/web/` par défaut) : relatif, dans le dépôt (liens symboliques résolus), sans aucun fichier suivi par Git (sinon refus `WEB_REPORTS` avant toute écriture) ; il reçoit un dossier par audit (`<AAAAMMJJ-HHMMSS>-url|apercu`, heure UTC) avec `summary.json` et, par page et appareil, `<page>.<appareil>.report.json` et `.report.html` du passage médian (`accueil` pour `/`) ; le dossier porte son propre `.gitignore` (`*`) : jamais versionné, l'arbre reste propre pour la suite complète. Les `web.keepAudits` audits les plus récents sont gardés (10) ; la rétention ne retire que des dossiers au nom d'un audit qui contiennent un `summary.json`, jamais autre chose.

**Comme contrôle** (`gates`) : par exemple `{ "id": "web", "stage": "full", "command": ["apv", "web", "audit", "--preview", "--base", "origin/main"], "timeoutMs": 2400000, "passEnv": ["HOME", "CHROME_PATH"] }` : reçu, empreinte et `apv gates verify` comme tout contrôle ; « non requis » passe (sortie `0`) quand la PR ne change que des fichiers sans effet web, et `apv gates verify` le recalcule. Ne pas le déclarer `readOnly` : il écrit ses rapports, et l'ordonnanceur lui laisse ainsi la copie pour lui seul (aucun autre contrôle de la suite ne tourne pendant la mesure). Variables : `HOME` (cache de `npx`), `CHROME_PATH` si besoin, et celles du fichier d'environnement de l'aperçu s'il en dépend.

Sortie texte : en-tête (origine, commit, Lighthouse, navigateur, passages), file et charge, tableau `page`, `appareil`, `perf`, `a11y`, `bp`, `seo`, `agent`, `FCP`, `LCP`, `TBT`, `CLS`, `SI`, seuils, détail des seuils manqués et des mesures invalides avec leurs opportunités et le rapport, puis la préparation (`[refus]`, `[avert.]`, notes), le dossier des rapports et le verdict. JSON (`--json`) : le contenu de `summary.json` (`ok`, `auditId`, `source`, `origin`, `commit`, `lighthouse`, `browser`, `runs`, `formFactors`, `categories`, `thresholds`, `queue`, `load`, `pages[]` avec `results[]` : `formFactor`, `valid`, `runs`, `invalid`, `median`, `shortfalls`, `opportunities`, `report`, `browser` ; `readiness` : `findings`, `notes` ; `counts` ; `reportsDir`) et `notes`.

Sortie : `0` tous les seuils atteints, toutes les mesures valides et aucun refus de préparation (ou « non requis » avec `--base`), `1` seuil manqué, mesure invalide, refus d'un contrôle de préparation, charge trop haute (`WEB_LOAD`), navigateur introuvable (`WEB_CHROME`), aperçu en échec (`WEB_PREVIEW`), page qui sort de l'origine (`WEB_PAGE`), dossier de rapports refusé (`WEB_REPORTS`) ou section `web` absente (`WEB_NONE`), `128 + signal` interruption (Chrome et l'aperçu lancés par l'audit arrêtés), `2` appel incorrect (dont `--base` introuvable ou dont la base commune est HEAD, `--preview` sans `--base` dans une suite complète).

## `apv status`

```
apv status [--repo <chemin>] [--json]
```

Résumé de l'état du projet : fichier de configuration (et format V2 le cas échéant), contrôles déclarés, registre des décisions (nombre de décisions et empreinte, ou nombre d'erreurs), specs de `.apv/specs/` (titre ou erreur de lecture), fichiers d'état de `.apv/state/` (taille et date), une ligne par exécution en cours (`apv run` : étape, tâches faites, en cours, en échec ; un état illisible est signalé), dernier relevé de `.apv/state/quota.log`, puis la section **« Fichiers d'état périmés »** (`freshness` en JSON : `maxAgeDays`, `maxLines`, `archive`, `checked` (fichiers existants surveillés), `stale` et `long`, listes d'entrées `file`, `external` (hors du dépôt), `modifiedAt`, `ageDays`, `bytes`, `lines` (compte exact jusqu'à `maxLines`, `null` au-delà, pour un secret ou un fichier illisible), `secret`, `stale`, `long`) : `.apv/state/resume.md`, les `.apv/state/*.md` et les chemins de `freshness.paths` (`~/` accepté) modifiés il y a plus de `freshness.maxAgeDays` jours (défaut 2) ou longs de plus de `freshness.maxLines` lignes (défaut 300 ; compte arrêté à `maxLines` + 1, taille seule au-delà de `maxLines` × 4 Kio), hors `.apv/state/suivi-constats.md`, avec « réécrire l'état court ou archiver » et « couper : état court + archive » ; lecture seule, date et nombre de lignes seulement, date seule pour un secret (nom ou cible réelle), lien sortant du dossier de son motif jamais suivi ([CONFIGURATION.md](CONFIGURATION.md#fraîcheur-de-létat--freshness)). Le crochet de début de session en cite les fichiers du dépôt en une ligne et compte ceux hors du dépôt sans les nommer. **Plugin** (`plugin` en JSON) :
- le plugin `apv@…` tel que Claude Code l'a installé (`<CLAUDE_CONFIG_DIR ou ~/.claude>/plugins/installed_plugins.json`, `enabledPlugins` du compte, puis du `settings.json` du dossier lu, puis de son `settings.local.json` ; depuis un worktree, le `settings.local.json` du checkout principal passe en dernier, au-dessus de celui que le worktree garde d'une version antérieure de Claude Code, et le `settings.json` du checkout principal n'est pas lu, comme dans Claude Code), avec sa version et son commit, face à ceux de l'outil lancé ;
- « ATTENTION » dans ces cas :
  - un projet sous APV n'a pas de plugin installé, ou l'a désactivé : la ligne donne la commande d'installation ou d'activation, à taper dans un terminal, hors de Claude Code ;
  - les fichiers de Claude Code existent mais sont illisibles (« état illisible ») ;
  - `disableAllHooks` coupe tous les crochets ;
  - le plugin installé n'est pas au niveau de l'outil : ses crochets, agents, compétences, workflows, son manifeste (`.claude-plugin`) ou son outil compilé (`dist/`) diffèrent. La ligne dit alors si le plugin est plus ancien (mettre le plugin à jour), plus récent (mettre l'outil à jour), d'une autre branche, ou d'un commit inconnu ou absent ;

  les fichiers de Claude Code (fichiers ordinaires de 1 Mio au plus ; un réglage illisible est dit illisible, jamais pris pour un plugin désactivé ; `disableAllHooks` suit la priorité des réglages) sont lus sans rien écrire. Une installation pour le projet est aussi reconnue depuis un de ses worktrees. git est lancé sans les variables `GIT_*` de l'appelant, sans crochets ni récupération réseau, et coupé après 5 s ;
- les règles de fusion que l'outil applique et que le plugin installé ne connaît pas (catalogue `docs/merge-rules.json` de chacun, lu au commit d'installation, sinon par la version qui les apporte), avec ce qu'elles exigent et la commande de mise à jour ;
- « Mise à jour à venir » : les règles qu'ajoute la branche suivie par la copie de l'outil, telle que récupérée (`git fetch`), pour réunir ce qu'elles exigent avant de mettre à jour l'outil et le plugin ensemble (« règles non lues » quand le catalogue de cette version manque à la copie). Lancé depuis la copie installée, l'outil lit la prochaine version dans le dossier de la marketplace locale.

Sous le journal de l'opérateur, `apv status` dit aussi, une ligne chacune, les relectures que le crochet du sceau n'a pas pu sceller (date, identifiant, domaine, commit : lu dans le dossier de l'enregistrement quand il est retrouvé, sinon donné en clair par la commande), même après un message refusé. Une note s'efface dès qu'une relecture du même domaine au même commit est scellée ensuite, celle-ci ou celle qui la remplace (une nouvelle relecture reçoit toujours un nouvel identifiant) ; une note sans commit connu (`--commit HEAD` d'un enregistrement introuvable) s'efface au sceau de n'importe quelle relecture de son domaine. Il en reste une au plus par domaine et commit. Une note de plus de 90 jours (durée fixe, indépendante de `rules.journalDays`) n'est plus affichée, et le crochet la supprime à son passage suivant dans ce dépôt. La relecture non scellée reste signalée par `apv review show`.

En JSON, `runs` liste les exécutions lues, terminées comprises, et `runsUnread` le nombre de fichiers d'état laissés de côté (50 fichiers et 16 Mio au plus, les plus récents d'abord). Les noms de fichiers, titres et erreurs affichés sont nettoyés (une ligne, sans séquence d'échappement ni caractère de contrôle). La commande ne modifie rien et sort toujours avec `0`, sauf appel incorrect.
