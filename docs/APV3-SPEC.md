# Agent Pipeline V3 : spécification (3.0.0-alpha)

Statut : proposition à valider par l'opérateur. Branche `apv3` du dépôt `agent-pipeline-v2`.
Sources : retour d'expérience du projet « Toujours rien » (`docs/RETOUR-TOUJOURS-RIEN.md`, 30 incidents et la section « Vision de l'opérateur ») et décisions de l'opérateur du 2026-09-23 (plugin Claude Code, même dépôt, version 3.0.0-alpha).

## 1. Objectif

Livrer une application de bout en bout, vite et proprement, avec les garde-fous qui ont fait leurs preuves : specs structurées, maquettes validées, contrôles, preuves et revues indépendantes. L'opérateur délègue ; le chef de projet (la session Claude principale) orchestre de vrais sous-agents, travaille en autonomie pendant des heures et ne rappelle l'opérateur que pour ce qui lui revient (produit, design, comptes, identité, fusion, déploiement) ou à la fin.

## 2. Principes

1. **Le chef de projet orchestre, le code ne décide pas à sa place.** Plus de contrôleur qui enchaîne des `claude --print` avec des délais : la méthode vit dans une compétence et des commandes, les rôles sont des sous-agents.
2. **Aucune limite bloquante arbitraire.** Pas de budget en dollars, pas de délai de ronde, pas de réparation de sortie structurée. La seule limite est le quota de l'opérateur, suivi et anticipé (section 9).
3. **La maquette validée est la référence absolue.** Le design se fait avec l'opérateur, par artefact, jusqu'à validation ; jamais de re-maquettage automatique.
4. **Parallèle par défaut, avec des verrous qui expirent.** Un espace de travail (worktree) par tâche, les modules partagés d'abord, des ressources partagées sous bail.
5. **Rien de faux.** Aucune approbation, aucun résultat de test, aucune source inventés. Toute affirmation sur un tiers (prestataire, DPA, région) est vérifiée sur une source officielle.
6. **Effets externes sous contrôle de l'opérateur.** Pousser des branches et ouvrir des PR brouillon : oui (délégation). Fusionner, force-push, déployer, écrire en production : jamais sans accord explicite, et jamais en masquant la sortie d'une commande qui écrit sur un service externe.

## 3. Ce qui change par rapport à V2

| V2 | V3 |
|---|---|
| Contrôleur TypeScript qui lance `claude --print` rôle par rôle | Sous-agents Claude Code orchestrés par le chef de projet |
| Product, Architecture, Design re-planifient chaque spec (40 à 60 min) | Spec rédigée une fois, validée, puis exécutée ; le design vient de la maquette validée |
| Chaîne séquentielle de tâches | Graphe de dépendances, vagues parallèles (workflows) |
| Budgets et délais qui arrêtent un rôle en plein travail | Suivi du quota, dosage des vagues, sauvegarde avant la limite |
| Base SQLite des runs, tableau de bord local | État lisible dans le dépôt (`.apv/`) et aperçu vivant de l'application |
| Revue QA unique, base de données conçue au fil des tâches | Modèle de données conçu avant le code ; revues indépendantes : sécurité, fidélité, données, RGPD |

Conservé tel quel ou presque : schéma et validation des specs, registre des décisions, calcul du minimum de sécurité OWASP, vérification des chemins autorisés, planification des contrôles, preuves (reçus), analyse du dépôt, les 6 compétences existantes.

## 4. Forme du plugin

```
agent-pipeline-v2/              (branche apv3, version 3.0.0-alpha)
  .claude-plugin/plugin.json    nom « apv », version, description
  agents/                       sous-agents (section 5)
  skills/                       compétences (section 7), dont les 6 de V2
  commands/                     ou skills invocables : /apv:* (section 6)
  workflows/                    scripts de vagues parallèles (section 8)
  hooks/hooks.json              garde-fous et reprise (section 11)
  src/                          outil `apv` en TypeScript (section 10)
  dist/                         outil compilé, versionné (le plugin s'installe sans étape de build)
  docs/                         guides, migration, retour d'expérience
```

Installation : `/plugin install` depuis le dépôt GitHub (ou `--plugin-dir` en local). Le projet cible reçoit un dossier `.apv/` (configuration, registre, specs, état) versionné.

## 5. Sous-agents

Chaque agent est un fichier `agents/<nom>.md` : description, outils autorisés, modèle, isolement, effort. Effort « high » au minimum, porté par le champ `effort` du frontmatter (accepté par le format d'agent de Claude Code, vérifié en phase 1).

Un agent `isolation: worktree` part de la branche par défaut du dépôt, pas de la base de sa tâche : sa consigne lui fait d'abord créer sa branche depuis la base exacte, `git switch -c <branche> <base>`, dans le worktree encore propre. Alternative par projet : `worktree.baseRef: "head"` dans `.claude/settings.json`, le chef de projet lançant alors l'agent depuis la bonne tête.

| Agent | Rôle | Isolement | Écrit du code |
|---|---|---|---|
| `product` | Rédige la spec depuis la demande et le registre : tâches, chemins autorisés, critères d'acceptation, plan de sécurité | aucun | non |
| `architecte` | Découpe en graphe de tâches, identifie les modules partagés à écrire d'abord, alloue les ressources | aucun | non |
| `designer` | Propose 2 ou 3 directions avant les détails (nouveau produit ou écran majeur), produit et itère la maquette en artefact avec l'opérateur ; ne code pas l'application | aucun | non |
| `critique-design` | Critique en lecture seule de chaque version de maquette avant présentation : grille notée (empreintes génériques, signature, états, animations, test des 5 secondes), corrections priorisées, deux tours au plus | aucun | non |
| `implementer` | Code UNE tâche dans son worktree, lance tous les contrôles, commite | worktree | oui |
| `integrateur` | Fusionne des branches parallèles, unifie les doublons, relance tous les contrôles | worktree | oui |
| `architecte-donnees` | Modélise la base AVANT le code (entités, relations, contraintes, index, RLS), puis revoit chaque migration et chaque requête ajoutée | aucun | migrations et doc du modèle, sur demande |
| `qa-securite` | Revue en lecture seule : attaques réelles avec deux utilisateurs, ZAP, secrets, OWASP | aucun | non |
| `qa-fidelite` | Revue en lecture seule : captures comparées à la maquette, textes, accessibilité, bonnes pratiques | aucun | non |
| `dpo` | RGPD : données, base légale, durées, sous-traitants et transferts vérifiés sur les DPA officiels, cohérence des pages légales avec le code | aucun | pages légales seulement, sur demande |

Les rôles de V2 (`roles/*.md`, archivés dans `docs/v2/roles/`) deviennent le corps de ces agents, sans les consignes « le contrôleur attend du JSON ».

## 6. Commandes

| Commande | Effet |
|---|---|
| `/apv:init` | Nouveau projet : registre des décisions, `.apv/config`, installation des agents et compétences dans le projet (phase 3) |
| `/apv:onboard` | Projet existant : analyse du dépôt, contrôles détectés, registre initial |
| `/apv:design` | Boucle de maquette par artefact jusqu'à validation ; versionne la maquette validée |
| `/apv:spec` | Rédige et valide une spec (outil `apv spec validate`, minimum de sécurité recalculé) |
| `/apv:run` | Exécute une spec : vagues parallèles, intégration, revues, corrections, PR brouillon |
| `/apv:review` | Lance les revues indépendantes (sécurité, fidélité, données, RGPD) sur une branche |
| `/apv:stack` | Fusionne une pile de PR dans l'ordre : re-cible, vérifie, fusionne, s'arrête à la première anomalie ; uniquement sur ordre explicite de l'opérateur |
| `/apv:preview` | Met à jour l'aperçu vivant sur une branche et l'annonce |
| `/apv:quota` | Relève les fenêtres d'usage (5 h, semaine) et recalibre les vagues |
| `/apv:resume` | Reprise après coupure : état `.apv/state`, environnement (Docker, piles), agents à relancer |
| `/apv:status` | Où en est-on : specs, tâches, PR, quota, aperçu |

## 7. Compétences

- `chef-de-projet` : la méthode complète (délégation, vagues, verrous, intégration, revues, PR, reprise, communication avec l'opérateur, règles d'effets externes).
- `design-artefact` : comment itérer une maquette avec l'opérateur et la verser comme référence.
- `rgpd` : grille du DPO, registre des sous-traitants, modèles de textes légaux sans promesse risquée.
- Existantes de V2 : `clean-code`, `design-patterns`, `refactoring`, `security`, `tdd`, `ui-design` (déjà au bon format).
- Par stack, fournies au projet : par exemple les bonnes pratiques Svelte 5 et le correcteur officiel (leçon 16 du journal).

## 8. Exécution d'une spec (`/apv:run`)

1. **Modèle de données** : si la spec touche aux données, l'architecte des données produit ou met à jour `.apv/data-model.md`, présenté à l'opérateur avant tout code.
2. **Plan** : l'architecte transforme les tâches de la spec en graphe ; les vagues sont les couches de dépendances ; une tâche dont au moins deux autres dépendent (types, messages, primitives, dépôts partagés) est une fondation, écrite par un seul agent ; une tâche part dès que ses dépendances sont faites et intégrées dans la branche de la spec, sans attendre la fin de sa vague.
3. **Vagues** : un workflow lance un `implementer` par tâche prête, chacun dans son worktree, avec la consigne commune du projet (brief) et les notes de vague (points d'extension, fichiers possédés).
4. **Intégration** : l'`integrateur` fusionne les branches de la vague, unifie les doublons, relance tous les contrôles.
5. **Revues** : `qa-securite`, `qa-fidelite`, `architecte-donnees`, `dpo` en parallèle, en lecture seule, sur une copie isolée.
6. **Corrections** : une passe par domaine (serveur, interface), en parallèle quand les fichiers ne se recouvrent pas.
7. **Livraison** : le chef de projet relance lui-même tous les contrôles, pousse, ouvre la PR brouillon (empilée si besoin), met à jour l'aperçu.

Chaque étape écrit son état dans `.apv/state/` : une coupure (session, machine, quota) se reprend sans rien perdre.

## 9. Quota

- Relevé par `claude -p "/usage"` (fenêtre de 5 h et semaine, heure de remise à zéro) : avant chaque vague et toutes les 10 à 15 minutes pendant l'exécution.
- La consommation observée par vague sert de **repère** pour doser le parallélisme, jamais de plafond.
- Seuils : 70 % ralentir ; 85 % finir les tâches en cours sans en lancer de nouvelles ; 95 % sauvegarder (arrêt propre des agents, commits « wip », push, notes de reprise) et prévenir l'opérateur.
- Un commit « wip » déjà poussé n'est jamais réécrit : on empile des commits propres.

## 10. Outil `apv` (TypeScript, sans dépendance)

Extrait de V2, sans le contrôleur :
- `apv spec validate <fichier>` : schéma, dépendances, chemins autorisés, minimum de sécurité recalculé depuis le dépôt (fin de l'incident 14 : même minimum qu'au lancement).
- `apv ledger validate|plan|apply` : registre des décisions (toutes les erreurs d'un coup).
- `apv gates run [--only …]` : exécute les contrôles déclarés (graphe, ressources, environnement transmis) et écrit des reçus.
- `apv scope check <tâche>` : fichiers modifiés contre les chemins autorisés.
- `apv lock run|acquire|release|status <ressource>` : verrous avec bail, propriétaire (pid) vérifié, expiration, file d'attente visible ; remplace le verrou `flock` sans bail (incidents 25 et 28).
- `apv db check [--live]` : contrôle du modèle de données (section 13 bis) ; `--live` lit la base en lecture seule par `psql` (`APV_DB_URL`, ou la commande `APV_PSQL`).
- `apv quota` : relevé et journal (`.apv/state/quota.log`, un objet JSON par ligne, ignoré par Git via `.apv/.gitignore` généré par l'outil).
- `apv preview update <branche>` : aperçu vivant (section 12), pilotable par projet.
- `apv stacks status|idle-stop|start` : piles de test déclarées, arrêt de celles inactives prouvées, redémarrage (section 18.4) ; `apv stack batch` : fusion par lot (section 18.5).
- `apv reuse check` et `apv map` : réutilisation des éléments existants et carte du code (section 22).

Tests : les suites V2 des parties conservées (contrats, politique, OWASP, preuves, ordonnanceur, inventaire) sont gardées ; les suites du contrôleur sont retirées.

## 11. Hooks

- `SessionStart` : affiche l'état de reprise (`.apv/state`) et le dernier relevé de quota.
- `PreToolUse` sur Bash : bloque `git push --force`, la fusion et le déploiement hors commande dédiée, et les commandes qui masquent la sortie d'une écriture externe (incident 30) ; gardes du harnais depuis 3.0.0-alpha.5 (arrêt de la session ou de ses parents, `killall`, `pkill -f`, installation à travers un `node_modules` lié, Docker ou Supabase sur une pile de test sans son verrou : section 18.2).
- `PostToolUse` sur les écritures d'un implementer : rappel des chemins autorisés quand une écriture en sort, d'après le marqueur de tâche `.apv/state/task.json` du worktree (vérification stricte par `apv scope check` à la fin de la tâche).
- `Stop` : enregistre l'état de reprise.

## 12. Aperçu vivant

Environnement permanent, séparé des tests (sa propre base, jamais remise à zéro par les tests), données de démonstration réalistes, compte de démo. Mis à jour à chaque livraison, avec l'adresse, la branche affichée et ce qui a changé. Le projet décrit comment le construire (commande de build, migrations, graine de données) dans `.apv/config`.

## 13 bis. Modèle de données et performance (agent `architecte-donnees`)

Leçon du projet pilote : la première version de la base avait des tables et colonnes en français (`candidatures`), des relations ajoutées au fil des tâches et un index qui ne correspondait pas au tri réel de la liste. En V3, la base est conçue avant d'être codée, et vérifiée à chaque livraison.

**Modélisation d'abord**
- Pour chaque spec qui touche aux données, l'architecte des données produit `.apv/data-model.md` : diagramme entités-relations (mermaid), une fiche par table (rôle, colonnes, types, nullabilité, valeurs par défaut, contraintes), cardinalités et règles de suppression (`on delete cascade / restrict / set null`) justifiées, stratégie d'isolation par utilisateur (RLS), index prévus avec la requête qu'ils servent. L'opérateur voit le modèle ; les tâches de code partent de ce modèle validé.
- **Tout en anglais dans le code et la base** : tables, colonnes, types énumérés, fonctions, en `snake_case`, au pluriel pour les tables. Le français reste réservé aux textes affichés. Aucune exception.

**Robustesse**
- Clé primaire UUID, clés étrangères partout où une relation existe, avec une règle de suppression explicite ; clé étrangère composite `(id, user_id)` quand une ligne enfant doit appartenir au même utilisateur que son parent.
- Contraintes en base plutôt que dans l'application seule : `not null`, `check` (valeurs, bornes, plages de dates), `unique`, types énumérés ; la validation côté serveur (zod) reprend les mêmes bornes, testées ensemble.
- RLS activée et forcée sur chaque table utilisateur, politiques avec `(select auth.uid())` ; droits par colonne quand une colonne ne doit pas être modifiée directement ; fonctions `security definer` réservées aux cas justifiés, `search_path` vide, propriétaire vérifié dedans.
- Migrations en avant uniquement, nommées, testées sur des données existantes (reprise sans perte) et vérifiées depuis une base vide.

**Transactions (ACID) et concurrence**
- Toute opération qui écrit à plusieurs endroits s'exécute dans une seule transaction : une fonction SQL, ou une transaction explicite côté serveur. Pas de suite d'appels séparés qui peut s'arrêter au milieu.
- Quand une étape ne peut pas entrer dans la transaction (fichier dans un stockage objet, e-mail, API externe), le modèle documente la compensation (annulation de l'étape déjà faite) ou l'idempotence (réservation avant envoi, clé d'unicité), et un test prouve le comportement en cas d'échec à chaque étape.
- Les invariants qui peuvent être cassés par deux requêtes simultanées (quota, doublon, « déjà fait ») sont protégés en base : contrainte d'unicité, verrou de ligne (`for update`) ou verrou consultatif ; un test lance des appels concurrents.

**Écritures uniques (anti double clic) et cohérence**

Un clic répété, une connexion lente qui renvoie, un retour arrière du navigateur ne doivent jamais créer deux écritures. Trois niveaux, tous obligatoires pour toute action qui écrit :
1. **Interface** : pendant l'envoi, le bouton passe en état « en cours » (`aria-busy`, `aria-disabled`, libellé de chargement) et ignore les clics suivants ; le formulaire n'est soumis qu'une fois.
2. **Serveur (idempotence)** : chaque formulaire de création porte une clé d'idempotence générée à l'affichage (champ caché, UUID) ; la table la stocke avec une contrainte d'unicité `(user_id, idempotency_key)` ; une seconde requête avec la même clé renvoie le résultat de la première au lieu d'écrire. Les actions de mise à jour sont idempotentes par nature (poser une valeur, pas l'incrémenter) ; les actions « faire une fois » (marquer fait, relancer, envoyer) vérifient l'état en base dans la même transaction.
3. **Base** : contraintes d'unicité sur les clés naturelles quand elles existent (un seul envoi par utilisateur, type et période ; un seul brouillon ouvert, etc.), en dernier rempart.

**Mises à jour concurrentes (pas de mise à jour perdue)**
- Deux onglets ou deux appareils qui modifient la même ligne : verrou optimiste par défaut, avec une colonne de version (`version integer` ou `updated_at`) envoyée avec le formulaire et vérifiée dans le `update … where id = … and version = …` ; en cas de conflit, l'utilisateur voit un message clair et la valeur actuelle, rien n'est écrasé en silence.
- Verrou pessimiste (`select … for update`) seulement dans une transaction courte qui lit puis écrit une valeur dont dépend l'invariant (compteur, quota, état).

**Verrous : règles**
- Transactions courtes : aucun appel réseau (e-mail, API, stockage) pendant qu'un verrou de base est tenu.
- Ordre de verrouillage fixe (par exemple toujours la candidature avant ses événements) pour éviter les interblocages ; `lock_timeout` et `statement_timeout` réglés pour qu'une attente anormale échoue proprement au lieu de bloquer.
- Verrous consultatifs (`pg_advisory_xact_lock`) libérés automatiquement en fin de transaction, jamais en mode session.
- Côté pipeline, les ressources partagées (base de test, ports) utilisent les verrous à bail de `apv lock` (expiration, propriétaire vérifié), jamais un verrou sans fin.

**Tests exigés**
- Double clic simulé sur chaque action qui écrit : une seule ligne créée, un seul envoi.
- Deux requêtes identiques envoyées en même temps au serveur (même clé d'idempotence, puis clés différentes sur une ressource unique) : le résultat attendu, sans doublon.
- Deux mises à jour concurrentes de la même ligne : la seconde reçoit un conflit, aucune donnée perdue.
- `apv db check` signale une table de création sans clé d'idempotence ni clé naturelle unique.

**Normalisation**
- Forme normale de Boyce-Codd (BCNF) par défaut, troisième forme normale au minimum.
- Toute redondance est déclarée dans le modèle avec sa raison et son garde-fou : par exemple `user_id` répété dans une table enfant pour la RLS, verrouillé par une clé étrangère composite `(id, user_id)` ; une valeur calculée gardée pour la performance, maintenue par la base (déclencheur ou fonction) et jamais écrite librement par l'application.
- `apv db check` signale une colonne dupliquée entre tables sans garde-fou déclaré.

**Performance et minimisation**
- Chaque requête sélectionne des colonnes nommées, jamais `*`. Chaque chargement de page ne remonte que ce que l'écran affiche ; rien de plus n'est envoyé au navigateur (contrôle du contenu des données de page).
- Un index par clé étrangère et par motif de requête réel (filtre, tri, pagination), vérifié par `EXPLAIN` sur un volume réaliste ; index partiels quand une condition est constante (par exemple lignes non supprimées).
- Pas de requête N+1 : nombre de requêtes par chargement de page mesuré dans les tests et borné ; pagination et limites côté serveur.
- Types adaptés (dates en `date`, horodatages en `timestamptz`, montants en entiers ou `numeric`), pas de JSON fourre-tout pour des données structurées.

**Contrôle automatique : `apv db check`** (contrôle déclaré, bloquant)
- Noms : aucun identifiant de table, colonne, type ou fonction hors anglais `snake_case` (liste de mots français courants refusée).
- Chaque clé étrangère a un index ; chaque table utilisateur a RLS activée et forcée ; aucune politique trop large ; aucune fonction `security definer` sans `search_path` fixé.
- Conseillers de la base quand ils existent (par exemple les « advisors » de sécurité et de performance de Supabase).
- Aucun `select('*')` ni `select *` dans le code serveur.
- `EXPLAIN` des requêtes principales listées dans le modèle : pas de parcours séquentiel sur une table utilisateur au-delà d'un seuil de lignes.

**Revue** : avant chaque livraison, l'architecte des données relit les migrations et les requêtes ajoutées (au même titre que les revues sécurité, fidélité et RGPD), avec une grille qui couvre la modélisation, les transactions, la concurrence, la normalisation, les index et la minimisation.

## 13. RGPD (agent `dpo`)

Consulté à trois moments : à la spec (données, base légale, durées, minimisation), à chaque nouveau prestataire ou traceur (registre des sous-traitants, transferts et garanties vérifiés sur les DPA officiels), avant chaque livraison (pages de confidentialité, cookies et mentions légales cohérentes avec le code réel). Il signale ce qui relève de l'éditeur (identité, relecture juridique) sans l'inventer.

## 14. Migration depuis V2

- Lu tel quel : `pipeline.v2.json` (contrôles, risques, règles de validation, compétences, environnement transmis), `.agent-pipeline/DECISIONS.json`, specs au format V2.
- Ignoré : agents, budgets, délais, profils de modèles, tuning.
- `/apv:onboard` sur un projet V2 crée `.apv/` à partir de ces fichiers et propose un commit.
- Projet pilote : « Toujours rien ».

## 15. Phases et critères d'acceptation

| Phase | Contenu | Accepté quand |
|---|---|---|
| 1. Socle | `plugin.json`, agents (dont `architecte-donnees`), compétence chef-de-projet, `/apv:status`, `/apv:quota`, `/apv:resume`, outil `apv` (spec, ledger, gates, scope, lock, db check), hooks de garde | Le plugin s'installe ; les tests conservés passent ; les verrous expirent ; le hook bloque un force-push ; `apv db check` refuse une table en français, une clé étrangère sans index et une table sans RLS |
| 2. Design et aperçu | `/apv:design`, `/apv:preview`, compétence design-artefact | Une maquette itérée et validée est versionnée ; l'aperçu se met à jour sur une branche |
| 3. Exécution | `/apv:init`, `/apv:spec`, `/apv:run` avec workflows, intégrateur, revues, `/apv:stack` | Une spec réelle est livrée en PR avec vagues parallèles, revues et reprise après interruption simulée |
| 4. RGPD et migration | agent `dpo`, compétence `rgpd`, `/apv:onboard` depuis V2 | « Toujours rien » tourne sous APV3 ; ses pages légales passent la revue du DPO |

État des phases :
- **Phase 1 : faite** (3.0.0-alpha.1, PR #68).
- **Phase 2 : faite** (3.0.0-alpha.2). `apv design register|list|check` verse une maquette validée par l'opérateur (citation exacte au registre, empreinte sha256) et détecte sa dérive ; `/apv:design` mène la boucle par artefact. `apv preview update|status|stop|logs` et `/apv:preview` mettent l'aperçu à jour sur une branche : essai réel sur « Toujours rien » (pile d'aperçu en 563xx, port 5190), qui remplace le script manuel du projet pilote.
- Phases 3 et 4 : à faire.

Chaque phase est livrée en PR à fusionner par l'opérateur.

## 16. Points ouverts

- ~~Champ d'effort dans le format d'agent~~ : fermé en phase 1, le champ `effort` est accepté dans le frontmatter des agents ; les 9 agents le fixent à `high` au minimum.
- Base de test par agent : schémas dédiés ou piles séparées selon la stack (Supabase : une pile par agent coûte cher en mémoire ; alternative : schéma par worktree).
- Hors de Claude Code (Codex, autres fournisseurs) : non couvert par V3 ; V2 reste disponible par ses tags.

## 17. Suites complètes : file, relance des échecs, garde-fous de démarrage (3.0.0-alpha.4)

Leçons du lancement de « Toujours rien » (journal du pilote, 26 au 28 septembre 2026), rendues génériques :
- une suite complète a expiré (`integration`, 600 s) alors qu'elle avait passé presque tout son délai à attendre le verrou de la pile de test tenu par des sous-agents ;
- une suite complète verte (10/10) n'a rien prouvé : un fichier d'état non suivi rendait l'arbre sale, `apv gates verify` l'a refusée après 25 minutes ;
- quatre chantiers en parallèle, charge jusqu'à 16 : six suites complètes rouges, chaque fois sur des tests différents et sans rapport, verts relancés seuls ;
- des serveurs de test orphelins d'une suite coupée tenaient encore les ports de la pile.

### Phase 1 (3.0.0-alpha.4)

**Suite complète** : une exécution de `apv gates run` qui lance en entier au moins un contrôle de stage `full` (`--stage full` ou sans `--stage`, même prédicat que le rythme de `/apv:run`). Les garde-fous ci-dessous ne concernent qu'elle : `--stage task` et une sélection `--only` sans contrôle `full` sont inchangés.

1. **File des suites complètes** (section `suite.queue` de `.apv/config.json`, active par défaut). Avant le premier contrôle, l'outil prend un verrou à bail du mécanisme de `apv lock` (docs/LOCKS.md : file FIFO, propriétaire vérifié, bail renouvelé, reprise d'un détenteur mort journalisée), fichier `suite.queue.lockFile` : relatif au répertoire Git commun (défaut `apv/locks/full-suite.lock`, commun à tous les worktrees du dépôt) ou absolu (commun à plusieurs dépôts de la machine). Attente bornée par `waitMs` (défaut 2 h) : au-delà, refus `SUITE_QUEUE`, sortie `1`, rien n'est exécuté. Si `maxLoad` est posé, l'outil attend ensuite, verrou tenu, que la charge moyenne sur 1 minute (`os.loadavg()[0]`) passe sous ce seuil, au plus `loadWaitMs` (défaut 30 min) ; au-delà il démarre quand même et le note (la charge peut venir d'ailleurs et ne jamais baisser : ne jamais bloquer sans fin). Attente et charge sont journalisées sur la sortie d'erreur pendant l'attente, puis dans `summary.json` (`queue`). Le verrou est libéré à la fin de l'exécution, quelle qu'en soit l'issue. Les délais (`timeoutMs`) des contrôles ne commencent qu'une fois le verrou (et la charge) obtenus.
2. **Verrou de ressource par contrôle** (champ `lock` d'un contrôle, facultatif, jamais par défaut : sans lui, rien ne change, empreinte de configuration comprise). Deux formes : `{ "resource": "<nom>" }`, verrou à bail de `apv lock` (même dossier, `APV_LOCK_DIR` compris ; réentrant par `APV_LOCK_HELD`, transmise à la commande) ; `{ "file": "<chemin>", "fileEnv": "<VARIABLE>" }`, verrou `flock` du noyau sur ce fichier (relatif au répertoire Git commun, ou absolu ; la variable, si elle est transmise au contrôle et non vide, remplace le chemin), pris par `flock(1)` dont la commande du contrôle est un descendant : un script de projet qui prouve le verrou par un ancêtre détenteur (`/proc/locks`) le voit tenu. `waitMs` borne l'attente (défaut 30 min). Le délai du contrôle ne commence qu'une fois le verrou obtenu ; l'attente est notée dans le reçu (`lockWaitMs`). Verrou non obtenu : reçu `timed_out` avec la raison, jamais une réussite.
3. **Relance des échecs** (champ `retryFailed` d'un contrôle : `{ "command": [...], "testPattern": "<regex>" }`, facultatif). Si la commande du contrôle échoue d'elle-même (statut `failed` : ni délai dépassé, ni annulation, ni commande introuvable), l'outil vérifie que le commit et l'état de l'arbre (fichiers suivis et non suivis hors ignorés) n'ont pas changé, puis lance UNE fois `retryFailed.command` (mêmes substitutions, variables, délai et verrou). Réussite : statut `passed_after_retry` (« réussi après relance »), qui compte comme réussi pour les dépendances, `apv gates run` et `apv gates verify`, mais s'affiche à part (« instable ») : fin du tableau de `gates run`, état et verdict de `gates verify`, listes `flaky` en JSON. Le reçu garde la première passe (statut, code, durée, empreintes des sorties, extrait de diagnostic), un extrait de la seconde et les tests concernés (lignes de la sortie de la première passe qui répondent à `testPattern`, 100 au plus). Échec de la relance : échec normal, reçu avec les deux passes. Jamais plus d'une relance ; sans `retryFailed`, comportement inchangé. **Pourquoi la garde ne baisse pas** : chaque test de la suite a réussi sur le code exact du commit, arbre inchangé (ceux de la première passe qui ont réussi, puis ceux qui avaient échoué, relancés seuls) ; un test qui échoue deux fois fait échouer le contrôle ; l'instabilité n'est jamais masquée (statut propre, liste des tests, signalée par `gates run` et `gates verify`) et reste un constat à traiter (règle de `/apv:run` : un test instable est un constat).
4. **Garde-fous de démarrage.** (a) Arbre sale : une suite complète refuse de démarrer (`GATE_DIRTY`, sortie `1`, fichiers listés, 50 au plus) si des fichiers suivis sont modifiés ou si des fichiers non suivis non ignorés existent, avant d'attendre la file ; `--allow-dirty` la laisse tourner, ses reçus portent `dirty: true` et ne prouvent rien (`apv gates verify` les refuse, comme avant). (b) Ports : après la file, les processus qui écoutent sur `suite.ports` et dont le répertoire courant est dans la copie où tourne la suite (un worktree lié) sont arrêtés par la logique de `apv procs stop` (SIGTERM puis SIGKILL après 5 s, pid réutilisé épargné) ; jamais un processus d'une autre copie, du checkout principal, hors du dépôt, d'un outil protégé ni de la session : ceux-là sont seulement signalés. Ce qui a été arrêté et ce qui a été laissé est écrit dans la sortie et dans `summary.json` (`ports`).

Tests exigés (un par capacité, qui échoue sans elle) : attente du verrou de file, délai d'un contrôle qui ne commence qu'après le verrou, seuil de charge simulé par injection, relance réussie et relance échouée, reçu et `gates verify` d'un contrôle instable, arbre sale refusé et `--allow-dirty`, orphelins de la même copie arrêtés et pas ceux d'une autre copie.

### Phase 2 (spécifiée ici, livrée en 3.0.0-alpha.5 : section 18.5 et 18.6)

- **Fusion par lot.** Plusieurs PR prêtes (chacune prouvée au niveau tâche) sont fusionnées dans une branche d'intégration `apv/lot-<date>` créée depuis la cible ; la suite complète tourne une fois sur la tête de cette branche ; si elle est prouvée (`apv gates verify --commit <tête du lot>` à `0`), `apv stack` fusionne les PR dans l'ordre du lot, chacune vérifiée « tête contient sa base » contre la cible au moment de sa fusion, et la cible finale doit être identique à la tête prouvée du lot (même arbre) ; sinon, refus. Un échec de la suite du lot est bissecté : lot coupé en deux, chaque moitié prouvée, jusqu'à isoler la PR fautive, qui sort du lot. L'opérateur reste seul à ordonner une fusion.
- **Répartition d'une suite sur deux piles.** Un contrôle déclare ses parts (`shards`, par exemple `--shard=1/2`, `--shard=2/2`) et les ressources interchangeables (`e2e`, `e2e-2`, avec leurs variables d'environnement) ; l'ordonnanceur lance chaque part sur une pile libre, sous son verrou ; le contrôle réussit si toutes ses parts réussissent, un reçu par part plus un reçu agrégé qui seul prouve le contrôle ; une part relancée (`retryFailed`) l'est sur la même pile. La file des suites complètes reste une par machine ; la répartition raccourcit la suite, elle n'en lance pas deux.

## 18. Lot 2 (3.0.0-alpha.5) : gardes du harnais, état commité, hygiène des piles, fusion par lot

Leçons du projet pilote (journal du 27 et du 28 septembre 2026), rendues génériques : le chef de projet a coupé sa propre session en tuant le parent d'une suite (le binaire de l'extension Claude Code), puis deux fois par `pkill -f` dont le motif figurait dans la ligne de commande du shell qui le lançait ; un `npm ci` lancé dans un worktree dont `node_modules` était un lien symbolique a vidé le `node_modules` du dépôt principal ; un conteneur de la pile de test a redémarré pendant une suite qui tenait son verrou ; une suite verte n'a rien prouvé à cause d'un fichier d'état non commité ; des piles Docker de test inutilisées restent démarrées des heures.

### 18.1 Piles de test déclarées (`stacks` de `.apv/config.json`)

Section facultative, un tableau (10 piles au plus) ; absente, aucune des capacités de cette section qui en dépend ne bloque ni n'arrête rien. Chaque pile : `id` (lettres, chiffres, `.`, `_`, `-`), au moins un verrou parmi `lockFile` (verrou `flock` du noyau : chemin relatif au répertoire Git commun, ou absolu, comme `lock.file` d'un contrôle) et `resource` (bail de `apv lock`), puis, facultatifs : `lockCommand` (commande du projet qui prend elle-même ce verrou, par exemple `["node", "scripts/e2e/lock.mjs"]`), `dockerProject` (nom de projet Docker des conteneurs : un conteneur `<préfixe>_<dockerProject>` ou le libellé `...=<dockerProject>`), `env` (variables qui désignent la pile, par exemple `{ "E2E_STACK": "2" }`), `envFile` (fichier `CLÉ=valeur` à charger pour viser la pile, relatif au répertoire Git commun ou absolu), `ports` (ports de ses serveurs de test), `stop` et `start` (commandes sans shell, lancées depuis la racine du dépôt, qui arrêtent et redémarrent la pile), `idleAfterMs` (délai d'inactivité avant arrêt, défaut 30 min). Les ports d'une pile sont aussi des ports de test déclarés pour `apv procs`.

### 18.2 Gardes du harnais (crochet `PreToolUse` sur Bash)

Le crochet `bash-guard.mjs` refuse, avec la raison et la commande à utiliser à la place (sortie `2`, décision `deny`), en plus des refus de la section 11 :
1. **Arrêt de processus dangereux.** `killall` et `pkill -f` (le motif figure aussi dans la ligne de commande du shell qui le lance) toujours ; `pkill <motif>` dont le motif désigne le nom d'un ancêtre du crochet (la session et ses parents) ; `kill` qui vise un ancêtre du crochet (pid, ou groupe `-<pgid>` d'un ancêtre), `$PPID` ou une substitution qui lit un `ppid`, `kill 0` et `kill -1` ; `kill` ou `xargs kill` alimenté dans la même commande par `pgrep -f`. Ancêtres : la chaîne des parents du processus du crochet, lue dans `/proc` (le crochet est lancé par la session, comme le shell de l'outil Bash). Proposé à la place : `apv procs list` puis `apv procs stop --port <p> | --repo <copie>` (qui protège la session, ses parents, les outils et le checkout principal), ou `kill <pid>` d'un pid lu dans `apv procs list`.
2. **Installation à travers un lien.** `npm ci|install|i|add|update|uninstall|…`, `pnpm install|add|…`, `yarn` (seul ou `install|add|…`) et `bun install|add|…`, dans un dossier (courant, suivi à travers les `cd` littéraux de la commande, ou `--prefix`, `-C`, `--dir`, `--cwd`) dont le `package.json` le plus proche a un `node_modules` qui est un lien symbolique : l'installation viderait la cible, partagée. Proposé : `unlink node_modules` (retire le seul lien) puis l'installation, ou travailler dans la copie cible.
3. **Pile de test sans son verrou.** Seulement si le projet déclare `stacks`. Une commande `docker` qui modifie (tout sauf `ps`, `logs`, `inspect`, `stats`, `top`, `port`, `images`, `version`, `info`, `events`, `diff`, `history`, `search`, `system df`, `compose ps|logs|config|ls|top|images|version`) et qui vise une pile (argument égal à `dockerProject`, ou qui finit par `_<dockerProject>`, ou libellé `=<dockerProject>`), ou qui vise tout Docker (`prune`, `stop|kill|rm|restart` d'une substitution `$(docker ps …)`) ; une commande `supabase` (directe, `npx`, `pnpm dlx`, `bunx`) qui modifie une pile locale (`start`, `stop`, `db reset|start|diff|push --local`, `migration up|down`, `seed`, `test db`) dont le `project_id` (de `--workdir <dossier>/supabase/config.toml`, sinon du dossier courant, sinon `SUPABASE_PROJECT_ID=` devant la commande) est le `dockerProject` d'une pile. Refusée sauf si elle tient le verrou de la pile visée : préfixée par `flock … <lockFile>`, par `apv lock run <resource>`, par la `lockCommand` de la pile (précédée des variables `env` de la pile quand elle en déclare), lancée par `sh -c`/`bash -c` sous l'un d'eux, ou verrou déjà tenu par un ancêtre (`/proc/locks` pour `lockFile`, `APV_LOCK_HELD` pour `resource`). Proposé : la même commande sous `flock -w 1800 <lockFile>` ou `apv lock run <resource> --`, ou les scripts du projet qui prennent ce verrou.

4. **Écriture sur une base distante.** Toujours, piles déclarées ou non, et sans variable qui lève le refus : une commande `supabase` (directe, `./node_modules/.bin/supabase`, `npx [-y] supabase@x`, `pnpm dlx|exec`, `yarn dlx`, `npm exec`, `bunx`) qui écrit une base distante : `db reset`, `db push`, `db execute`, `db query`, `migration up|down|repair`, `seed` avec `--linked`, `--project-ref` ou un `--db-url` qui n'est pas sur cette machine (hôte `localhost`, `127.x`, `[::1]`), ainsi que `db push` et `migration repair` sans `--local` (ils visent le projet lié par défaut). Motif : les écritures sur une base distante (production) sont réservées à l'opérateur, dans son terminal. `--dry-run` reste permis.

Les scripts `sh -c`, `bash -c` (et `-lc`, `-ec`…) et `flock <fichier> -c` sont examinés comme des commandes (trois niveaux au plus), pour toutes les règles du crochet. Garde-fou contre l'erreur, jamais une frontière de sécurité : une commande qui calcule ses cibles (`kill "$pid"`) n'est pas devinée.

### 18.3 État d'exécution commité à la livraison

`apv run set <id> delivery running` commite, dans le checkout de l'état, les seuls fichiers `.apv/state/run-<id>.json` et `.apv/state/resume.md` (s'ils ont changé ou ne sont pas suivis ; jamais un autre fichier, même indexé), en un commit « chore(apv) : état de l'exécution <id> (livraison) », quand ce checkout est sur la branche de l'exécution (`apv/<id>` ou `apv/<id>-…`) ; sinon il le dit et ne commite rien. La suite complète de livraison part donc d'un arbre propre, sur la tête qui contient l'état. `--no-commit-state` l'évite ; `apv run save <id>` fait le même commit à n'importe quel point de sauvegarde (message « … (sauvegarde) »).

### 18.4 Hygiène des ressources

1. **Fin de suite.** `apv gates run` d'une suite complète marque chaque commande de contrôle (variable `APV_SUITE_RUN=<exécution>`, hors empreinte d'environnement) et, à la fin, qu'elle réussisse, échoue ou soit interrompue (SIGINT, SIGTERM, SIGHUP : contrôles annulés, reçus `cancelled`, sortie `128 + signal`), arrête par la logique de `apv procs stop` les processus encore vivants qui portent cette marque (serveurs lancés par la suite et sortis de son groupe de processus) et les orphelins de sa copie sur `suite.ports` ; jamais la session, un outil protégé, une autre copie ni le checkout principal. Résultat dans la sortie et dans `summary.json` (`cleanup`).
2. **Piles inutilisées.** `apv stacks status` montre chaque pile (verrou tenu ou libre, dernière utilisation connue, inactive depuis). `apv stacks idle-stop [--after 30m] [--watch] [--dry-run]` arrête (commande `stop`, sous le verrou de la pile pris sans attendre) une pile inactive depuis au moins ce délai : aucun verrou de la pile tenu, aucune suite complète en cours (file `suite.queue` libre), aucun processus à l'écoute sur ses `ports`. L'inactivité se prouve par observation : chaque passage note la pile libre ou occupée dans `<répertoire Git commun>/apv/stacks/<id>.json` ; la période d'inactivité commence au premier passage qui la trouve libre après une utilisation, et se rompt si deux passages sont séparés de plus de 2 min (rien ne prouve qu'elle soit restée libre entre deux) ou si une utilisation est connue après son début (fin d'un contrôle de `apv gates run` sous son verrou, événement du bail dans `apv lock`). Un passage isolé n'arrête donc jamais rien : `--watch` passe toutes les 30 s jusqu'à arrêt de toutes les piles concernées (ou SIGINT). Chaque décision (arrêt, refus et raison) est journalisée dans `<répertoire Git commun>/apv/stacks/events.log`. Redémarrage : `apv stacks start <id>` (commande `start`, sous le verrou de la pile). Une suite (`apv gates run`) dont un contrôle verrouille une pile arrêtée par `idle-stop` et pas redémarrée depuis (ni `apv stacks start`, ni contrôle réussi sous son verrou) l'annonce avant ses contrôles, en tête et dans son résultat (`stoppedStacks`), avec `apv stacks start <id>`.

### 18.5 Fusion par lot

`apv stack batch <pr...> [--target <branche>] [--dir <dossier>] [--bisect] [--merge]` : PR indépendantes, chacune vers la cible. L'outil lit chaque PR (`gh pr view`), vérifie qu'elle est ouverte, vise la cible, est fusionnable avec des contrôles GitHub au vert ou absents ; crée la branche `apv/lot-<AAAAMMJJ-HHMMSS>` depuis `origin/<cible>` dans un worktree (`--dir`, défaut `<répertoire Git commun>/apv/lots/<nom>`) ; y fusionne la tête de chaque PR dans l'ordre (`git merge --no-ff`, jamais de rebase ; conflit : arrêt, PR nommée) ; lance la commande `batch.setup` de `.apv/config.json` (installation des dépendances, facultative) ; puis UNE suite complète (`apv gates run --stage full`, file et garde-fous compris) et `apv gates verify --commit <tête du lot>`. Suite en échec et `--bisect` : le lot est coupé en deux, chaque moitié reconstruite et prouvée, récursivement, jusqu'à isoler la ou les PR fautives, qui sortent du lot ; le reste est reconstruit et prouvé une dernière fois. Lot prouvé et `--merge` (avec `APV_ALLOW_MERGE=1`, sinon refus comme `apv stack merge`) : fusion des PR dans l'ordre du lot (`--merge` de GitHub seulement, `--match-head-commit`), chacune précédée de : PR relue (ouverte, cible, fusionnable, contrôles, tête identique à celle fusionnée dans le lot), arbre actuel de la cible identique à celui du lot avant cette PR (la cible au départ du lot pour la première, sinon le commit de fusion précédent du lot) ; chaque fusion constatée par relecture, puis arbre de la cible comparé à celui du commit de fusion correspondant du lot. L'écart de la tête de chaque PR (elle ne contient pas les fusions précédentes du lot) est ainsi toléré : le contenu fusionné est celui qui a été prouvé. À la fin, l'arbre de la cible doit être identique à celui de la tête prouvée du lot ; toute différence arrête la fusion et est signalée. Journal : `.apv/state/stack.log`.

Compléments (revue de la PR #91) :
- **Contrôles de la cible.** Un lot se prouve avec la configuration de la cible (`gates`, `environment.passEnv`, `batch` dont `batch.setup`, `stacks`, `suite` lus à `origin/<cible>`), jamais avec celle qu'il apporte. Une PR qui change ces sections (sa tête contre sa base commune avec la cible) fait refuser le lot avant toute construction, avec la marche à suivre : la prouver seule.
- **Lot partiel.** Dès qu'une PR demandée reste hors du lot prouvé (conflit, ou isolée par la bissection), le lot est « partiel » : le reste est prouvé (et fusionné avec `--merge`), mais la sortie est `1` et le statut `partiel` (`left` : les PR laissées et pourquoi) ; jamais un succès.
- **Interruption.** SIGINT, SIGTERM ou SIGHUP : la suite en cours est annulée, et le lot s'arrête à l'étape suivante, en particulier juste avant chaque `gh pr merge` (jamais d'effet externe après le signal) ; rapport « Lot interrompu » avec les PR déjà fusionnées, sortie `128 + signal`.

### 18.6 Répartition d'une suite sur deux piles

`apv gates run --stage full --stacks 1,2` (deux piles déclarées au moins) : les contrôles « de pile » (ceux dont `lock` désigne le verrou d'une pile déclarée : même `lockFile`, ou même `resource`) sont distribués sur les piles données, tour à tour dans l'ordre de la configuration (le premier sur la première pile, le deuxième sur la deuxième...) ; un contrôle qui a des dépendances, ou dont d'autres dépendent, reste sur la première pile (ses entrées et sorties sont dans la copie de la suite). Sur la première pile, le contrôle tourne dans la copie de la suite ; sur une autre, dans une copie détachée du même commit (`<répertoire Git commun>/apv/copies/<exécution>-<pile>`, préparée par `batch.setup`, arbre propre exigé, retirée à la fin), avec les variables de la pile (`envFile`, puis `env`, puis le `fileEnv` du verrou pointé sur le `lockFile` de la pile, seulement les noms que le contrôle reçoit par `passEnv`) et sous le verrou de cette pile. Une variable de `env` de la pile que le contrôle ne reçoit pas (absente de son `passEnv` et de `environment.passEnv`) fait refuser la répartition (`GATE_STACKS`) : le contrôle tournerait sur une autre pile que celle de son reçu. Les clés de `envFile` non reçues (le fichier est l'environnement complet de la pile) sont seulement listées (`notPassed`). Chaque copie a son ordonnanceur (ressources et exclusion d'écriture propres à son espace de travail) : les copies tournent en même temps, et un échec les arrête toutes sous `failFast`. Une copie impossible à préparer : ses contrôles ne sont pas lancés, reçu `spawn_error` avec la raison. Les reçus vont tous dans l'exécution de la suite (un par contrôle, avec `stack`) et prouvent la suite comme les autres (même commit, arbre propre). La file des suites complètes reste une par machine : la répartition raccourcit une suite, elle n'en lance pas deux. Limite : un contrôle de pile réparti en parts (`--shard`) reste à faire.

## 19. Tests modifiés répétés et attentes à durée fixe (3.0.0-alpha.6)

Leçon du projet pilote (28 septembre 2026), rendue générique : des tests e2e écrits avec des attentes à durée fixe, l'horloge réelle ou des données partagées entre tests passaient seuls, puis échouaient au hasard sous charge et bloquaient des suites complètes des jours plus tard ; un agent a fini par les corriger à la main en rejouant chaque test des dizaines de fois sous charge artificielle. Un test instable doit être rouge sur la branche qui l'apporte, pas dans la suite d'un autre.

1. **Répétition des tests modifiés** (champ `repeatChanged` d'un contrôle, facultatif, jamais par défaut : sans lui, rien ne change, empreinte comprise). Une exécution de `apv gates run` qui lancerait un tel contrôle (en entier ou ciblé) exige `--base <ref>` : sans elle, appel incorrect (sortie `2`) avant toute recherche de preuve et toute attente ; une base dont HEAD ne descend pas strictement (égale à HEAD ou en aval) : refus `GATE_BASE`. Avant toute attente (file, verrou), l'outil liste les fichiers de test ajoutés ou modifiés depuis la base commune de `<ref>` et de HEAD et, pour un contrôle lancé en entier à l'étape `full`, aussi depuis la base commune de la référence (`reference`, obligatoire : la branche où va le changement ; introuvable, la suite complète est refusée, sortie `2`, jamais un repli sur `--base` seule) et de HEAD : une `--base` trop proche ne réduit pas la liste (arbre de travail et fichiers non suivis non ignorés compris : une tâche peut ne pas avoir commité ; fichiers supprimés jamais ; renommage compté comme un ajout) qui répondent à `paths`. Plus de `maxFiles` fichiers (10 par défaut), ou un chemin qui commence par `-` : refus `GATE_REPEAT` avant toute attente, fichiers listés, rien n'est lancé. Une fois la commande du contrôle réussie (statut `passed`, ou `passed_after_retry` après sa relance), dans la même copie, sous le même verrou (bail tenu, `flock` repris) et la même file de suite complète, HEAD et arbre vérifiés identiques à leur état relevé juste avant la commande du contrôle (sinon refus, entrées de `git status` listées), l'outil lance `command` (`{{repeat}}` remplacé par `times`, 5 par défaut, partout dans un argument : le nombre du reçu est celui que la commande exécute ; `stressArgs` ajoutés ; puis les fichiers), bornée par `timeoutMs` (sinon le délai du contrôle). **Tout échec rend le contrôle rouge** : statut de la répétition (`failed`, `timed_out`...), même si la commande n'avait réussi qu'après `retryFailed`, et la répétition n'est jamais relancée. Diagnostic « Test instable : … échoue » avec « échoue X fois sur N » par test nommé par `testPattern` (sinon celui de `retryFailed`), X étant le nombre de lignes de la sortie qui le nomment. Délai dépassé : « Refus : … a dépassé son plafond de durée », jamais un saut. `apv stack batch` passe la cible comme base et comme référence ; il applique `maxFiles` (et le refus des attentes à durée fixe) PR par PR avant toute construction, jamais à la somme du lot ; une suite de lot refusée avant de tourner (`GATE_REPEAT`) arrête le lot sans bissection, jamais prise pour un échec de suite.
2. **Preuve.** Le reçu porte `repeat` (`base`, `files`, `times`, `status`, `command`, `durationMs`, `exitCode`, `failures`, `output`, `fixedWaits`) et `summary.json` le résume ; un reçu dont la répétition a échoué ne peut pas être un succès (validation du reçu). `repeatChanged` fait partie de la définition du contrôle : l'ajouter ou le changer change l'empreinte des contrôles (`configHash`) et la clé de preuve. **`apv gates verify` recontrôle la répétition** : pour un contrôle qui la déclare, le reçu réussi retenu ne compte que s'il la prouve ; l'outil recalcule depuis le commit les fichiers de test ajoutés ou modifiés depuis la base enregistrée et, au niveau complet pour un reçu complet, depuis la référence, et refuse (état `unrepeated`) une référence introuvable, un reçu sans répétition (`no_base`), une répétition qui n'a pas réussi, une base égale au commit, un fichier absent de `repeat.files`, une attente à durée fixe avec `"refuse"`. Une répétition rouge ne s'efface ainsi ni par une suite relancée sans base, ni par une base égale à HEAD ou trop proche ; `--skip-proven` s'appuie sur cette même preuve. Une référence introuvable n'est jamais une preuve (« référence introuvable »).
3. **Charge** (`stressArgs`, facultatif) : arguments qui chargent la répétition, par exemple plus de workers parallèles (`--workers=4 --fully-parallel` pour Playwright) : les répétitions d'un même test tournent en même temps, ce qui révèle les données partagées et les attentes trop courtes sous charge.
4. **Attentes à durée fixe** (`fixedWaits`, `"warn"` par défaut, `"refuse"`, `"off"`) : dans les lignes que le changement ajoute aux fichiers répétés (un fichier nouveau : toutes), `waitForTimeout(`, `sleep(`, `delay(`, `await setTimeout(` et `new Promise(r => setTimeout(r, …))` (argument de type compris, sur deux à quatre lignes consécutives ; lignes de commentaire ignorées) sont listés dans la sortie et le reçu ; avec `"refuse"`, l'exécution est refusée avant toute attente (`GATE_REPEAT`). Garde-fou contre l'erreur, jamais une preuve de stabilité : la répétition reste le contrôle.
5. **Consignes** (implementer, consigne commune, revues, chef de projet) : dans un test e2e, attendre un fait observable (réponse réseau, élément, état), jamais une durée fixe (`waitForTimeout`, `setTimeout`, délais arbitraires raccourcis) ; l'horloge contrôlée (`page.clock`) pour ce qui dépend du temps ; des données propres à chaque test (utilisateur, enregistrements, noms uniques), jamais des données partagées entre tests. La suite complète avant une PR se lance avec `--base <base de la PR>`.

Tests exigés : référence introuvable (base HEAD~1 sans test touché, dépôt sans `origin`) refusée par `gates run` et non prouvée par `verify`, refus sans `--base` et avec une base égale à HEAD ou en aval, `verify` qui refuse un reçu sans répétition, une base égale au commit ou des fichiers laissés de côté (et `--skip-proven` qui relance), arbre modifié par la commande, plafond PR par PR dans un lot et suite de lot refusée non bissectée, aucun fichier modifié, fichiers ajoutés, modifiés, non suivis et renommés répétés et fichiers supprimés ou hors motif ignorés, plafond de fichiers refusé avant toute exécution, plafond de durée, échec de répétition rouge avec « échoue X fois sur N », échec de répétition non masqué par `retryFailed` et jamais relancé, sans `--base`, répétition sous le verrou du contrôle, attentes à durée fixe (avertissement, refus, lignes non touchées et commentaires ignorés), reçu et empreinte.

## 20. Qualité web mesurable (3.0.0-alpha.7)

Constat du projet pilote (28 septembre 2026), rendu générique : l'opérateur a lancé Lighthouse à la main dans DevTools et obtenu un faux 0 dans toutes les catégories (`NO_FCP`, onglet en arrière-plan), quand une mesure en ligne de commande sans interface donnait 89/100/100/100/100. Une qualité mesurée à la main n'est ni fiable ni reproductible : la pipeline la mesure elle-même, pour tout projet web qu'elle livre, et prouve que chaque site est au meilleur niveau **mesurable**, sans jamais promettre un classement ni une citation par une IA.

1. **Commande** `apv web audit (--url <origine> | --production | --preview) [--base <ref>]` (docs/CLI.md) : section `web` de `.apv/config.json` (docs/CONFIGURATION.md). Lighthouse à version épinglée (`web.lighthouse`, dépendance du projet à cette version, sinon `npx -y lighthouse@<version>`), sans shell, en Chrome sans interface (`web.chrome`, `CHROME_PATH`, Chromium de Playwright, système), mobile et bureau, `web.runs` passages valides (3) par page ; médiane par catégorie (performance, accessibility, best-practices, seo, agentic-browsing) et par métrique (FCP, LCP, TBT, CLS, SI). Une mesure invalide (erreur Lighthouse dont `NO_FCP`, avertissement de mesure, statut HTTP autre que 200, redirection, score ou métrique absent, autre version ou autre appareil, rapport absent) est écartée avec sa raison et refaite, au plus `runs` fois de plus ; jamais comptée comme un score. Les Chrome qu'un passage laisse (processus détachés, marqués `APV_WEB_AUDIT`) sont arrêtés ; `--preview` arrête l'aperçu qu'il a démarré, quelle que soit l'issue.
2. **Seuils** `web.thresholds` : catégories (performance 90, les autres 100) et métriques (LCP 2,5 s, CLS 0,1, TBT 200 ms ; FCP et SI sans seuil par défaut). Seuil manqué : sortie `1`, tableau marqué, trois principales opportunités ou diagnostics du passage médian. Rapports JSON et HTML du passage médian et `summary.json` dans `web.reportsDir` (ignoré par Git), `--json` pour le résumé.
3. **Préparation à la recherche et aux IA**, légère, sur l'origine auditée seulement : statut 200 sans redirection, robots.txt (RFC 9309, robots de `web.robotsAgents`, pas de `noindex`), sitemap déclaré qui liste les pages, canonical unique absolu vers la page, title et description présents et uniques, `lang`, JSON-LD analysable (`@context`, `@type`), hreflang cohérent et réciproque, `llms.txt` si attendu ; chaque contrôle `refuse`, `warn` ou `off` (`web.checks`).
4. **Intégration** : (a) contrôle déclaré dans `gates` (`apv web audit --preview --base origin/main`, stage `full`) : audit de l'aperçu sur le commit exact, **requis par défaut** dès qu'un fichier changé depuis la base commune est hors de `web.neutralPaths` (`tests/**`, `e2e/**`, `.github/**`, `*.md` à la racine, `docs/**` ; `.apv/config.json`, `package.json`, fichiers de verrouillage, contenus `.md`, `.mdx`, `.svx`, `.html` sous `src/`, `content/`, `static/`, `public/`, `docs/**/*.html` et `web.paths` comptent toujours) ; « non requis » (sortie `0`) seulement si tous les fichiers changés sont sans effet web ; base introuvable ou dont la base commune est HEAD (HEAD égal à la référence ou en amont) : appel incorrect (sortie `2`), comme `repeatChanged` ; dans une suite complète, `--base` obligatoire ; reçu et empreinte comme tout contrôle, avec le relevé de l'audit (`web` : requis, base, référence, fichiers, audit fait), et `apv gates verify` recalcule depuis le commit tout reçu dont le relevé dit « non requis », quelle que soit la commande, d'après la référence et la base enregistrées (état `unaudited` si le recalcul dit requis ou si la référence est introuvable ; sans relevé, repli sur la commande) ; sur la branche principale, `--production` ou `--url` ; (b) après une fusion déployée, `apv web audit --production`. La mesure prend la file des suites complètes avant le verrou et la construction de l'aperçu (déjà tenue dans une suite, `APV_SUITE_RUN`) puis attend, avant chaque passage, une charge sous `web.load.max` (défaut `suite.queue.maxLoad`, sinon la moitié des processeurs), `web.load.waitMs` bornant le seul temps d'attente ; au-delà, refus `WEB_LOAD`, les mesures déjà faites gardées : une mesure sous charge fausse la performance, elle ne démarre jamais « quand même ». Sûreté : pages et redirections (5 au plus) sur l'origine auditée seulement, corps lus en flux et bornés, dossier de rapports relatif, dans le dépôt et jamais suivi par Git (rétention limitée aux dossiers d'audit), Lighthouse du projet seulement si c'est le vrai paquet à la version épinglée, options de Chrome qui lancent un programme ou ouvrent le navigateur refusées, Chrome arrêtés avant de libérer la file, annulation propagée au verrou et à la construction de l'aperçu.
5. **Méthode** : compétence `web-qualite` (quand mesurer, lire, prioriser, ne rien promettre), agent `auditeur-web` (lecture seule, corrections classées par gain mesuré), règle dans la consigne des implementers et de la compétence du chef de projet (livraison, déploiement).

Tests exigés : audit requis par défaut (fichiers serveur, bibliothèques, configuration de build) et « non requis » seulement hors effet web, base égale à HEAD ou en amont refusée, `verify` qui refuse un « non requis » que le recalcul contredit ou un reçu sans relevé ; redirections sur l'origine seulement et bornées, page qui sort de l'origine refusée, dossier de rapports suivi refusé, rétention limitée aux audits, alias de Lighthouse ignoré, options de Chrome refusées, charge : mesures gardées ; robots.txt lu comme Google (BOM, jeton, groupes fusionnés, encodage), barre finale exacte ; analyse d'un rapport Lighthouse 13 réel (réduit), mesure invalide refusée pour chaque cause, médiane et passage représentatif, seuils et défauts, configuration refusée, robots.txt (groupes, règle la plus longue, jokers), sitemap, balises, JSON-LD et chaque contrôle de préparation sur des documents d'exemple ; commande de bout en bout avec un Lighthouse de substitution (passages, médiane, rapports ignorés par Git, Chrome laissé arrêté, file tenue), seuil manqué, passage invalide refait puis refus, appel incorrect, `--readiness-only`, `--preview --base` (non requis, puis aperçu construit, audité et arrêté), refus pour charge, contrôle dans une suite complète avec reçu et `apv gates verify`.

## 21. Portée de la preuve : suite complète non requise pour une PR sans effet (3.0.0-alpha.8)

Constat du projet pilote (28 septembre 2026), rendu générique : une PR qui ne change que de la documentation ou des réglages de la pipeline (décisions, specs) payait la suite complète de 35 minutes (tests navigateur et intégration) comme une PR de code. La vitesse ne doit rien retirer à la sécurité : toute PR qui touche le code, la configuration de build, les dépendances, les migrations, les tests eux-mêmes ou les scripts de test garde la suite complète.

1. **Champ `skipWhenOnly` d'un contrôle** (facultatif, jamais par défaut : sans lui, le contrôle est toujours requis, empreinte comprise) : `paths` (motifs des fichiers sans effet, obligatoire ; un motif qui couvre du code source est refusé à la validation), `except` (motifs retirés de `paths`), `reference` (la branche où va le changement, obligatoire). Il ne joue qu'à l'étape `full`.
2. **Décision, avant toute attente.** Même rigueur que `repeatChanged` (section 19) : à la suite complète, `--base` obligatoire (appel incorrect sinon, avant `--skip-proven`), base dont HEAD descend strictement (`GATE_BASE` sinon), référence qui se résout **par sa ref complète** (`git for-each-ref` sur `refs/remotes/<nom>`, `refs/heads/<nom>`, `refs/tags/<nom>`, `refs/<nom>` : aucune, ou plusieurs, donc un nom ambigu comme une branche locale ou un tag `origin/main` qui masquerait la vraie, font refuser, appel incorrect ; une ref complète `refs/...` ou un identifiant de commit complet est pris tel quel ; jamais un repli sur `--base` seule ; même résolution pour `repeatChanged.reference` et pour la base de `apv web audit`). Fichiers comptés : `git diff --raw --no-renames` entre le commit et la base commune de `--base`, et entre le commit et la base commune de la référence (union ; ajouts, modifications, suppressions, avec leurs modes). Le contrôle n'est **non requis** que si TOUS ces fichiers répondent à `paths`, à aucun `except`, à aucun fichier toujours requis (comparaisons de `except` et des fichiers toujours requis sans tenir compte de la casse), gardent leur mode et leur type, **ne sont nommés nulle part ailleurs**, ni eux ni leurs dossiers (`git grep -F -i` au commit dans **tout l'arbre suivi**, sauf les fichiers que la liste de la référence dispense, `.apv/config.json`, `.apv/DECISIONS.*`, `.apv/specs/**`, `.apv/state/**`, `pipeline.v2.json` et les fichiers d'exclusion d'outils `**/.*ignore` : le chemin, le nom et le chemin Windows du fichier, et, pour un fichier atteint par un motif à joker, chaque dossier parent comme segment de chemin, `docs/`, `/docs`, `\docs`, `docs\`, ou comme nom cité, `'docs'`, `"docs"`, `` `docs` `` ; un fichier listé exactement n'est cherché que par son chemin et son nom (compromis : un `readdirSync` de son dossier n'est pas vu) ; les commentaires comptent ; un dossier cité rend requis tout fichier changé dessous, ce qui couvre `readdirSync('docs')`, `join('docs', nom)`, `import.meta.glob('../docs/*.md')` et les lectures depuis la racine ou d'autres dossiers ; faux positifs acceptés, le défaut est la suite complète ; fichiers supprimés compris ; recherche impossible, en échec ou au-delà de 1000 motifs : requis) et **ne sont la cible d'aucun lien symbolique** du commit (cible résolue en chemin réel avant d'être jugée hors du dépôt ; un lien vers la racine ou l'un de ses ancêtres rend tout requis ; au-delà de 500 liens : requis). Un chemin entièrement calculé (nom de dossier assemblé à partir de morceaux, lu depuis une variable d'environnement ou une base de données) échappe à la recherche : la dispense suppose qu'aucun code ne lit ces fichiers, et une liste fermée de fichiers est préférable à un motif de dossier. Un fichier lu par l'application ou par les tests n'est jamais sans effet : il va dans `except`. Listes lues **à la référence** (la configuration de `origin/<cible>`, comme `apv stack batch` depuis 3.0.0-alpha.5), jamais dans le changement ni dans un `--config` : une PR ne se donne pas de dispense ; une PR qui change la liste touche `.apv/config.json`, toujours requis, et se prouve sans dispense. Toujours requis, quelle que soit la configuration (`ALWAYS_REQUIRED`) : `.apv/config.json`, `pipeline.v2.json` et le fichier de `--config` s'il est dans le dépôt ; manifestes et verrous de dépendances ; CI et `.gitmodules` ; le dossier des maquettes validées (`design.dir`, `docs/design` par défaut, de la configuration du changement et de la référence) ; le contenu que l'application compile, sert ou charge par convention (`.md`, `.mdx`, `.svx`, `.html` sous `src/`, `static/`, `public/`, `content/`, `app/`, `pages/`, à toute profondeur ; un contenu chargé par convention ailleurs va dans `except`) ; `**/.gitattributes` ; configuration de build, de test et d'exécution (`**/*.config.*`, `tsconfig*.json`, `.env*`, `Dockerfile*`, `Makefile`...) ; tests et scripts de test (`scripts/**`, `**/*.sh`, `test/**`, `tests/**`, `e2e/**`, `**/*.test.*`, `**/*.spec.*`, `**/*.e2e.*`, les `testPaths` et `repeatChanged.paths` du contrôle, les chemins que nomment ses commandes) ; migrations (`**/migrations/**`, `**/*.sql`) ; tout fichier dont le mode ou le type change (lien symbolique, sous-module, exécutable). Requis aussi : arbre modifié, commit déjà contenu dans la référence, référence sans base commune, configuration de la référence illisible ou qui ne déclare pas le champ pour ce contrôle, plus de 2000 fichiers. Quand la configuration (du changement ou de la référence) déclare `web`, tout fichier que l'audit web jugerait « web » (`webImpact`) rend requis tout contrôle qui a `skipWhenOnly`, quelle que soit sa commande ; `skipWhenOnly` reste refusé sur un contrôle dont la commande lance `apv web audit`. Requis encore : une configuration de la référence qui déclare une autre `reference` que celle du contrôle (une PR qui pointe sa référence ailleurs n'est jamais dispensée). Un contrôle requis rend requises ses dépendances (transitivement). Limite assumée : la référence nommée doit être la branche cible protégée. La résolution par ref complète interdit qu'une branche locale ou un tag masque la branche de suivi distante ; elle ne protège pas d'une ref de suivi réécrite localement (`git update-ref refs/remotes/origin/main <commit>`) : la dispense a alors la même confiance que les reçus locaux, écrits sur la même machine ; `apv stack batch` y échappe, il récupère la cible (`git fetch`) et passe son commit. Reste le cas d'une autre branche distante fabriquée, qui contiendrait déjà le code du changement et que la configuration désignerait comme référence (elle-même se désignant) : ce détour change `reference` dans `.apv/config.json`, visible dans la PR contre sa vraie cible, et `apv stack batch` s'ancre sur la cible de la PR lue sur GitHub.
3. **Reçu.** Un contrôle non requis n'est pas lancé : reçu `not_required` (code `null`, jamais un succès par lui-même, validé par le schéma) qui porte `scope` : `required`, `reason`, `base`, `reference` (bases communes), `referenceName`, `referenceSha` (commit où la liste a été lue), `fileCount`, `files` (tous), `blocking` ; un contrôle requis porte aussi `scope` avec sa raison. `summary.json` le résume. Si tous les contrôles `full` sont non requis, ni file, ni ports, ni fin de suite.
4. **Preuve recalculée.** `apv gates verify` ne croit jamais le reçu : pour un reçu `not_required`, il recalcule la portée depuis le commit (base enregistrée, référence de la configuration ou cible du lot, listes lues à la référence) et ne le compte que si le recalcul dit « non requis » ; sinon état `required` (« requis (dispense non prouvée) »), avec la raison et les fichiers. `--skip-proven` et `apv stack batch` s'appuient sur cette même preuve ; le lot passe la cible comme référence, et une PR qui change `gates` fait refuser le lot (dérive de configuration, section 18.5).

Tests exigés : documentation seule (non requis, rien lancé, reçu complet, `verify` à 0, `--skip-proven`) ; fichier dispensé lu par l'application ou nommé par un test (casse ignorée), supprimé mais encore nommé, nommé par un fichier des commandes du contrôle, dossier lu sans nommer le fichier (`readdirSync`, `join`, `import.meta.glob`, lecture depuis la racine, `app/`, `packages/*/src`, un script Python), cible d'un lien symbolique vers son dossier, lien vers la racine ou un ancêtre, cible hors du dépôt par son texte mais dedans par son chemin réel (requis) ; fichier nommé seulement dans des fichiers dispensés ou dans `.apv/` (non requis) ; `skipWhenOnly` refusé sur un contrôle `apv web audit` ; référence ambiguë (branche locale ou tag `origin/main`) refusée pour `skipWhenOnly`, `repeatChanged` et `apv web audit` ; `repeatChanged` et `skipWhenOnly` ensemble ; maquettes, contenu sous `src/`, `**/.gitattributes`, casse (requis) ; `**/*.md` sans `except` couvrant `src/`, `static/`, `public/`, `content/` refusé ; un fichier source, un fichier d'`except`, un test, un script, `package.json`, la CI, une migration, une configuration de build (requis) ; `.apv/config.json` touché, liste élargie par la PR, `--config` hors dépôt plus large que la cible, référence sans le champ (requis) ; lien symbolique et changement de mode (requis) ; sans `--base`, base égale à HEAD, référence introuvable, commit déjà dans la référence, arbre modifié ; `verify` qui recalcule (base égale au commit, reçu reporté sur un commit de code, liste réduite à la référence) ; dépendances rendues requises ; validation et empreinte ; lot de PR de documentation (non requis) et lot avec une PR de code (requis).

## 22. Réutilisation des éléments existants et carte du code (3.0.0-alpha.9)

Constat du projet pilote (30 septembre 2026), rendu générique : un implementer a codé une administration avec sa propre coquille (barre latérale, barre d'onglets, toasts, icônes) à côté de celle de l'application, des `<select>` natifs à côté du composant partagé de liste déroulante, et des heures qui se coupaient en fin de ligne ; des feuilles de style locales redéfinissaient les primitives du socle (jusqu'à 13 copies d'un même bloc). Aucune étape ne l'a arrêté : la consigne ne demandait pas de réutiliser, le contrôle de code mort ne voit pas le code copié, les relectures ne posaient pas la question, et l'inventaire du dépôt (section 10) ne servait qu'à `apv spec validate`, jamais aux implementers. Règle de l'opérateur : utiliser les éléments existants, rendre modulable ce qui sert à plusieurs fonctionnalités, aucun code mort, inutile ou répété.

1. **Consigne** : implementer, modèle de consigne commune, architecte (plan), intégrateur (composants unifiés), designer et critique design (composants existants dans les maquettes), compétences `clean-code`, `refactoring`, `ui-design`, `design`, `run`, `init`, `onboard` : lire la carte du code avant de créer ; réutiliser, ou étendre de façon générique ; jamais de copie par fonctionnalité ; partager ce que deux fonctionnalités utilisent ; justifier tout nouveau composant d'interface ; retirer ce que le changement rend inutile ; éléments natifs réservés et primitives de style utilisés tels quels ; valeurs typographiques insécables selon la langue. Le rapport d'un implementer porte `reuse` (élément, décision `reused`, `extended` ou `added`, entrée de la carte ou justification) : le workflow `apv:vague` refuse un rapport sans cette liste, une réutilisation sans entrée de la carte ou un ajout sans justification.
2. **Carte du code** `apv map` (docs/REUSE.md, section 1) : `.apv/code-map.md`, construite depuis l'inventaire du dépôt étendu à l'arbre de travail (`buildWorktreeInventory`, partiel au-delà de 50 000 fichiers), déterministe, bornée en entrées et en octets (32 Ko, composants partagés d'abord), secrets masqués, fichiers non suivis sans résumé, écrite atomiquement et jamais à travers un lien symbolique ; versionnée, régénérée par l'intégration une fois par vague (jamais commitée par une tâche : `apv scope check` le signale), hors de la recherche des mentions de `skipWhenOnly` ; contrôle `code-map` (`apv map --check`, stage `full`) qui échoue quand elle est absente ou périmée.
3. **Contrôle** `apv reuse check --base {{baseSha}}` (docs/REUSE.md, section 2), stage `task` (donc aussi dans la suite complète), reçus comme tout contrôle, la base dans la clé de preuve : éléments natifs réservés hors des composants génériques, primitives de style (classe de base, jamais un état ni un thème) redéfinies, ou retouchées sous une classe du composant ailleurs que dans leur mise en page, blocs copiés (détecteur interne par jetons, méthode de jscpd, sans dépendance, qui lit la base commune ; constat sur la copie ajoutée ; styles seuls en avertissement), composants homonymes ou redondants (règle des noms sur la carte), valeurs typographiques sécables ; fichiers générés laissés de côté et listés ; **échec fermé** (règle `coverage`) : aucun fichier de code, d'interface ou de style créé, modifié ou déplacé par le changement ne sort du contrôle sans une déclaration de la configuration. Nouveau (bloquant en `error`) : ce que le changement ajoute depuis la base commune ; existant : signalé, jamais bloquant.
4. **Relecture** : point obligatoire de la revue `fidelite` (agent `qa-fidelite`, workflow `apv:revues`, `/apv:review`) : « quel composant existant aurait dû servir ? », gravité `eleve` quand un équivalent partagé existe et n'est pas utilisé.
5. **Installation** : `apv init` et `apv onboard` déclarent `code-map` pour tout projet et `reuse` pour un projet web, détectent la section `reuse` (référence, dossiers partagés, primitives, composant de chaque élément réservé, langue), écrivent la carte ; `apv onboard` liste ce qui est déjà dupliqué ou refait. Une configuration existante n'est jamais modifiée.

Tests exigés : clones entre fichiers et dans un fichier, seuils, commentaires, espaces et imports ignorés, lignes entières ; bloc déjà copié à la base et seulement déplacé (existant), deux copies modifiées (nouveau) ; éléments natifs (casse, attributs, commentaires, chemins permis, composant nommé) ; primitives (`@layer`, `@media`, `@utility`, imbrication, `:global`, préfixes, exceptions, ajustement imbriqué refusé ou permis) ; noms (même nom, affixe, rôle contre un composant générique, coquille contre ses barres, parties et composition exceptées) ; typographie française (heure, date, unité, milliers, interpolations, lignes changées seulement, autres langues inactives) ; configuration (défauts, erreurs refusées par le chargeur) ; carte (routes des routeurs à fichiers, imports et alias, props et variantes, rôle, bornes partagées, déterminisme, périmée, absente, autre fichier) ; bout en bout sur un projet exemple (onboard qui détecte et liste l'existant, PR fautive bloquée règle par règle puis corrigée, contrôles et reçus dans `apv gates run`) ; rapport de vague refusé sans `reuse`.

## 23. Arborescence : découpage par usage, cliquet et carte de l'architecture (3.0.0-alpha.11)

Constat du projet pilote (30 septembre 2026), rendu générique : `src/lib/applications/` avait 27 fichiers de code à plat (seuil 12), d'autres dossiers 20 à 34 ; `apv structure check` ne proposait aucun déplacement faute de préfixe commun, ne bloquait rien, et aucun agent n'était chargé de proposer un rangement. Règle de l'opérateur : une arborescence qui suit des conventions reconnues, cohérente avec le vocabulaire existant, compréhensible vite par un nouveau développeur ; une carte de l'architecture pour que les agents et les développeurs se retrouvent. Détails : docs/STRUCTURE.md.

1. **Découpage par usage** (`src/structure/split.ts`) : pour un dossier à plat, après les règles de noms, socle gardé à la racine (importé par le quart du dossier, ou modèle par son nom), autres fichiers décrits par leurs importeurs (dossiers, routes, fichiers qui les importent ensemble), leurs liens d'import et les mots de leurs noms et exports ; ancres : sous-dossiers existants et sous-dossiers du même domaine ailleurs (hors routes), plus le découpage proposé pour le dossier de modules de même nom (deux passes) ; liaison moyenne sur le cosinus, déterministe ; noms tirés du vocabulaire du projet ; raisons et convention par groupe. Jamais appliqué par l'outil.
2. **Cliquet** (`apv structure check --base {{baseSha}}`, contrôle `structure`, étape tâche, obligatoire) : configuration lue à la base ; fichier de code ajouté à un dossier au-dessus du seuil, ou qui l'y fait passer : bloquant, avec le sous-dossier proposé ; renommage dans le dossier et descente dans un sous-dossier toujours acceptés ; existant signalé sans bloquer ; constats d'analyse `error` bloquants seulement sur les fichiers du changement.
3. **Carte de l'architecture** (`src/structure/archmap.ts`, `structure.architectureMap`, `docs/carte-architecture.md`) : parties générées (arborescence de premier et deuxième niveau avec conventions, points d'entrée, routes principales, liens) réécrites par `apv map` et `apv structure map` ; parties écrites (en bref, couches et flux en mermaid, règles transverses, rôles) jamais réécrites ; contrôle : dossier, route principale ou point d'entrée ajouté sans rôle, lien cassé par le changement, carte supprimée : bloquants ; existant signalé. La carte du code nomme les dossiers à plat et leurs sous-dossiers proposés.
4. **Profils de pile** (`src/structure/profiles.ts`) : SvelteKit, Next.js, Nuxt, Astro, Angular, Vue, React, Python, Go, générique ; ancres, dossiers de routes, dossiers et points d'entrée connus, conventions avec liens vers la documentation officielle ; `structure.profile` pour imposer.
5. **Rôles** : compétence `structure` (juger, préparer un plan de rangement validé par l'opérateur, tenir la carte), architecte (règle 10), implementers et relecteurs (carte de l'architecture lue en premier), champ `placement` du rapport de vague (refusé s'il manque), revue `fidelite` ; `apv init` et `apv onboard` ajoutent le contrôle `structure` pour tout projet, écrivent la carte et listent les dossiers à plat existants.

Tests exigés : découpage d'un dossier sans préfixe par usage (socle, ancre miroir, noms, raisons, tests qui suivent, déterminisme quel que soit l'ordre, sans graphe : noms seuls), sous-dossier existant qui attire, dossier partagé jamais nommé par ses utilisateurs ; profils (liens officiels, détection) ; carte (éléments, rôles écrits gardés, motifs, liens, régénération idempotente) ; bout en bout sur un projet exemple : `apv init`, ajout refusé avec son sous-dossier, nouveau dossier à décrire, déplacement accepté, seuil franchi, configuration de la base, lien cassé nouveau et ancien, carte supprimée, `apv structure map --check` ; rapport de vague refusé sans `placement`.
