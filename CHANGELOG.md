# Changelog

## Non publié

- **Branches fusionnées supprimées par `apv stack merge` et `apv stack batch --merge`.** Projet pilote, 1er octobre 2026 : les deux commandes fusionnaient les PR sans supprimer leurs branches, et le dépôt n'avait pas le réglage GitHub « supprimer la branche après fusion » : 54 branches fusionnées s'étaient accumulées. Après les fusions, la branche de tête de chaque PR dont la fusion est constatée est supprimée par l'API REST (`gh api -X DELETE repos/<propriétaire>/<dépôt>/git/refs/heads/<branche>`, arguments séparés, sans shell) : les PR sont lues d'abord, la branche relue juste avant la suppression, puis son absence constatée par une relecture, jamais déduite du code de sortie. Elle est gardée, avec la raison : `--keep-branches` ; PR venue d'un fork (ou dont l'origine n'est pas connue) ; dépôt lui-même fork ; branche cible ou branche par défaut ; branche de longue durée nommée par la nouvelle section `stack.keepBranches` de `.apv/config.json` (motifs ; défaut `develop`, `development`, `release/*`, `releases/*`, `staging`, `hotfix/*`) ; base ou tête d'une PR encore ouverte, ou branche qui a déjà servi de base à une PR (lu par l'API ; dans une pile, la PR suivante est re-ciblée avant) ; branche protégée ; tête qui n'est plus le commit fusionné (celui de `--match-head-commit`). Une branche absente (404, par exemple supprimée par GitHub avec `delete_branch_on_merge`) est notée « absente (404) », sans erreur. Une ligne par branche (supprimée avec sa tête pour la recréer au besoin, gardée et pourquoi, absente) et champ `cleanup` en JSON ; un échec de suppression est un avertissement, la fusion reste acquise et le code de sortie ne change pas ; un lot interrompu ou arrêté sur une anomalie ne supprime rien. Si `delete_branch_on_merge` est faux, le rapport donne la commande qui l'active (`gh api -X PATCH repos/<propriétaire>/<dépôt> -F delete_branch_on_merge=true`), jamais lancée. `apv init` lit aussi ce réglage pour le dépôt GitHub de `origin` (github.com, ou un hôte où `gh` est connecté) et le signale quand il est faux, avec la même commande, sans la lancer (champ `github` en JSON ; identifiants de l'adresse masqués). `gh pr view` lit désormais aussi `isCrossRepository`. Limite connue : la suppression REST n'est pas conditionnelle (fenêtre d'un appel `gh` entre la relecture et la suppression).
- **Répétition des tests modifiés : un test dont seuls les imports changent n'est plus répété.** Projet pilote, 1er octobre 2026 : la PR de rangement #108 (modules déplacés) réécrit les chemins d'import de 13 fichiers e2e sans rien d'autre ; `repeatChanged` les comptait comme des tests modifiés et refusait la preuve (`GATE_REPEAT`, plafond `maxFiles` 10), et les 6 PR de rangement suivantes auraient fait de même. Un fichier de test dont les seules différences avec chaque base sont les chemins de ses imports (`import`, `import type`, `export … from`, `import '…'`, `vi.mock('…')` et apparentés, `import('…')` littéral, réécriture Prettier sur plusieurs lignes, renommage ou déplacement par Git sans autre changement) n'est plus répété ni compté dans `maxFiles` : il est listé dans la sortie (« tests dont seuls les imports changent : non répétés ») et dans le reçu (`repeat.importsOnly`), jamais sauté en silence, et la commande du contrôle l'exécute comme les autres. Un nom importé, un `as`, l'ordre ou toute autre ligne changée en font toujours un test modifié. `apv gates verify` recalcule la même liste depuis le commit ; la définition du contrôle reste celle de la base. `skipWhenOnly` n'est pas concerné (un test changé y rend toujours le contrôle requis).
- **3.0.0-alpha.11 : arborescence : dossiers à plat découpés par usage, ajouts refusés face à la base, carte de l'architecture.** Projet pilote, 30 septembre 2026 : `src/lib/applications/` avait 27 fichiers de code à plat (seuil 12), `src/lib/guides/` 34, `src/lib/home/` 28, `src/lib/components/applications/` 30, `src/lib/shared/` 20 ; `apv structure check` ne donnait qu'un avertissement « sans préfixe commun ni rôle reconnu », sans aucun déplacement proposé, ne bloquait rien, et aucun agent n'était chargé de proposer un rangement ; la carte du code ne donnait pas de vue d'ensemble. Spécification : section 23 de `docs/APV3-SPEC.md` ; guide : `docs/STRUCTURE.md`. **Découpage par usage** (`apv structure check`, `flat-folder`) : même sans préfixe commun, à partir du graphe des imports de la carte du code : socle gardé à la racine (importé par le quart du dossier, ou modèle par son nom), groupes par importeurs (dossiers, routes, fichiers qui les importent ensemble), liens d'import et mots des noms et des exports ; sous-dossiers existants et du même domaine ailleurs (`components/<domaine>/<x>/` pour `lib/<domaine>/`) comme ancres, deux passes pour que les composants suivent le découpage du code métier ; noms tirés du vocabulaire du projet, raisons et convention de la pile pour chaque groupe (`groups`, `core` en JSON) ; déterministe ; plan `ancien -> nouveau` avec tests et compagnons, jamais appliqué. **Cliquet** : `apv structure check --base <ref>`, configuration lue à la base : un fichier de code ajouté à un dossier à plat, ou qui en fait un, bloque (`flat-growth`) avec le sous-dossier où le mettre ; renommage dans le dossier et descente dans un sous-dossier toujours acceptés ; existant signalé sans bloquer ; changement de la section `structure` signalé, bloquant avec du code. **Carte de l'architecture** (`structure.architectureMap`, `docs/carte-architecture.md`) : parties générées (arborescence de premier et deuxième niveau avec conventions, points d'entrée, routes principales, liens) réécrites par `apv map` et la nouvelle commande `apv structure map [--check]`, parties écrites entre marqueurs (en bref, couches et flux en mermaid, règles transverses, rôles) jamais réécrites ; contrôle `architecture-map` : dossier, route principale ou point d'entrée ajouté sans rôle, lien cassé par le changement, carte supprimée bloquent. La carte du code gagne une section « Dossiers » (dossiers à plat, sous-dossiers proposés). **Profils de pile** (`src/structure/profiles.ts`) : SvelteKit, Next.js, Nuxt, Astro, Angular, Vue, React, Python, Go, générique, avec les liens de leur documentation officielle ; `structure.profile`. **Rôles** : compétence `structure` (juger le découpage, préparer un plan de rangement validé par l'opérateur, tenir la carte), architecte, implementers et relecteurs (carte de l'architecture lue en premier), champ `placement` du rapport de vague (workflow `apv:vague`, refusé s'il manque), revue `fidelite` (`apv structure check --base`). `apv init` et `apv onboard` ajoutent le contrôle `structure` (étape tâche, obligatoire, `--base {{baseSha}}`) à tout projet, écrivent la carte de l'architecture si elle manque et listent les dossiers à plat existants. Configuration : `structure.severity` accepte `flat-growth` et `architecture-map` (`error` par défaut), `structure.architectureMap`, `structure.profile`. **Relecture (PR #98)** : le cliquet compte chaque fichier de code créé ou déplacé (`dates.extra.ts` n'est plus un compagnon de `dates.ts` ; seuls les tests, `.svelte.ts`, `.server.ts`, `.client.ts`, `.d.ts` d'un module présent le sont) ; exclusions par défaut (`dist`, `build`, `coverage`, `vendor`, dossiers à point) seulement à la racine du dépôt ou d'un paquet et pour l'existant, ce que le changement crée est toujours analysé ; lien symbolique ou sous-module ajouté : bloquant (`coverage`) ; marqueur de la carte dupliqué : refusé ; un élément nouveau n'est décrit que par sa clé exacte ou un motif déjà présent à la base, et par un rôle de trois mots au moins ; nom de fichier généré accepté seulement s'il est déclaré dans `reuse.generated` de la base ; renommage réécrit dans le même dossier accepté ; sous-dossier créé par descente : rôle proposé en avertissement ; dossiers de primitives (`components/ui`) jamais découpés ; groupes nommés par le vocabulaire du projet (dossiers, domaines portés par la moitié du groupe), jamais d'après un de leurs fichiers, ni par une route hors de `src/routes`, ni par un synonyme d'un dossier voisin, sinon « à nommer par l'opérateur » ; un fichier de test seul ne compte pas dans le cliquet ; la migration de la carte du code se reconnaît à l'absence de la section « Dossiers ». **Mise à jour** : sur un projet existant, lancer `apv map` une fois après la mise à jour et commiter la carte du code (nouvelle section « Dossiers ») ; `apv map --check` le dit tant que ce n'est pas fait.
- **`apv gates verify` refuse une base non vérifiée, sauf `--offline`.** Suite de la PR #96 : un dépôt distant illisible (réseau absent), ou un commit distant qui n'a pas pu être récupéré, laissait `verify` accepter la base locale avec un simple avertissement. `verify` refuse désormais (`GATE_BASE`, « rétablir l'accès, git fetch »), sauf option explicite `--offline`, qui l'accepte en le disant (ligne « Attention : » en tête). `gates run` reste en avertissement ; `--offline` sur `run` est un appel incorrect. Le fetch automatique de la branche de base passe `--no-auto-gc` : il ne lance jamais de nettoyage du dépôt.
- **3.0.0-alpha.10 : contrôles lus à la base.** Suite de la PR #95 (limite connue) : `apv gates run` et `apv gates verify` lisaient la configuration du candidat, qu'un changement pouvait modifier pour retirer ou relâcher les contrôles qui le prouvent. Ils lisent désormais aussi la configuration de la base commune de `--against <ref>` (nouveau, sur `run` et `verify`), sinon de `--base`, sinon de la branche par défaut du dépôt distant : chaque contrôle de la base, obligatoire ou non, retiré, rendu facultatif ou modifié par le candidat, reste exigé avec sa définition de base (et ses dépendances), et la différence est dite (texte, `baseGates` en JSON). La référence se résout par sa ref complète (ambiguïté refusée) ; une ref de suivi distante est comparée au dépôt distant (`git ls-remote`) : commit distant absent, récupéré (fetch limité à cette branche) puis comparé de nouveau ; refus seulement si la ref locale est prouvée hors de l'historique distant ; en retard, avertissement pour `run` et refus pour `verify` ; distant illisible, avertissement ; branche locale jumelle d'une distante et distant sans base appliquée signalés. Le candidat peut seulement ajouter ou durcir des contrôles ; les changer passe par une PR de configuration seule, prouvée par les contrôles de sa base puis fusionnée par l'opérateur (docs/CLI.md, « Contrôles de la base »). Sans référence ni configuration à la base, rien ne change. Aucun contrôle existant retiré ni assoupli.
- **3.0.0-alpha.9 : réutilisation des éléments existants, carte du code.** Projet pilote, 30 septembre 2026 : une administration livrée avec sa propre coquille (barre latérale non repliable, barre d'onglets, toasts, icônes) à côté des composants partagés de l'application, des `<select>` natifs à côté du composant de liste déroulante, des heures coupées en fin de ligne (« 14 / h 47 »), des feuilles de style locales qui redéfinissaient les primitives du socle (jusqu'à 13 copies d'un même bloc) ; aucune étape ne l'a vu (consigne muette, code mort aveugle au code copié, relectures sans la question, inventaire du dépôt jamais donné aux agents). Spécification : section 22 de `docs/APV3-SPEC.md` ; guide : `docs/REUSE.md`. **Carte du code** : `apv map [--check]` écrit `.apv/code-map.md` depuis l'inventaire du dépôt, étendu à l'arbre de travail (`buildWorktreeInventory`) : composants partagés (rôle en une ligne, props, variantes, où ils sont utilisés), modules partagés (exports, utilisateurs), routes (routeurs à fichiers et routes déclarées dans le code), ce qui est propre à une fonctionnalité avec les doublons possibles ; déterministe, sans modèle, bornée (40 entrées par dossier, `map.maxEntries` partagées entre les sections) ; `--check` échoue si elle est absente ou périmée (contrôle `code-map`). **Contrôle** `apv reuse check [--base <ref>] [--all]` (contrôle `reuse`, stage `task`, reçus) : éléments natifs réservés (`select`, `dialog`, `datalist`, `input[type=...]` configurable) hors des chemins permis, avec le composant partagé à utiliser ; primitives de la feuille globale (`src/app.css`...) redéfinies dans un style local, ou ajustées sous une classe du composant (refusé sauf `styles.nested: "allow"`) ; blocs copiés (détecteur interne par jetons, méthode de jscpd, sans dépendance, imports ignorés, paires `fichier:lignes`) ; composants homonymes ou redondants (même nom, nom construit sur un partagé, même rôle qu'un partagé générique, coquille à côté des barres partagées ; composition exceptée) ; valeurs typographiques sécables en français (heure, date, montant, unité, milliers). Nouveau depuis la base commune de `reuse.reference` ou de `--base` : bloquant en `error` ; existant : signalé, jamais bloquant (un bloc déjà copié et seulement déplacé reste existant). Section `reuse` et `map` de `.apv/config.json`, validées par le chargeur commun. **Installation** : `apv init` et `apv onboard` déclarent `code-map` (tout projet) et `reuse` (projet web), détectent la section `reuse` (référence, dossiers partagés, primitives, composant de chaque élément réservé, langue), écrivent la carte ; `apv onboard` liste ce qui est déjà dupliqué ou refait. **Consigne et relecture** : implementer, consigne commune, architecte, intégrateur (composants unifiés, carte régénérée après fusion), designer et critique design, compétences `clean-code`, `refactoring`, `ui-design`, `design`, `run`, `init`, `onboard` ; le rapport de vague porte `reuse` (entrée de la carte réutilisée, ou ajout justifié), refusé sans elle ; la revue `fidelite` répond pour chaque nouveau composant à « quel composant existant aurait dû servir ? » (gravité `eleve` si un équivalent partagé n'est pas utilisé). Aucune vérification existante retirée ni assouplie. Relecture de la PR : base du contrôle `reuse` prise dans la clé de preuve (`--base {{baseSha}}`, une ref de suivi déplacée ne rend plus une copie « existante ») ; carte écrite atomiquement, jamais à travers un lien symbolique ni hors du dépôt ; fichiers générés (types de base de données, clients) laissés de côté et listés ; primitives limitées à la classe de base (jamais un état ni un thème) ; constat de copie sur le côté ajouté ; éléments natifs permis dans les seuls composants génériques et remplacés par le composant générique (jamais signalé pour lui-même) ; carte bornée à 32 Ko, régénérée par l'intégration (contrôle `code-map` à l'étape `full`, tâches sans commit de la carte, `apv scope check` qui le dit) ; absence de base commune expliquée ; carte partielle au-delà de 50 000 fichiers ; avertissement si `apv` n'est pas sur le PATH ; `<select>` en commentaire ou en chaîne ignoré ; retouches de mise en page d'une primitive acceptées (`styles.nested: "layout"`) ; copies de styles seuls en avertissement (`duplicates.styles`) ; référence jamais la branche courante ; typographie sans commentaires ni dessins SVG ; secrets masqués et fichiers non suivis sans résumé dans la carte ; motifs à répétition bornée ; `git show` en environnement assaini ; `mapEntry` vérifié dans le rapport de vague. Le cas d'origine bloque : un nouveau composant qui refait, sans le composer, un composant partagé générique de la structure ou du socle (`names.strong`) est une erreur (`names.strongSeverity`), et une copie de styles d'un composant partagé générique reste bloquante ; seules les copies de styles entre fonctionnalités et les ressemblances faibles de noms restent des avertissements. Contre-vérification : une mention « généré » ne vaut que si le fichier la portait à la base (ajoutée par le changement : constat bloquant) et jamais pour un fichier d'interface ; `*.types.ts` n'est plus exclu par son seul nom ; `names` bloquant pour la même famille exacte seulement, composition suivie d'import en import, coquille face aux barres et sous-composants en avertissement ; carte tronquée par priorité (composants génériques d'abord, part minimale par section, dossiers omis nommés) ; message français quand `--base` manque ; `apv scope check` suit `map.file` ; `min-height` et `white-space` comptés comme mise en page. Troisième relecture : un fichier créé sous un nom de fichier généré (`*.gen.*`, `generated/`...) est un constat bloquant, analysé, sauf déclaration dans `reuse.generated` ; jamais un fichier d'interface ; `dist/`, `build/`, `coverage/` et `vendor/` écartés à la racine du dépôt et des paquets seulement, dossiers cachés seulement pour les outils connus ; fichiers écartés listés (`excluded`). Quatrième relecture, principe d'échec fermé (règle `coverage`, toujours `error`) : tout fichier de code, d'interface ou de style créé, modifié ou déplacé par le changement est analysé, sauf déclaration dans `reuse.ignore` ou `reuse.generated`, maquette validée du registre, ou exclusion déjà vraie à la base au même chemin ; les exclusions par défaut ne valent que pour l'existant (un fichier nouveau dans l'une d'elles bloque) ; fichier illisible (octet nul, plus de 2 Mo, encodage invalide) bloquant ; `package.json` ajouté sans effet de racine ; fichiers du changement écartés jamais tronqués ; extensions déclarées par `svelte.config.js` lues ; import d'une extension inconnue signalé. Cinquième relecture : configuration de réutilisation lue à la base (un changement ne relâche jamais son propre contrôle), changement des sections `reuse`, `map`, `design.dir`, des contrôles `reuse` et `code-map` ou d'un contrôle obligatoire signalé (bloquant avec du code) ; liens symboliques et sous-modules ajoutés bloquants sauf déclaration à la base ; couverture stricte limitée aux composants, aux fichiers des dossiers de sources et à ce que l'application importe (scripts de CI et pages de documentation seulement listés) ; maquettes validées lues au registre de la base. Sixième relecture : code et styles créés ou modifiés dans `vendor/`, `dist/`, `build/`, `coverage/` toujours tenus ; graphe d'imports étendu à `@import` et `url()` des feuilles de style, `import.meta.glob`, `globEager` et `require.context`, suivi de fichier en fichier ; raison de chaque exclusion dite (`excluded.why`) ; une PR de configuration n'est « seule » que sans aucun fichier de code du changement, même écarté. La limite connue alors (liste des contrôles lue au candidat par `apv gates`) est levée en 3.0.0-alpha.10.
- **3.0.0-alpha.8 : portée de la preuve, suite complète non requise pour une PR sans effet.** Projet pilote, 28 septembre 2026 : une PR de documentation, de décisions ou de specs payait la suite complète de 35 minutes (tests navigateur et intégration). Spécification : section 21 de `docs/APV3-SPEC.md`. **Portée** : champ facultatif `skipWhenOnly` d'un contrôle (`paths`, `except`, `reference` obligatoire ; un motif qui couvre du code source est refusé) ; à la suite complète, avec `--base` obligatoire, une base dont HEAD descend strictement et une référence qui se résout (même rigueur que `repeatChanged`), le contrôle est « non requis » seulement si chaque fichier changé depuis la base commune de `--base` et depuis celle de la référence répond aux chemins **lus à la référence** (jamais dans la PR ni dans `--config`), à aucun `except`, à aucun fichier toujours requis (`.apv/config.json`, dépendances et verrous, CI, configuration de build et de test, tests et scripts de test, chemins des commandes du contrôle, migrations) et garde son mode et son type (lien symbolique, exécutable : requis) ; un contrôle requis rend requises ses dépendances. **Reçu** `not_required` (rien lancé, jamais un succès par lui-même) avec `scope` : bases, référence, commit où la liste a été lue, fichiers, raison ; ni file ni ports si aucun contrôle `full` ne tourne. **Preuve** : `apv gates verify` recalcule la portée depuis le commit (état `required` sinon, « requis (dispense non prouvée) »), `--skip-proven` et `apv stack batch` (cible comme référence) s'appuient sur elle ; une PR qui change la liste touche `.apv/config.json` et se prouve sans dispense. **Revue** : un fichier lu par l'application ou les tests n'est jamais dispensé (dossier des maquettes `design.dir` toujours requis ; fichier nommé littéralement, casse ignorée, dans `src/`, `tests/`, `test/`, `scripts/`, `e2e/` ou un fichier des commandes du contrôle, par `git grep -F` au commit ; cible d'un lien symbolique ; `.md`, `.mdx`, `.svx` sous `src/`, `static/`, `public/`, `content/`) ; `**/*.md` exige un `except` couvrant ces dossiers ; `**/.gitattributes` ; `except` et fichiers toujours requis sans la casse. **Relecture** : la recherche des mentions couvre tout l'arbre suivi (hors fichiers dispensés, `.apv/`, `.gitignore`) et chaque dossier parent (`docs/`, `'docs'`...) : un dossier cité rend requis tout fichier changé dessous ; liens résolus en chemin réel, lien vers la racine ou un ancêtre : tout requis ; `skipWhenOnly` refusé sur un contrôle `apv web audit` ; une ref de suivi réécrite localement reste de la confiance locale (`apv stack batch` y échappe). **Troisième relecture** : avec une section `web`, tout fichier « web » rend requis tout contrôle qui a `skipWhenOnly` ; seuls `.apv/config.json`, `.apv/DECISIONS.*`, `.apv/specs/**` et `.apv/state/**` échappent à la recherche sous `.apv/` ; chemins Windows cherchés ; fichiers d'exclusion d'outils (`**/.*ignore`) non fouillés ; un fichier listé exactement n'est cherché que par son chemin et son nom ; `.md`, `.mdx`, `.svx`, `.html` sous `app/` et `pages/` toujours requis. **Références par ref complète** (`git for-each-ref`) : une branche locale ou un tag qui masquerait `refs/remotes/<nom>` rend le nom ambigu, refusé, pour `skipWhenOnly.reference`, `repeatChanged.reference` et la base de `apv web audit`. **Compatibilité** : installer 3.0.0-alpha.8 sur toutes les machines et copies qui lisent les reçus avant d'activer `skipWhenOnly` ; une version antérieure ne connaît pas le statut `not_required` et signale ces reçus comme illisibles (worktree) ou leur exécution du magasin partagé comme altérée : prudent (rien n'est pris pour une preuve) mais bruyant.

Seule tolérance : des commits de fusion, tous listés, qui ne changent aucun fichier (la PR suivante d'une pile fusionnée par `--method merge`) ; une comparaison impossible est refusée. Dérogation exceptionnelle `--allow-behind --reason "<texte>"`, journalisée avant la fusion dans `.apv/state/stack.log` (jamais versionné) et dans le rapport ; un journal impossible à écrire refuse la fusion. La preuve locale au commit exact de la tête reste une étape du chef de projet (compétences `/apv:stack`, section 2 bis, et `/apv:run`, Livraison ; `livraison-pile.md` : ordre de fusion de PR parallèles, mise à jour de chaque suivante), pas une exigence de l'outil : elle bloquerait une PR sans reçus sur cette machine. JSON : `freshness` par PR, `derogations` pour `merge`. Faux `gh` : réponse à la comparaison (`behind`, `compareFail`, `afterMergeBehind`).
- **Reçus partagés entre worktrees : ils survivent à la copie de livraison.** Projet pilote, 25 septembre 2026 (PR #32) : `apv gates run` écrivait ses reçus dans `.apv/receipts/` du worktree où il tournait ; la suite complète de livraison tourne dans une copie détachée retirée par `git worktree remove` une fois la PR ouverte, et ses reçus partaient avec elle. Le corps de la PR citait un identifiant d'exécution que personne ne pouvait plus vérifier (`apv gates verify --commit <tête>` rendait « Preuve incomplète » depuis le checkout principal) : 10 minutes de suite complète relancées pour revérifier. `apv gates run` copie désormais chaque exécution dans le magasin partagé du dépôt, `<répertoire git commun>/apv/receipts/<exécution>/` (`git rev-parse --git-common-dir` : commun à tous les worktrees, jamais versionné), avec `manifest.json` (empreinte sha256 de chaque fichier), par un dossier temporaire renommé à la fin ; une copie impossible est signalée, jamais fatale. `apv gates verify --commit <sha>` lit le worktree puis, pour les exécutions qu'il n'a pas, le magasin partagé, avec les mêmes exigences (commit exact, arbre propre, configuration actuelle, reçu le plus récent) ; une exécution du magasin dont un fichier ne correspond plus au manifeste, ou dont un reçu contredit son exécution (autre commit, autre exécution, fichier d'un autre contrôle), est refusée en entier et signalée (`altered`). Le manifeste détecte une altération des fichiers, pas un faussaire qui réécrit aussi le manifeste (aucune clé secrète). Les reçus du worktree gardent leur forme et leur lecture (une exécution présente dans le worktree est lue là, comme avant). Rétention bornée : section facultative `receipts` de `.apv/config.json` (`keepDays`, 30 par défaut ; `keepRuns`, 1000), appliquée après chaque copie. `--skip-proven` voit aussi ces preuves. Nouvelles commandes : `apv gates receipts list [--commit <ref>] [--limit N]`, `apv gates receipts export <exécution> --out <dossier>` (copie avec manifeste), `apv gates receipts prune [--keep-days N] [--keep-runs N]`. `apv gates verify --commit-config` lit la configuration des contrôles au commit vérifié, pour vérifier depuis un checkout dont la configuration diffère. Consignes (`/apv:run` Livraison et dernière intégration, `chef-de-projet` livraison et intégration, `docs/RUN.md`) : la PR cite l'identifiant d'exécution de la suite complète, que le chef de projet principal vérifie depuis n'importe quel checkout du dépôt par `apv gates verify --commit <tête>`.
- **Domaines de revue selon le diff : `apv review plan`.** Projet pilote, 25 septembre 2026 : une spec de pur rangement (77 renommages, imports, aucun changement de comportement, aucune migration, aucun écran) est passée par les quatre revues par défaut, 40 à 70 minutes, alors que fidélité, données et RGPD n'avaient rien à relire ; la session l'avait décidé seule. `apv review plan --base <ref> [--head <ref>] [--force <domaine>]... [--json]` lit `git diff -M` depuis la base commune et classe chaque fichier : renommage pur, chemins seuls réécrits (imports, `vi.mock`, chemins cités en commentaire, spécificateurs relatifs résolus depuis le fichier, imports réordonnés ou remis en forme) ou contenu changé ; interface, données, migration ou schéma, données personnelles, texte légal, neutre (tests, documentation, outillage) ou non classé. `securite` est toujours retenue, sans exception ; `fidelite` si l'interface ou une maquette validée change de contenu ; `donnees` si une migration (renommage compris), un schéma, une requête ou un dépôt change, ou si un terme de données apparaît dans les lignes changées d'un composant ; `rgpd` si une migration, des données personnelles, un export, un traceur ou un texte légal changent, ou si un terme RGPD (cookie, stockage local, e-mail...) apparaît dans les lignes changées. Un fichier non classé au contenu changé garde tous les domaines (prudence) : un domaine n'est sauté que sur preuve positive. Sortie : domaines retenus et sautés, raison et fichiers qui décident, en texte ou en JSON. Nouvelles clés facultatives de `review` dans `.apv/config.json`, validées par le schéma : `paths` (`ui`, `data`, `migrations`, `personal`, `legal`, `neutral`, défauts génériques), `terms` (`data`, `personal`), `always` (domaines toujours gardés) ; `db.migrations` et `design.dir` sont repris. `/apv:review`, `/apv:run` et le workflow `apv:revues` (nouveau paramètre `skipped`, rendu dans le résultat ; `securite` sautée refusée) ne lancent que les domaines retenus ; chaque domaine sauté est noté `apv run set <id> review:<domaine> skipped --note "<raison de l'outil>"` : sauter une revue exige désormais `--note`, et `review:securite skipped` est refusé par l'état. Sur la branche du rangement du projet pilote (tête `676cefd`, 203 fichiers), le plan retient `securite` seule.
- **CI sur Linux seulement.** La matrice ne lance plus macOS (Node 22.16 et 24 sur ubuntu-latest) : l'opérateur n'utilise pas macOS. Le code garde ses précautions pour macOS (chemins canoniques, absence de `/proc`), mais elles ne sont plus vérifiées par la CI.
- **Identifiant de commit relu, jamais recopié.** Projet pilote, 24 septembre 2026 : le rapport d'une tâche a donné un sha complet dont seuls les 7 premiers caractères étaient justes, le reste inventé ; `apv run set --commit` l'a refusé. `apv run set --commit` et `--base` résolvent par git un sha complet ou abrégé, ou un nom de branche, et affichent le sha complet enregistré, suivi de « résolu depuis « <ref> » » quand il diffère (JSON : `resolved`). Un commit introuvable est refusé avec le commit que désignent ses 7 premiers caractères et la tête de la branche de la tâche (`--branch`, sinon celle de l'état). Le rapport structuré du workflow `apv:vague` exige les sorties brutes de `git rev-parse HEAD` et `git log --oneline -1` (`headRevParse`, `headLog`) et liste dans `commitChecks` les rapports où elles ne s'accordent pas avec `commit`. Consignes : l'implementer et l'intégrateur collent ces sorties telles quelles ; le chef de projet relit toujours la tête par `git rev-parse <branche>` avant `apv run set --commit` (`/apv:run`, `chef-de-projet`, `integration-revues.md`).
- **`apv wait` : attendre sans dormir.** En session non interactive, `sleep`, `tail --pid` et les boucles sur `kill -0` sont refusés par les permissions ; la session du projet pilote a bricolé des scripts node pour attendre la suite complète. `apv wait --pid <pid>` attend la fin d'un processus (absent, ou zombie) ; `apv wait --file <chemin> [--contains <texte>]` attend un fichier, ou un texte dans ce fichier (seuls les octets ajoutés sont relus, fichier ordinaire seulement). `--timeout` de 1 à 580 s (défaut 580), sous la limite d'un appel Bash ; sortie `0` « Terminé », `1` « Délai dépassé » (relancer l'appel), `2` appel incorrect. Autorisé dans `/apv:run` et `/apv:review` (`node .../dist/cli.js wait`) ; les règles des sessions non interactives, l'implementer et l'intégrateur l'emploient à la place de `sleep` et consorts.
- **Copies détachées hors du dépôt.** Une session du projet pilote a créé sa copie de livraison dans un dossier frère du dépôt, hors des dossiers prévus, et `/apv:review` plaçait lui-même les copies des revues à côté du dépôt. Les copies des revues, du scan dynamique et de la livraison vont dans le dossier de session du chef de projet (où les permissions le laissent lancer ses commandes) ou sous un chemin que l'outil donne, jamais à côté du dépôt, et sont retirées par `git worktree remove` à la fin (`/apv:run`, `/apv:review`, `chef-de-projet`, `livraison-pile.md`). Le workflow `apv:revues` refuse une copie donnée par un chemin relatif. `apv dast run` range ses rapports hors de la copie, par défaut sous le dossier temporaire de la machine.
- **Scan dynamique lancé par le chef de projet : `apv dast run` et `review.dast`.** Les agents de revue n'ont pas le droit de lancer Docker : le scan ZAP prévu par la revue sécurité n'a tourné sur aucune des quatre livraisons suivies du projet pilote (septembre 2026). Nouvelle section facultative `review.dast` de `.apv/config.json` (`command` en argv avec les jokers `{{reportDir}}`, `{{commit}}`, `{{repo}}` ; `resource`, défaut `dast` ; `timeoutMs`, défaut 1 h ; `passEnv` ; `description`), validée par le chargeur commun. `apv dast run [--repo <copie>] [--out <dossier>] [--commit <ref>] [--wait <durée>] [--json]` lance cette commande dans la copie du commit revu, sous le verrou déclaré, bornée par son délai, sortie dans `dast.log`, puis écrit `summary.json` (statut `passed`, `failed`, `timed_out` ou `lock_timeout`, commit, fichiers) ; refus d'un dossier dans la copie (chemins comparés sous forme canonique : liens symboliques résolus, `/var` et `/private/var` de macOS confondus) ou déjà utilisé, et d'une copie sur un autre commit. Le chef de projet le lance avant les revues (`/apv:review`, section 3 bis ; un long scan s'attend par `apv wait --file <dossier>/summary.json`) et donne le dossier à la revue sécurité (paramètres `dast` et `dastMissing` du workflow `apv:revues`), qui lit les rapports sans lancer Docker, ou note le scan « non vérifié » avec la raison. `runLocked` accepte une sortie redirigée et un délai (code 124).
- **Niveau de confiance dans l'état d'exécution.** `apv run set <id> <task:<id> | fixes> done --confidence prouve|probable|suppose` garde le niveau retenu par le chef de projet dans l'état (champ facultatif `confidence` de la tâche ou de l'étape, et de l'événement), affiché par `apv run status <id>` et retiré quand le travail est rouvert ; `apv run next` liste le travail fait en dessous de `prouve` (`unproven`) avec l'action attendue (vérifier d'abord, ou remonter à l'opérateur). Un état écrit avant ce champ reste lisible et garde sa forme ; un état qui en porte un n'est pas lisible par une version antérieure de l'outil. Consigne : le chef de projet le renseigne quand il marque une tâche ou la passe de corrections faite (`/apv:run`, `chef-de-projet`, `confiance.md`).
- **Le rythme de la suite complète est tenu par l'outil.** Nuit du 24 au 25 septembre 2026 sur « Toujours rien » (spec de 12 tâches, 65 critères) : environ 9 h d'exécution, dont 3 h pour une seule intégration intermédiaire, parce que la session a lancé `apv gates run --stage full` alors que `apv run next` annonçait « niveau attendu à cette étape : contrôles de tâche et ciblés » ; la suite a trouvé des tests qui se gênaient, deux passes de corrections ont suivi, suite relancée chaque fois. Désormais, dans le cadre d'une exécution, `apv gates run --stage full` (ou sans `--stage`) refuse, sortie `1` (`GATE_RHYTHM`), une suite qui exécuterait un contrôle de stage `full` quand l'étape courante n'attend que le niveau tâche (même calcul que `apv run next` : `computeNext`, `suite.level`) ; le message cite l'étape, le niveau attendu et la commande à lancer à la place. L'exécution : `--run <spec-id>` (nouvelle option ; état absent : `RUN_MISSING`), sinon la branche courante `apv/<id>` ou `apv/<id>-<suffixe>` (l'identifiant le plus long d'abord) quand le checkout principal du dépôt (premier worktree de `git worktree list`) a `.apv/state/run-<id>.json`. Dérogation : `--reason "<texte>"` (nouvelle option, 1 à 500 caractères, jamais avec `--stage task`) laisse passer la suite, journalise un événement `gates:full` (raison et commit) dans l'état par l'API d'état, sous le verrou `run:<id>`, et écrit la raison dans chaque reçu et dans `summary.json` (champ `override`, facultatif). Hors exécution (autre branche, tête détachée, aucun état), à la dernière intégration, à la livraison et avec `"each-integration"` : inchangé. JSON de `apv gates run` : `rhythm` et `notes`. `suiteMode` est partagé par `apv run next` et `apv gates run` (`src/run/rhythm.ts`).
- **État d'une exécution trouvé dans tous les worktrees.** Projet pilote, 25 septembre 2026 : plusieurs exécutions tournaient côte à côte, chacune lancée depuis son propre worktree (état dans ce worktree, sur `apv/<id>`), alors que le contrôle du rythme de `apv gates run` ne cherchait l'état que dans le checkout principal (premier worktree de `git worktree list`) : `--run <id>` était refusé (`RUN_MISSING`) et, sans `--run`, la déduction par la branche ne trouvait rien ; le rythme n'était pas tenu. Désormais l'état `.apv/state/run-<id>.json` est cherché dans tous les worktrees du dépôt (`git worktree list --porcelain`, `locateRunState` dans `src/run/rhythm.ts`) ; plusieurs copies (un état versionné voyage avec les commits) : celle du worktree sur `apv/<id>`, sinon celle du checkout principal, sinon refus `RUN_AMBIGUOUS` (sortie `1`) qui liste les emplacements. Le niveau attendu se calcule avec `run.fullSuite` du checkout qui a l'état, donné dans le JSON (`rhythm.checkout`). `apv run set|next|status <id>|pause|resume` gardent l'état du checkout courant quand il en a un et, sinon, le trouvent de la même façon (note sur la sortie d'erreur) ; la consigne de `/apv:run` dit de les lancer depuis le checkout de l'exécution, plus seulement depuis le checkout principal.
- **Specs plus petites, chaînes plus courtes.** La même spec formait une chaîne de 5 couches (base, données, relances et documents, ajout et actions et fiche, liste et colonnes), chaque couche attendant l'intégration de la précédente. `apv spec validate` avertit, sans jamais invalider la spec ni changer son code de sortie, au-delà de `spec.maxTasks` tâches (défaut 6) ou `spec.maxAcceptance` critères (défaut 30) (`SPEC_SIZE` : découper en specs indépendantes de 4 à 6 tâches, livrées en parallèle, chacune avec sa PR), et au-delà de `spec.maxDepth` couches de dépendances (défaut 3, les vagues de `apv run start`) en nommant le chemin le plus long (`SPEC_DEPTH`). Nouvelle section `spec` de `.apv/config.json`, validée par le schéma (entiers bornés, propriété inconnue refusée). JSON : `warnings` et `limits`. Consignes : compétences `spec` et `chef-de-projet` (`references/planification.md`, section 1 bis), agents `product` et `architecte` : une demande large devient plusieurs specs de 4 à 6 tâches, indépendantes quand c'est possible, exécutées en parallèle sur des piles de test distinctes si le projet en déclare plusieurs ; motif « contrats d'abord » (la première tâche pose types, schémas, signatures, interfaces de composants et migrations avec des implémentations minimales testées, les tâches suivantes se construisent en parallèle contre eux) ; une dépendance ne se déclare que si la tâche a besoin du code de l'autre. La définition d'une fondation ne change pas.
- **Quota : doser les exécutions simultanées.** Trois exécutions simultanées ont coûté 2 h 30 de pause de quota la même nuit. `apv quota` nomme la fenêtre la plus contraignante (`binding` : `session` ou `week`, la semaine en cas d'égalité ; champ ajouté au journal) et dit combien d'exécutions `/apv:run` peuvent tourner en même temps. Règle (`/apv:run` section Quota, `chef-de-projet`, `quota-sauvegarde.md`, `/apv:quota`) : avant d'en lancer une de plus, relever `apv quota`, semaine comprise ; au niveau `ok`, autant d'exécutions que de piles de test libres ; au premier seuil (70 %), une de plus au maximum ; au-delà, aucune nouvelle, on finit celles en cours ; la consommation du chef de projet principal (vérifications, relectures) compte aussi.
- **Suite complète deux fois par spec, sans baisser la garde.** Sur « Toujours rien » (septembre 2026), la suite complète (intégration et navigateur, environ 9 minutes) tournait à chaque intégration, à chaque intégration de corrections et à la livraison : 4 à 5 fois par spec, environ 45 minutes, plus l'attente du verrou `e2e` partagé. Nouveau réglage `run.fullSuite` de `.apv/config.json`, validé par le schéma : `"final"` (défaut) lance la suite complète à la dernière intégration (toutes les tâches intégrées, avant les revues, qui citent ses reçus) et à la livraison sur la tête finale ; les intégrations intermédiaires et les passes de corrections avancent `apv/<id>` sur les contrôles de tâche et les tests ciblés (`affected`) de tous les fichiers changés depuis la dernière suite complète, vérifiés au commit exact, plus le test qui prouve chaque correction. `"each-integration"` garde l'ancien rythme. Pour une spec à trois vagues avec une passe de corrections : 5 suites complètes avant, 2 avec `"final"` ; sans corrections, 4 contre 1. `apv gates verify --stage task` exige désormais aussi les contrôles `full` qui déclarent `affected`, prouvés par leur reçu ciblé (ou complet), avec `--base <ref>` obligatoire : un reçu ciblé ne compte que si la base de son exécution est `<ref>` ou l'un de ses ancêtres (lue dans son `summary.json`) ; JSON enrichi (`base`, `targeted`, `reserved`, et par contrôle `viaTargeted`, `proof`, `otherBase`). Pas de double suite : `apv gates run --stage full` signale une suite déjà prouvée au commit exact, arbre propre (`alreadyProven`), et `--skip-proven` ne la relance pas dans ce cas ; la livraison commence par `apv gates verify --commit <tête>`. `apv run next` donne le rythme, le niveau de vérification attendu à chaque étape et la base des tests ciblés (`suite`). Garde-fous réécrits explicitement et inchangés (`/apv:run`, `chef-de-projet`) : contrôles de tâche complets pour chaque implementer, tests négatifs, toutes les revues dont la sécurité aux attaques réelles, suite complète et `apv gates verify` à `0` au commit exact avant toute PR, contrôle rouge jamais ignoré, test instable traité comme un constat. Compromis déclaré : une régression entre vagues, hors des fichiers changés et de ce qui en dépend, peut n'être vue qu'à la dernière intégration ; les tests ciblés la limitent. Consignes mises à jour : `/apv:run`, `chef-de-projet` et ses références, `/apv:review`, `/apv:init`, agents `implementer` et `integrateur`, workflows `apv:vague` et `apv:revues` (docs/RUN.md, docs/CONFIGURATION.md, « Exécution : `run` », docs/CLI.md).
- **Pauses de quota visibles.** `apv run pause <id> --until <HH:MM | date ISO> [--note]` écrit la pause dans l'état (champ `pause`, absent hors pause : un état jamais mis en pause garde sa forme) et la journalise (événement `pause` avec `until`) ; une nouvelle pause la prolonge ; `apv run resume <id>` la termine, comme toute transition `apv run set`. Elle s'affiche dans `apv run status`, `apv run next` (première action) et `apv status`. `/apv:run` (section 8) et la référence de sauvegarde demandent de noter chaque pause pour le quota.
- **Heure locale.** Les heures affichées par l'outil sont en heure locale (Intl, fuseau du système ou `TZ`), avec leur décalage : `2026-09-24 20:22 UTC+2` (`apv run status`, `apv status`, résumé du hook de démarrage, `apv lock`, `apv preview`). `apv run status <id>` montre les cinq derniers événements avec leur note. L'état et les reçus gardent des dates ISO en UTC.
- **Confiance calibrée et escalade.** Les agents rapportaient « corrigé » ou « cause trouvée » sans dire leur degré de certitude ; exemple observé (anonymisé) : un correctif livré alors que la cause vue en production n'avait jamais été reproduite. Idée reprise de typesafe.ai (décisions typées, confiance calibrée, seuil d'action et remontée à un humain), sans leur modèle. Trois niveaux communs à tous les rapports d'agents (constats, causes, corrections, décisions prises seul, notes de grille) : `prouve` (preuve reproductible jointe : test qui échoue puis passe, commande et sortie, capture), `probable` (lecture du code, raisonnement vérifiable, sans exécution), `suppose` (hypothèse) ; chacun exige sa preuve ou sa justification, et une correction dont la cause n'a pas été reproduite reste au mieux `probable`. Seuils du chef de projet (compétence `chef-de-projet`, section 9 bis et nouvelle référence `references/confiance.md` ; `/apv:run`, `/apv:review`, `/apv:stack`) : il n'intègre, ne livre, ne fusionne sur ordre et n'annonce « corrigé » que sur du `prouve` ; `probable` demande d'abord un test ou une exécution ; `suppose` remonte à l'opérateur avant toute action sur la production, toute fusion ou toute annonce « corrigé » ; ses comptes rendus disent le niveau de chaque affirmation importante. Workflows : `apv:vague` exige `confidence` (`prouve`, `probable`, `suppose`) et `evidence` (texte non vide) par rapport de tâche, `apv:revues` par constat et, pour l'audit de concurrence, `confidence` avec `proof` par chemin de l'inventaire ; un rapport sans niveau, avec un niveau inconnu ou un `prouve` sans preuve est refusé (`refused`, jamais compté) ; les résultats donnent `escalation.verify` (`probable`) et `escalation.operator` (`suppose`) ; un constat fusionné garde la preuve la plus forte. Agents `implementer`, `integrateur`, `qa-securite`, `qa-fidelite`, `architecte-donnees`, `dpo`, `critique-design` et `designer` : section « Niveau de confiance » propre à leur métier (le test des 5 secondes simulé par un agent est au mieux `probable`) ; consigne commune type, grille de critique (colonne « Niveau »), fichier de corrections, corps de PR et remise finale mis à jour. Guide : [docs/CONFIANCE.md](docs/CONFIANCE.md).
- **Design : direction avant détails, grille de critique notée, agent critique.** L'opérateur voulait des interfaces attrayantes et vivantes qui « ne font pas IA » ; le dire à un agent ne suffit pas. Sur le projet pilote, un testeur a cru qu'une application de suivi de candidatures pour chercheurs d'emploi servait aux entreprises à recruter : la compréhension par la cible n'était jamais vérifiée. Projet sans V2 : contrôles détectés dans `package.json`, `Makefile` et `pyproject.toml`, proposés avec `mandatory: false`, source et note. `--dry-run` montre le même plan sans rien écrire. `/apv:onboard` montre ce plan à l'opérateur, lance `apv onboard`, complète avec lui contrôles, consigne commune et aperçu, vérifie le registre et les contrôles et propose le commit. Le re-ciblage passe par `gh api -X PATCH repos/<propriétaire>/<dépôt>/pulls/<n> -f base=<cible>` ; propriétaire, dépôt et hôte viennent de l'adresse que `gh pr view` rend pour la PR (champ `url` ajouté à la lecture). Sortie toujours affichée, base toujours relue ; un appel en échec ou une base inchangée arrête la pile. Une adresse inutilisable est une anomalie du plan, avant toute fusion.
- **Fondations au niveau de la tâche.** Les vagues sont les couches topologiques des dépendances ; une tâche dont au moins deux autres dépendent directement est marquée `foundation: true` dans l'état. `apv run start`, `status` et `next` affichent « fondations (un seul agent) : … » et « en parallèle : … ». Avant, toute tâche de première couche dont une autre dépendait partait seule en vague 0 (constat 3 de l'essai de la phase 3). L'état passe en version 2 ; un état de version 1 est converti à la lecture en gardant son plan.
- **Une tâche est prête quand ses dépendances sont faites et intégrées.** `apv run next` exige que le commit de chaque dépendance soit un ancêtre de la tête de la branche de la spec (la base de l'exécution tant qu'elle n'existe pas) et liste à part les tâches « en attente d'intégration » ; `apv run set task:<id> running` applique la même règle, sauf `--force-unintegrated` avec `--note`, journalisés (constat 4). Les tâches prêtes se lancent toutes, quelle que soit leur vague.
- **Corrigé : lecture bornée de l'état visé.** `apv run start|set|next|status <id>` lisent l'état comme le résumé (fichier ordinaire, 4 Mio au plus) : une FIFO nommée comme l'état ne bloque plus la commande (constat 5).
- **`bin/apv`** : le plugin fournit un exécutable `apv`. Claude Code ajoute le dossier `bin/` d'un plugin activé au `PATH` de l'outil Bash : `apv` s'y appelle directement, sans alias. Le script lance, dans le même processus, le `dist/cli.js` de son propre plugin, dont le chemin est calculé depuis son emplacement réel (liens symboliques résolus), jamais depuis le `PATH`, le dossier courant ou une variable d'environnement ; arguments, sortie et code de sortie sont ceux de l'outil. L'interpréteur, lui, vient du `PATH` par le shebang (`#!/usr/bin/env node`) et Node applique `NODE_OPTIONS` : risque résiduel accepté et déclaré (qui contrôle le `PATH` contrôle déjà `git` ; un chemin absolu casserait nvm), voir [docs/PLUGIN.md](docs/PLUGIN.md). `bin` entre dans le champ `files` du paquet.
- **Résumé des exécutions partagé** (`src/run/summary.ts`) : une entrée par `.apv/state/run-*.json`, avec les tâches en cours nommées, ou la raison d'un état illisible, invalide, trop volumineux (plus de 4 Mio), qui n'est pas un fichier ordinaire ou dont l'identifiant de spec ne correspond pas au nom du fichier, sans jamais faire échouer l'appelant. Les fichiers les plus récents sont lus d'abord, 50 au plus et 16 Mio au total : les autres sont comptés (« N autre(s) non lue(s) »), jamais lus. Chaque ligne est nettoyée (séquences d'échappement, caractères de contrôle et de format retirés) et bornée ; une erreur nomme le fichier par son chemin dans le dépôt et ne cite rien de son contenu. `apv status` et `apv run status` s'en servent pour leur liste des exécutions ; `apv status` nettoie aussi les noms de fichiers, titres et erreurs des specs et des fichiers d'état.
- **Exécutions non livrées au démarrage de session** : le hook `SessionStart` les liste juste après l'en-tête, comme un état lu sur disque à vérifier, avec `apv run next <id>` pour un état lisible dont l'identifiant de fichier est valide. Il ne lit pas plus de fichiers qu'il n'affiche de lignes : les huit états les plus récents, puis le nombre des autres et un renvoi à `apv status`. Sans `dist/`, une ligne le signale et la session démarre quand même ; une erreur de lecture de `.apv/state` a sa propre ligne, et une entrée illisible de `.apv/state` ne vide plus la liste des fichiers récents.
- **`apv run set --commit` sur les étapes et les revues** : le champ `commit`, déjà enregistré pour une tâche, vaut aussi pour une étape (commit du plan, tête intégrée) et pour une revue (commit revu), vérifié dans le dépôt. Il est facultatif : un état écrit avant ce champ reste lisible. Remplacer le commit d'une cible déjà `done` exige `--note`, journalisée comme la réouverture d'un travail fait.
- **État d'exécution plus strict** : les dates (`createdAt`, `updatedAt` et celles des étapes, tâches, revues et événements) doivent suivre le format ISO de `Date#toISOString` ; un état dont l'identifiant de spec diffère du nom de son fichier est refusé par `apv run start|set|next|status`.
- **Lignes du hook nettoyées** : `oneLine`, commun aux hooks, retire désormais séquences d'échappement, caractères de contrôle et de format, comme le module de résumé ; les noms des fichiers d'état récents et les lignes des notes de reprise passent par elle.

## 3.0.0-alpha.3 : phase 3, exécution (outil)

- **`apv init`** prépare un projet : `.apv/config.json` (nom du projet, aucun contrôle), registre des décisions vide et valide, `.apv/brief.md` tiré du modèle de consigne de la compétence `chef-de-projet`, `specs/`, `state/` et `.apv/.gitignore`. Jamais un fichier existant n'est écrasé : la commande se relance sans risque et dit ce qu'elle a créé, complété ou trouvé. Refus hors d'un dépôt Git. La configuration gagne la section `name`, lue par le chargeur commun.
- **`apv spec new <id>`** écrit le gabarit d'une spec, accepté par `apv spec validate --draft` ; sa question ouverte fait refuser un gabarit non rédigé au lancement. Identifiant en kebab-case, aucun écrasement.
- **`apv run start|set|next|status`** tient l'état de reprise d'une exécution dans `.apv/state/run-<spec>.json` : spec validée comme au lancement et son empreinte, base et son commit, vagues calculées depuis les dépendances (vague 0 : les fondations, écrites seules), statut des six étapes, des tâches (branche, worktree, agent, base, commit) et des quatre revues, journal des changements. Écriture atomique sous le verrou à bail `run:<spec>` : des agents parallèles ne perdent aucune mise à jour. Transitions vérifiées (dépendances faites avant de démarrer une tâche, commit existant pour la terminer, raison pour rouvrir). `apv run next` donne, de façon déterministe, l'étape courante, les tâches prêtes, les tâches à reprendre et celles à relancer (worktree disparu, aucun commit après la base), les revues à lancer, et signale une spec modifiée depuis le lancement : la reprise après coupure part de là. `apv status` affiche une ligne par exécution en cours.
- **`apv stack plan|merge`** : la fusion d'une pile de PR qui a manqué dans le projet pilote (incident 30). `plan` vérifie la pile sans rien modifier (PR ouvertes, chaque base sur la tête de la précédente, fusionnables, contrôles au vert ou absents) et liste toutes les anomalies. `merge` exige `APV_ALLOW_MERGE=1`, refait la vérification juste avant chaque fusion, re-cible la PR suivante et constate la nouvelle base par une relecture (jamais par le seul code de sortie), fusionne avec `--match-head-commit`, constate la fusion, affiche en entier la sortie de chaque appel `gh` et s'arrête à la première anomalie. `--ready` retire le statut brouillon sur ordre de l'opérateur. `APV_GH` permet les tests avec un faux `gh`.

- **Corrigé : hooks inactifs derrière un lien symbolique.** Chaque hook comparait son chemin résolu au chemin de lancement non résolu : un plugin atteint par un lien symbolique (dossier de plugin lié, `/var` sous macOS) n'exécutait aucun hook, sans message, garde de force-push et de fusion comprise. Les chemins sont maintenant comparés résolus (`isMainModule`).
- **Corrigé : chemins résolus comme les racines de Git.** Les commandes affichaient des chemins relatifs en `../../..` quand le dossier courant passait par un lien symbolique (CI macOS en échec depuis la phase 1), et un dossier d'aperçu pas encore créé, dans un dépôt atteint par un lien, échappait au refus « dans le dépôt ».
- **Corrigé : ordre de la file des verrous.** Les tickets sont datés par l'horloge murale, commune aux processus, et non plus par `performance.timeOrigin`, estimé par processus : un second demandeur pouvait passer devant le premier. Le ticket du détenteur, encore présent un instant après l'acquisition, n'est plus compté comme un demandeur (affichage de la file et positions).
- **Corrigé : aperçu, dossier vérifié d'abord.** `apv preview update` refuse un dossier d'aperçu étranger avant d'arrêter le serveur en cours ou de vérifier le port : un refus ne coupe plus l'aperçu pour rien.

## Unreleased — reliability and efficient feature work

- **Un rôle voit enfin les bornes qu'on lui impose.** Le schéma transmis au fournisseur passait par `strictSchema`, qui ne garde que les mots-clés portables des sorties structurées — `maxLength` et `maxItems` n'en font pas partie et disparaissaient. On demandait donc un document précis et complet sans jamais dire qu'un champ est limité à 300 caractères, puis on rejetait le document entier pour trente-cinq caractères de trop. Constaté quatre fois en un après-midi sur une seule spec : une décision d'architecture à 873 caractères pour 800, une description de surface à 335 pour 300, un CSS de maquette à 21 445 pour 20 000. La borne est désormais énoncée dans la `description`, que tout fournisseur transporte : « 1 to 800 characters » seule, ou ajoutée entre parenthèses à la description existante. Le jeu de mots-clés reste strictement portable — le test qui l'épingle à chaque profondeur est inchangé et c'est lui qui a écarté la première tentative, qui passait `maxLength` directement. `Schema.parse` demeure la seule autorité qui refuse.

- **La QA ne suit plus la voie de la tâche qu'elle contrôle.** `qaProfile` valait `lane` par défaut : sans configuration, le rôle chargé de vérifier le travail des trois autres prenait le profil de la voie du candidat — donc le profil rapide sur une tâche rapide, et le profil rapide encore sur tout projet qui n'avait rien déclaré. Le contrôleur pouvait ainsi être plus faible que ce qu'il contrôle, et c'est précisément sur les tâches les moins risquées, celles qu'on relit le moins, que l'écart passait inaperçu. Le défaut passe à `deep` : la QA prend le profil profond quelle que soit la voie relue. Le réglage ne nomme aucun modèle — un projet qui déclare le même modèle partout ne change rien, il continue simplement de relire avec son profil profond — et `qaProfile: 'lane'` reste disponible pour qui veut l'ancien comportement. Constaté sur un vrai projet : les quatre rôles étaient figés sur un même modèle en effort moyen, et personne n'avait remarqué que la QA héritait du niveau de ce qu'elle jugeait.

- **Product regarde enfin au-delà du dépôt avant de faire écrire un mécanisme.** Tout ce qu'il était invité à réutiliser regardait vers l'intérieur : l'inventaire, les symboles existants, « prefer reuse over parallel abstractions ». Rien ne lui demandait de vérifier qu'une bibliothèque éprouvée fait déjà le travail. Combiné à la règle voisine — une installation que l'Implementer ne peut pas exécuter devient un prérequis opérateur — cela se lisait facilement comme une invitation à tout écrire à la main pour garder le manifeste intact. Une capacité manquante borne pourtant *qui* exécute une étape, jamais si le projet a le droit d'utiliser une bibliothèque. Product doit désormais nommer la bibliothèque qu'il veut, même absente du projet, et l'énoncer comme prérequis dans une décision. Constaté sur un vrai projet : un design a réécrit ses propres courbes d'accélération alors que le paquet qui les fournit tenait en une ligne d'import, et la page produite paraissait terne pour cette raison même.

- **Une erreur de schéma dit enfin laquelle de ses règles a été violée.** `s.string` était le seul validateur muet : `number` annonce « expected integer in [1, 200] », `enum` liste ses valeurs, `boolean` dit ce qu'il attendait, mais une chaîne trop longue, vide, contenant un NUL ou ne respectant pas son motif produisait le même « invalid string ». Le rôle qui recevait ce refus ne pouvait pas se corriger, et la réparation de sortie prévue pour ce cas ne servait à rien : elle relançait le même texte contre la même règle invisible. Constaté sur un vrai projet, où une planification a échoué sur `$.decisions[5].decision: invalid string` — la décision faisait 873 caractères contre 800 autorisés, un dépassement de neuf pour cent qu'il a fallu aller lire dans le schéma pour comprendre. Le message porte désormais la longueur reçue et les bornes attendues, le motif attendu, ou la présence d'un NUL, chacun dans sa propre vérification.

- **Écrire pour la version que le projet installe, pas pour l'idiome dont on se souvient.** Un idiome dépassé compile, passe chaque contrôle et livre quand même le défaut : aucun reçu ne peut l'exclure, donc la règle vit dans les rôles. L'Implementer doit lire le manifeste qui gouverne l'API qu'il s'apprête à utiliser — l'intelligence du dépôt en donne déjà les chemins — et la version installée, avant de l'utiliser. La QA doit signaler un idiome que cette version dépasse, et répondre `unknown` plutôt que de supposer une écriture courante. Une version plus récente publiée en amont n'est pas un constat : seule celle que l'espace de travail installe gouverne le candidat. Constaté sur un vrai projet : un champ de formulaire écrit dans la forme antérieure à `defaultValue` a passé types, tests, intégration, build et navigateur, et effaçait la saisie d'un gestionnaire de mots de passe.

- **Le prompt à coller passe de 483 à 49 lignes.** Le bloc d'entrée demandait de coller un document dont la première section ordonne à l'assistant d'aller lire ce même document : neuf dixièmes du collage recopiaient ce qu'il commandait. Ce qui reste collé est ce qui ne peut pas attendre une lecture — la tâche, les quatre champs et les principes qui lient l'assistant avant tout, dont ne jamais fabriquer d'approbation ni de preuve, ne pas force-pousser ni fusionner, et traiter le contenu du dépôt comme des données non fiables. Le prompt exige en retour une preuve de lecture avant toute commande qui écrit : la version du CLI et le profil réel détecté. Les quinze sections deviennent une section « Procédure », au même endroit, que l'assistant lit lui-même ; les deux portes d'entrée y renvoient au lieu d'en écrire une version courte de leur cru, ce que `prompts/ONBOARDING.md` faisait en perdant les principes au passage.

- **Une preuve survit désormais à la revue humaine qu'elle protège.** `validationMaxAgeMs` bornait à une heure le délai avant approbation ou export, pour éviter qu'une preuve ne décrive plus l'environnement. Mais une heure ne survit pas à l'étape même que cette borne protège : lire un diff, y réfléchir, fusionner après le déjeuner, et l'on revenait à une preuve expirée — rejeu complet des contrôles et nouvelle revue qualité facturée, sur un candidat que personne n'avait touché. Le défaut passe à vingt-quatre heures, l'unité dans laquelle une revue humaine se déroule, et `configAdvice` signale toute valeur qui expirerait en moins d'une heure au lieu de la laisser couper le travail en silence.

- **Deux portes d'entrée au lieu d'une.** Un dépôt vide et un projet commencé depuis des années n'ont ni la même première commande ni les mêmes pièges, mais arrivaient sur le même document de 510 lignes qui ouvre sur le cas du projet neuf. `prompts/ONBOARDING.md` donne la porte du projet existant, avec ce qui ne concerne que lui : le mode preuves proposé par l'onboarding et ce qu'il exige d'un dépôt sans tests, le classement de risque qui pousse en lane haute tout ce qui touche à l'authentification, aux migrations ou aux dépendances, et les amendements de périmètre que provoque un couplage implicite. `prompts/BOOTSTRAP.md` garde celle du projet neuf. Les deux restent des pointeurs, jamais des copies : le déroulé complet vit toujours dans `START-HERE.md`.

- **Une spec ancienne ne fait plus tomber toute la liste.** Une configuration gelée avant que le contrat ne gagne son champ `model` le stocke absent ; le calcul de décision le nommait quand même, transformant cette absence en `undefined`, sur lequel aucune identité ne peut être calculée. `spec list` et le tableau de bord échouaient donc entièrement à cause d'une seule spec ancienne, au lieu de la signaler. Les champs absents sont désormais omis plutôt que portés comme indéfinis. Même famille que le gel de publication corrigé plus haut : une forme enregistrée hier, relue par le contrat d'aujourd'hui.

- **Un conseil de progression ne masque plus la cause d'un blocage.** Une spec publiée puis arrêtée par sa revue qualité était invitée à synchroniser : `spec sync` rapportait la fusion, réclamait une revue de candidat que le rapport interdisait d'enregistrer, et renvoyait au même endroit. Le conseil capable de la débloquer — autoriser une réparation ou ouvrir une spec de suite — n'était jamais affiché. Le conseil d'une erreur passe désormais avant celui de la publication, et l'avis donné après une fusion observée dit ce qui bloque réellement quand la revue demande des corrections. Constaté sur un vrai projet : six contrôles verts, vingt critères tenus, et une boucle de deux commandes.

- **Une validation qui a échoué ne fige plus la spec sur son échec.** Un run en échec est terminal et ne peut jamais reprendre : tant qu'il restait le run final, `spec run` se contentait de rejouer le même message, et `spec verify` refusait de revalider ce qui n'était pas une validation complète. Une spec dont le seul tort était un contrôle tombé une fois — un service absent, une suite instable — n'avait plus de chemin vers une preuve complète. La validation ratée est désormais dépassée : elle reste dans l'historique comme l'observation qu'elle est, et la prochaine exécution gagne sa preuve dans une tentative neuve, sur le même candidat.

- **Le nombre de reprises d'une sortie malformée est amendable.** `maxOutputRepairs` était gelé à l'approbation, à une seule reprise. Un rapport de QA de 35 000 tokens qui sort en JSON invalide arrêtait donc la spec sur un problème de forme sans rapport avec le code — dix-huit sorties de rôle rejetées sur une seule spec réelle. `spec budget` peut désormais le relever, dans les bornes du contrat : un rapport illisible ne dit rien du candidat, et réessayer sa mise en forme n'abaisse jamais ce qu'il doit prouver. L'approbation, les preuves et les contrôles sont inchangés.

- **Une spec rejetée par la QA nomme la réparation qu'elle peut encore autoriser.** `QA_REJECTED` conseillait uniquement de créer une spec de suite, alors que `spec qa-repair` accepte ce code depuis son ajout : le recours existait et n'était nommé nulle part. Le conseil propose désormais l'autorisation quand chaque contrôle configuré a prouvé ce candidat, et la spec de suite sinon — la précondition étant énoncée une seule fois, partagée par la commande et par le conseil. Trouvé en écrivant la propriété « la commande annoncée débloque réellement », qui prolonge chaque scénario jusqu'à la reprise au lieu de s'arrêter au panneau.

- **Les règles de décision sont énoncées comme des propriétés.** Ce qui décide de la preuve due par un changement — classement du risque, plan de contrôles, frontières de périmètre, identité d'un contenu, empreinte d'un échec — était vérifié par une poignée d'exemples écrits à la main. `test/policy-properties.test.mjs` en énonce dix règles et les éprouve sur l'espace d'entrée : ajouter un fichier n'abaisse jamais l'assurance due, un plan contient toujours ses dépendances et tous les contrôles obligatoires, `dir/*` ne traverse jamais un séparateur, une empreinte ignore durées, horodatages et pid sans confondre deux échecs distincts. Environ mille cas en moins d'une demi-seconde, sans espace de travail ni agent. Vérifié dans les deux sens sur deux familles de régression : un joker qui traverserait un `/`, et un classement qui ne jugerait qu'une partie du changement.

- **Les recours sont éprouvés depuis les états réellement atteints.** L'audit des codes d'erreur vérifie que chaque code est classé ; il ne peut prouver ni qu'un état est atteignable, ni que le conseil affiché nomme quoi que ce soit. `test/lifecycle-recourse.test.mjs` pilote le contrôleur réel avec des séquences de commandes et de perturbations — un contrôle qui se met à échouer, une revue qui exige une correction, une enveloppe épuisée, une branche qui avance — et échoue dès qu'un code déclaré « actionnable par l'opérateur » retombe sur le repli générique « Resolve CODE ». Deux scénarios scriptés garantissent la couverture, l'exploration aléatoire (`fast-check`, devDependency : aucune dépendance runtime ajoutée) cherche le reste. Vérifié dans les deux sens : retirer le conseil de `GATES_FAILED` fait échouer la suite — et le tirage aléatoire seul, lui, restait vert, ce qui montre pourquoi la garantie ne peut pas reposer sur le hasard.

- Audit des recours : inventaire syntaxique des codes d’erreur, catalogue des actions et lacunes, et test de couverture pour les nouveaux codes ou expressions dynamiques. Ce contrôle classe les refus ; il ne modifie pas les reprises du moteur et ne garantit pas leur accessibilité.

- **Fusionner une spec ne l'empêche plus de se clore.** Le dépôt source doit être propre et rester sur la base de la spec : un plan approuvé contre un état du dépôt ne doit pas s'implémenter contre un autre, et ce garde-fou ne bouge pas. Mais il s'appliquait aussi quand la branche avait avancé **à cause du travail de la spec elle-même** : une fois la pull request fusionnée, plus aucune exécution n'était possible, donc plus de preuve fraîche, donc plus de revue, donc plus de clôture — alors que `spec sync` voyait parfaitement la fusion et réclamait cette revue. Une branche qui contient déjà le candidat de la spec est désormais acceptée ; rien d'autre ne change, et les espaces de travail restent des worktrees détachés créés sur des commits explicites. Constaté sur un vrai projet : spec livrée, fusionnée, puis enfermée pour toujours par le déroulement le plus banal qui soit.

Mais l'opérateur qui a inspecté le constat n'avait aucun moyen de dire « le manque est dans le candidat, pas dans la configuration » : budget de réparation épuisé, plus aucune tâche restante donc pas de `spec replan`, et revue comme publication exigeant une QA conforme. `apv2 spec qa-repair SPEC_ID --confirm --note TEXT` autorise désormais exactement une réparation : elle exige que chaque contrôle configuré ait déjà prouvé ce candidat, elle est consommée par la réparation qu'elle autorise, son motif est enregistré, et la revue suivante doit toujours conclure sur ses propres preuves. La règle automatique ne bouge pas. Constaté sur un vrai projet : dix tâches, six contrôles verts, vingt critères — et trois assertions manquantes qu'aucune commande ne pouvait plus faire ajouter.

## V2 : notes non publiées (historique, avant APV3)

- **La phrase du fournisseur d'abord.** Un arrêt peut venir du compte, pas de la configuration : la limite de session d'un abonnement termine la session avec `subtype: success` et `is_error: true`, et la seule explication lisible est la phrase du fournisseur. Elle est désormais reprise telle quelle dans le message d'échec, avant les dépenses : « the provider said: "You've hit your session limit · resets 11:50am" ». Constaté sur un vrai run : l'opérateur ne voyait que « spent: 10 turns, 1.31 USD » et pouvait croire à un défaut de la pipeline.

- **Des valeurs par défaut qui avertissent au lieu de couper.** Les bornes livrées jusqu'ici arrêtaient le travail en cours : 32 tours, 5 $ par appel dans l'exemple d'installation, 15 minutes de délai, une seule passe de réparation. Sur un vrai projet, elles ont arrêté trois tours de Product et deux tentatives d'implémentation sans rien produire. Nouvelles valeurs : `agent.maxTurns` 200 (filet anti-boucle), `agent.maxBudgetUsd` null, `agent.timeoutMs` 30 min, `maxRunMs` 45 min (une session d'agent **plus** ses contrôles), `maxRepairAttempts` 3, et surtout `workflow.maxSpecCostUsd` activé par défaut à 25 $ — la seule borne qui avertit : elle s'arrête entre deux tâches, annonce le coût déclaré et attend une autorisation explicite. `apv2 inspect` signale dans `configAdvice` les réglages d'une configuration existante qui coupent le travail, avec la raison de chacun. Les exemples de configuration fournisseur sont alignés.

- **Un tour de rôle raté propose de relancer la rédaction.** Quand Product échoue (délai, refus, sortie invalide), la spec n'a rien à approuver ; l'action suivante proposait pourtant `spec approve --hash NO_VALID_PROPOSAL`. Elle propose désormais `spec refine` avec le code de l'échec, ou l'abandon, et la console affiche « Relancer la rédaction ». Les rôles enregistrent aussi ce que le fournisseur déclare (coût, tours, raison d'arrêt) dans `role.finished`, et un échec de rôle nomme cette raison avant l'extrait de sortie. Constaté sur un vrai projet : un tour de Product tué à 15 minutes, suivi d'une action inutilisable.

- **Voir ce qu'une tentative a coûté, et nommer ce qui l'a arrêtée.** Quand le fournisseur le rapporte, chaque tentative enregistre son coût déclaré, son nombre de tours et sa raison d'arrêt (`agent.usage`). Un échec dit désormais « the provider stopped it at its turn limit (agent.maxTurns); spent: 33 turns, 3.31 USD » avant l'extrait de sortie, au lieu d'un JSON de 2 000 caractères où la phrase utile était noyée. La console affiche le coût par tentative et le total de la spec. Nouveau réglage facultatif `workflow.maxSpecCostUsd` : la spec s'arrête sur `COST_BUDGET` en indiquant ce qui a été dépensé, et l'opérateur autorise explicitement la suite (`spec run --accept-cost`, ou le bouton de la console). Les coûts sont des valeurs **déclarées par le fournisseur**, jamais une facture vérifiée.

- **Des tâches taillées pour une session d'agent.** Product reçoit `executionCapabilities.attempt` — tours du fournisseur, plafond de coût, délai de l'agent, budget du run, passes de réparation — et la consigne de dimensionner chaque tâche pour une seule session, en découpant par surface (une route, un module ou un écran avec ses tests) plutôt que par couche. Une tâche plus grosse qu'une session n'est pas seulement plus lente : le fournisseur s'arrête en cours de route. Avant l'approbation, `sizeAdvice` signale à l'opérateur les tâches qui déclarent plus de huit fichiers ; c'est un avertissement, jamais un blocage. Constaté sur un vrai projet : une tâche de huit fichiers a épuisé deux fois la limite de tours.

- **Réparer tant que ça avance, s'arrêter dès que ça tourne en rond.** `maxRepairAttempts` accepte désormais jusqu'à 5 passes (1 par défaut, inchangé), et une passe qui laisse les contrôles échouer **exactement comme avant** arrête la boucle sur `REPAIR_NO_PROGRESS` sans dépenser les passes restantes. La comparaison porte sur une empreinte du diagnostic débarrassée de ce qui change à chaque exécution (durées, dates, pid, empreintes de commit) ; elle sert uniquement à cette décision, n'est jamais affichée et ne prouve rien. Constaté sur un vrai projet : la première réparation avait corrigé les tests, le contrôle suivant a trouvé une erreur de typage, et l'unique passe autorisée était déjà consommée.

- **Le travail d'un agent arrêté n'est plus jeté.** Un agent qui s'arrête sans rendre son résultat — limite de tours ou de budget du fournisseur, délai, sortie illisible — a déjà écrit des fichiers. La tentative reste désormais *interrompue* et récupérable : l'opérateur inspecte l'espace de travail, puis `spec run --accept-current` enregistre ce travail et le soumet aux contrôles, à la QA et à sa revue, ou `spec retry --confirm` le jette et recommence. Rien n'est adopté sans cette décision explicite, et aucun contrôle n'est allégé. L'action suivante et la console proposent les deux issues. Constaté sur un vrai projet : deux tentatives arrêtées sur « Reached maximum number of turns (32) », chacune après avoir écrit presque tout le code, perdues toutes les deux pour 6 $.

- `apv2 spec retry` transmet à la nouvelle tentative pourquoi la précédente s'est arrêtée : son erreur, le diagnostic des contrôles en échec (borné) et son résumé. La tentative repart de la base approuvée ; sans ce contexte, elle pouvait refaire la même erreur. `GATES_FAILED` propose désormais `spec retry` comme action suivante, et la console affiche le bouton. Constaté sur un vrai projet : une tâche arrêtée sur une erreur de typage dans un test qu'elle avait écrit.

- **Tableau de bord local** : `apv2 ui`. Specs par dépôt avec statut et action suivante, détail complet (critères et verdict QA, tâches, tentatives et contrôles, maquettes, amendements, avertissements), activité des agents **en direct**, opérations lancées et maintenance. Actions de la CLI depuis la page (brouillon, affinage, approbation, exécution, revalidation, nouvelle tentative, amendements, revue, synchronisation, rejet, nettoyage) ; la purge reste au terminal. Sans dépendance, lié à `127.0.0.1`, jeton d'entrée échangé contre un cookie `HttpOnly; SameSite=Strict`, contrôle de l'en-tête `Host`, jeton anti-CSRF et même origine pour toute action, hash exact et note pour toute approbation, maquettes en *sandbox*. Les opérations longues sont des processus CLI séparés qui survivent à la page.

- **Adoption de preuve** (décision de l'opérateur) : pour une spec à une tâche, la validation d'intégration adopte les reçus de la tâche au lieu de rejouer les contrôles, sous conditions strictes (même commit, base, changements, voie, plan de contrôles, préparation, environnement remesuré, preuve fraîche). Les reçus adoptés sont `cached` avec `reusedFrom`, la fraîcheur n'est jamais prolongée, l'approbation humaine reste exigée. Toute différence refuse l'adoption avec sa raison et rejoue les contrôles. L'identité générale des preuves est inchangée.
- **Aperçus de maquette** : `stylesheets` fait charger les feuilles de style globales du projet avant le CSS de la maquette, qui n'écrit plus que ses ajouts. Mêmes garanties que les ressources (suivies au commit de référence, résolues physiquement), `.css` seulement, bornées, et refus de tout texte pouvant fermer l'élément `<style>`. L'effet sur la durée de l'étape reste à mesurer sur un vrai run.
- **`impactAdvice` moins bruyant** : un test non déclaré n'est signalé que s'il importe le fichier par un chemin relatif résolu ; chaque entrée indique sa preuve (`declared-later`, `resolved-import`). Rejoué sur deux vraies specs : 6 alertes pour 2 vraies ruptures deviennent 3 alertes gardant les 2 ; 4 fausses alertes deviennent 1.

- Retire le lien symbolique `node_modules` commité par erreur (PR #22) et ignore désormais `node_modules` quel que soit son type : la règle `node_modules/` ne visait que les dossiers. Un test vérifie que le dépôt ne suit aucun lien symbolique.

- `apv2 spec retry` reconstruit la tâche à partir de l'état actuel (spec effective, amendements approuvés, consigne de réparation en vigueur) au lieu de rejouer la copie figée de la tentative échouée. Constaté sur un vrai projet : après un correctif de la consigne de réparation QA, la relance a rejoué l'ancienne consigne et le correctif ne pouvait pas s'appliquer à la spec pour laquelle il avait été fait.

- La QA reçoit `taskSummaries`, ce que chaque tentative a rapporté : un critère qui demande à l'Implementer de *signaler* quelque chose devient vérifiable, au lieu de rester « inconnu ». Son rôle précise qu'un résumé est une affirmation, jamais une preuve du comportement.
- Une réparation QA sait qu'elle peut toucher, au minimum, un fichier hors périmètre quand un constat l'exige : le contrôleur demande alors un amendement explicite. Elle reçoit aussi les résumés des tâches, et doit dire précisément quand un constat ne se corrige pas dans les fichiers.
- `NO_CHANGE` indique ce que la dernière tentative a expliqué et propose `spec retry` ou une spec de suivi.

Constaté sur la spec de nettoyage d'un vrai projet : la QA a relevé un commentaire devenu faux dans un fichier hors périmètre et n'a pas pu vérifier un critère portant sur les résumés ; la réparation, cantonnée au périmètre, n'a rien changé et la spec s'est arrêtée sur `NO_CHANGE`.

Défauts constatés en bouclant l'incrément 2 d'un vrai projet :

- `apv2 spec publish --for-review` ouvre la PR brouillon **avant** l'approbation, pour lire le candidat sur la forge (contrôles valides et QA passée exigés). Une fusion observée avant la revue ne clôture pas la spec : `MERGED_BEFORE_REVIEW`, puis clôture au `spec sync` suivant la revue.
- `apv2 spec close` accepte une spec **revue** sans bundle de livraison : l'opérateur peut intégrer le candidat lui-même.
- `apv2 prune` ne propose jamais la spec qui porte la direction visuelle que la prochaine maquette prolonge (`kept` dans la simulation).
- Rejeter une spec libère son pointeur de run, et une spec terminale dont le pointeur est resté sans processus vivant redevient collectable par `gc` et `prune`.
- Product reçoit la consigne de ranger un test impacté dans la première tâche qui change ce qu'il compare, et l'opérateur voit `impactAdvice` avant d'approuver : tests existants qui citent un fichier d'une tâche mais sont rangés plus tard ou nulle part. Avertissement lexical, non bloquant.
- La recherche des tests impactés résout les chemins relatifs cités (`../db`) et lit comme du texte les fichiers de test que Git classe comme binaires. Rejouée sur la spec réelle, elle signale désormais les deux tests qui avaient bloqué la première tâche, avec quatre signalements qui n'ont pas cassé.

- Tests : les faux fournisseurs transmettent la requête à leur sous-processus par un fichier temporaire (`test/support/run-worker.cjs`) au lieu de `spawnSync({ input })`. Sur macOS / Node 22.16, ce sous-processus ne voyait parfois jamais la fin de son entrée et restait bloqué, ce qui faisait échouer ou annuler la CI de `main` depuis plusieurs fusions. Le blocage a été localisé grâce à l'instrumentation de la #17 : entrée du faux fournisseur lue, sous-processus lancé, puis `spawnSync … ETIMEDOUT`. Le framework lui-même n'utilise aucun lancement synchrone de processus.

- Les rôles Implementer et QA encadrent les commentaires : documentation des déclarations publiques dans la convention du langage hôte (JSDoc, Javadoc, docstrings, rustdoc…) et notes qui expliquent *pourquoi* ; jamais de preuve ni de journal en commentaire (valeurs calculées, listes de vérifications, historique, identifiants de run). La QA signale ces commentaires comme constat mineur. Constaté sur un vrai projet : un en-tête CSS de trente lignes listait des ratios de contraste calculés, non vérifiés, qui deviennent faux dès qu'une couleur change.

- **La QA juge la spec effective, pas le texte stocké.** Son contexte portait `r.content`, si bien qu'une correction de critère approuvée n'atteignait jamais la QA, et qu'un amendement de périmètre approuvé était signalé comme hors périmètre. Tous les rôles reçoivent maintenant la même vue : critères corrigés, vérifications d'exigences de sécurité corrigées, chemins amendés — plus la liste des amendements approuvés avec leur motif et leur relecteur. Constaté sur le vrai projet juste après la première correction de critère : la QA citait encore l'ancien texte.
- `apv2 spec criterion` peut corriger, dans la même approbation, les **exigences de sécurité qui vérifient ce critère** (`requirements: [{id, verification}]`) : elles portaient la même contrainte intenable. Une exigence qui ne vérifie pas le critère est refusée.
- Une preuve de validation expirée (`STALE_EVIDENCE`) indique désormais `apv2 spec verify` comme action suivante.

- Nouveau recours `apv2 spec criterion` : corriger **un** critère d'acceptation devenu intenable sur une spec en cours d'exécution, en deux temps (proposition avec hash, puis approbation explicite avec motif). Le texte approuvé reste dans le magasin, la correction porte sa propre approbation, et l'évaluation rouvre (QA et dossier de revue invalidés). Constaté en pilotant un vrai projet : un critère promettait qu'un test ne changerait pas, alors que la migration approuvée modifiait ce que ce test compare ; 18 critères sur 19 passaient et la seule issue était de jeter un candidat fini.
- Un fournisseur qui échoue est rapporté avec son code de sortie, sa durée et **sa propre sortie** (stdout compris, extrait centré sur l'échec). Constaté en pilotant un vrai projet : une tâche s'est arrêtée sur `Agent failed: ` — message vide, parce que seul stderr était lu et que le fournisseur avait écrit son refus sur stdout. Même correction pour les rôles.

Corrections issues d'un audit externe qui a rejoué chaque défaut sur l'archive `de9d782`. Une suite verte ne couvrait aucun de ces parcours.

- **La maquette approuvée atteint enfin l'implémentation.** L'Implementer reçoit le markup et la feuille de style que l'opérateur a approuvés (borné : au-delà du budget, il reçoit la description et le chemin de l'aperçu), plus le chemin du fichier d'aperçu de ses écrans. QA reçoit la maquette et doit signaler un écart visible comme constat. Auparavant les deux ne recevaient qu'une paraphrase, et QA rien du tout.
- **Le dossier de revue ne détruit plus les maquettes approuvées.** Il ne reconstruit que ce qui lui appartient (worktree du candidat, patch, REVIEW.md, QA.md, INVENTORY.md) au lieu d'effacer le répertoire parent, qui contient le bundle design. `REVIEW.md` pointe désormais vers les aperçus.
- **Un nouveau candidat remplace la revue précédente au lieu de bloquer la spec.** Après une réparation QA, `r.review` est explicitement invalidé ; `REVIEW_STALE` ne peut plus enfermer une spec dans un blocage définitif.
- **Les documents de revue suivent ce qu'ils décrivent.** L'identité du dossier couvre candidat, spec, design, rapport QA et résultats de gates : un rapport QA remplacé sur le même candidat régénère `QA.md` sans reconstruire le worktree.
- **Une revue sémantique qui échoue ne perd plus la proposition Setup.** Elle est persistée avant la revue, et l'échec est enregistré avec son code et son message au lieu de laisser un document « pending ».
- **Un commit du Decision Ledger ne peut plus emporter le travail indexé de l'opérateur** : le commit porte un pathspec limité aux deux fichiers du ledger.
- **Une ressource de maquette ne peut plus être lue hors du dépôt.** Le chemin est résolu physiquement (un répertoire du dépôt peut être un lien symbolique) et doit être un fichier suivi par Git au commit de référence.
- **L'action suivante d'une spec bloquée lève son blocage** : amendement de périmètre avec son identifiant, `retry`, `recover`, suivi explicite après QA rejetée, au lieu de rejouer `spec run` qui reproduit le même arrêt.
- **La réutilisation d'une validation dépend de la preuve, pas de la revue humaine** : une spec à une tâche réutilise sa validation quand tous les gates configurés sont passés sur le même candidat et qu'aucune approbation n'est perdue. Quand la voie exige des approbations, la validation d'intégration reste exécutée — c'est délibéré.

- Les règles structurelles d'une spec (au moins une tâche, chaque critère rattaché à une tâche) s'appliquent dès qu'une spec est produite sans question, au lieu d'être vérifiées seulement à l'approbation. Constaté en pilotant un vrai projet : un critère de non-régression rattaché à aucune tâche n'était signalé qu'au moment de l'approbation, 16 minutes après le début. Le message nomme désormais les critères orphelins, et `SPEC_COVERAGE` étant réparable, la boucle de réparation corrige le cas en un appel. La règle ne s'applique qu'à une sortie de rôle fraîche : un document déjà stocké reste lisible, quelle que soit la règle ajoutée après lui.
- `git config --get` reçoit `HOME` (et les variables de configuration documentées par Git) : l'identité de l'opérateur vit presque toujours dans le `~/.gitconfig` global, donc le repli sur `user.name` ne fonctionnait jamais et `--reviewer` était obligatoire. Les commandes Git qui écrivent gardent leur environnement minimal.

- `apv2 prune` était documentée et routée dans le cycle de vie, mais absente de la liste de commandes de `cli.ts` : le binaire répondait « Unknown command prune ». Un test vérifie désormais que chaque commande documentée dans l'aide atteint son gestionnaire.

- Continuité visuelle entre incréments : une nouvelle proposition design reçoit la direction déjà approuvée pour le dépôt (`establishedDesign`) et doit l'étendre — ne maquetter que les écrans créés ou modifiés, ne styler que ce qui est nouveau — au lieu de redériver une direction complète. Enregistrée dans `design.reusedFrom` et visible dans `INDEX.md`. Constaté en pilotant un vrai projet : l'étape design coûtait 401 s sur 748 s en redessinant des écrans inchangés.
- Le validateur de maquettes analyse les éléments et leurs attributs, et non le texte affiché : une maquette peut montrer du markup échappé, `src=` ou une URL comme contenu. L'analyse tient compte des guillemets, donc un `>` dans une valeur d'attribut ne masque plus un attribut suivant.
- Une maquette peut utiliser les polices et images du dépôt : `assets` déclare des fichiers (chemin relatif au dépôt), référencés par `url(asset:ID)`, que le contrôleur insère dans l'aperçu en `data:` URI (512 Kio par fichier, 2 Mio au total, pas de SVG ; CSP `font-src data:`). Toute autre forme de `url()` et `@import` restent refusées. Les aperçus peuvent enfin montrer la typographie réelle du projet.
- Nouvelle commande `apv2 prune [--id ID] [--older-than DAYS] [--confirm]` : supprime du magasin les documents abandonnés (specs terminées ou brouillons jamais approuvés, plans jamais appliqués) avec leurs runs, reçus, événements et workspaces. Simulation par défaut, rien de plus récent que 30 jours, et jamais un document verrouillé, actif ou appliqué.

- Diagnostics d’échec centrés sur les échecs : début et fin de la sortie plus les lignes portant un vocabulaire d’échec générique (fail, error, expected, ×…), jusqu’à 16 000 caractères (au lieu des 8 000 derniers caractères, qui masquaient quels tests échouaient). Sortie des gates capturée jusqu’à 1 Mio.
- Une réparation d’Implementer qui ne change rien s’arrête avec `REPAIR_NO_CHANGE` au lieu de relancer les gates sur le même candidat.
- L’Implementer reçoit `repositoryIntelligence.referencingTests` (tests existants qui référencent ses fichiers, marqués `outsideScope`) et doit mettre à jour un test cassé par un changement voulu plutôt que laisser échouer : le contrôleur demande alors un amendement de périmètre explicite. Product doit inclure ces tests quand un contrat partagé change.
- `role.finished` enregistre `timingsMs` (avant lancement, processus, contrôle du workspace, validation).
- Les crochets et parenthèses sont des caractères littéraux dans les chemins et globs (routes dynamiques `[id]`, groupes `(app)`) ; accolades et négation `!` restent refusées. Une erreur `GLOB` dans une réponse de rôle devient réparable. Constaté en pilotant un vrai projet : une spec valide était rejetée et tout le tour Product (7,5 min) perdu.
- Garde déterministe `SPEC_CAPABILITY` : une spec ne peut pas confier un fichier généré par l’outillage (`workflow.generatedPaths`, lockfiles par défaut) à un Implementer sans shell ; appliquée aux propositions Product, importées et à l’approbation.
- Limites configurables `limits.maxTaskContextChars` (défaut 120 000, plafond 400 000) et `limits.maxQaDiffBytes` (défaut 512 Kio, plafond 8 Mio).
- Pilote opt-in `npm run pilot:repair` : prouve avec un vrai fournisseur que la boucle de réparation transmet l’erreur du contrôleur et obtient une réponse corrigée (au plus deux appels).
- Réparation bornée des sorties de rôle (Setup, revue sémantique, Product, design, QA) : une violation du contrat du contrôleur réinvoque le rôle avec l’erreur exacte, jusqu’à `workflow.maxOutputRepairs` (défaut 1). Délais, annulations, refus de permission et échecs de processus ne sont jamais réessayés.
- Contexte de tâche ciblé : la proposition design associe écrans et tâches (`taskScopes`) ; une tâche ne reçoit que ses écrans, et aucune tâche sans travail visuel ne reçoit le design.
- Product reçoit `executionCapabilities` (outils réels de l’Implementer, setup, gates) et doit transformer les étapes impossibles (installation, lockfile, générateur) en prérequis opérateur.
- `requiresDesign` ne détecte plus l’interface par extensions de frameworks : `uiImpact` déclaré et vocabulaire générique uniquement.
- Nouvelles commandes `apv2 decisions plan|apply` (mise à jour du Decision Ledger liée à un hash, `supersedes` explicite), `apv2 gc [--confirm]` (nettoyage prudent, simulation par défaut) et `apv2 spec list --active`.
- Les commits candidats portent le titre de la tâche, avec un trailer `Agent-Pipeline-Run`.
- Tests de régression rejouant les échecs réels observés (vérification > 3000 caractères, markup refusé, SHA QA erroné, métadonnées de clarification sur une décision confirmée, délai dépassé).
- Ajoute un inventaire déterministe et indépendant de la stack (`src/knowledge/inventory.ts`) : profils de langage déclaratifs (extension, préfiltre, grammaire, règle de surface publique) et repli en unités de fichier pour toute autre technologie texte, sans nom de framework dans le contrôleur (verrouillé par un test).
- `knowledge.languages` dans `pipeline.v2.json` permet d’ajouter ou de remplacer un profil de langage.
- Repository Intelligence transmet `inventory` (toute la surface publique bornée) à Product et Implementer ; `reuseCandidates` découpe les identifiants (camelCase, snake_case, chemins) et monte à 40.
- QA reçoit `inventoryDelta` (ajouts, retraits, `possibleDuplicates`) et doit signaler une réimplémentation injustifiée d’un comportement existant comme constat `major`.
- Le review workspace ajoute `INVENTORY.md` et une section « Public surface changes » dans `REVIEW.md` ; nouvelle commande `apv2 inventory`.
- Product doit inclure le document d’architecture existant dans une tâche lorsqu’une spec change frontières, interfaces publiques, persistance, authentification/autorisation, conventions ou une décision enregistrée.
- Régénère `examples/schemas/config.schema.json` et `task.schema.json`.
